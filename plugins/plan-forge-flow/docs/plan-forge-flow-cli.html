1. Архитектура и слои

Плагин — это набор независимых частей, которые общаются только через файлы и JSON на stdin/stdout. Один и тот же бинарь обслуживает оба хоста; хост выбирается флагом --host codex|cursor.

  • Skill/команда хоста — инструкции для LLM-оркестратора. Два комплекта: skills/forge/ (Codex: workflow.md, native-plan-ux.md, model-selection.md) и cursor/skills/forge/ (Cursor: workflow.md, native-plan-contract.md, model-waiver.md) плюс слэш-команда cursor/commands/forge.md. Здесь живёт всё «поведение», включая требование работать в Plan mode: сам CLI режим не проверяет.
  • CLI (bin/<rid>/planforge через launcher) — конечный автомат-привратник: валидирует, пишет состояние, отказывает при нарушении инварианта.
  • Hook (UserPromptSubmit → planforge hook capture-context) — только для Codex: читает транскрипт сессии и переносит последний предложенный план в файл. У Cursor хуков нет — их роль играет внешний PendingRun.
  • Agents — agents/forge_builder.toml, forge_reviewer.toml для Codex (постоянный билдер workspace-write, свежий ревьюер read-only) и cursor/agents/forge-builder.md, forge-reviewer.md для Cursor (свежие и билдер, и ревьюер; readonly: true — только флаг намерения).

Две политики JSON

Сериализация — source-generated, без reflection, двумя разными контекстами:

  • ForgeJsonContext — всё, что принадлежит Forge (ForgeState, PendingRun, манифест, pending-план, stdin-запросы, все DTO ответов). Политика UnmappedMemberHandling.Disallow: любое лишнее поле роняет чтение. Свои файлы fail-closed.
  • CodexJsonContext — payload'ы Codex (вход хука, записи транскрипта). Политика Skip: новое поле в Codex не должно ломать захват плана. Чужие данные fail-open.

JsonOutput.Success принимает JsonTypeInfo<JsonSuccess<T>> явным параметром, поэтому забытая регистрация DTO в контексте — ошибка компиляции, а не рантайма. Любой stdin читается через JsonInput.Read, который снимает BOM перед разбором.

Контракт вывода

{"ok":true, "command":"build dispatch", "data":{...}}
{"ok":false,"command":"review verdict","error":{"code":"verdict","message":"…","details":[…]}}

Коды выхода: 0 — успех; 1 — usage/environment/unexpected; 2 — verdict (провал ревью, покрытия, чувствительные данные); 3 — state (нарушен инвариант автомата, включая unsupported-state-schema). Исключение — hook capture-context: он пишет объект в формате хуков Codex (без обёртки CLI) и всегда возвращает 0.

3. Границы доверия и одобрение

Граница доверия Codex. Стейджинг — не одобрение. Хук не определяет режим текущего хода и ничего не блокирует: он просто обновляет pending-план, если в транскрипте есть Plan-mode превью. Требования «Act 1 только в Plan mode» и «материализовать только в первом Default-ходе» живут исключительно в skill; CLI их проверить не может и не пытается. Одноразового токена одобрения нет, привязки к конкретному ходу или сессии нет. Любой процесс с доступом к ~/.codex/plugin-data может подменить pending-план.
Граница доверия Cursor: ревью и исполнение развязаны намеренно. Ревьюер видит чат-черновик, а собирается по нативному файлу. Единственное, что связывает их, — это идентичность прогона: маркер <!-- plan-forge-flow:run=<id>;workspace=<scope> --> и идущая ровно за ним преамбула. Ни пути, ни хеша черновика в PendingRun после finalize не остаётся: draftText стирается. При материализации CLI проверяет у нативного файла только форму — маркер, преамбулу, отсутствие секретов и корректный ## Approach — и берёт его текст целиком (включая frontmatter Cursor) как .forge/PLAN.md. Тело может сколь угодно отличаться от одобренного черновика, и это зафиксировано как решение (native-plan-contract.md: «user edits to the native plan do not require another plan review»). Хеш транзакции защищает атомарный replay, а не идентичность одобрения. Практическое следствие: PLAN-REVIEW-LOG.md описывает один текст, а PLAN.md и tasks[] происходят из другого.

4. Состояние, фазы и стадии

Состояние прогона живёт в .forge/state.json. Документ версионирован явно: schemaVersion: 1 плюс host (codex|cursor). Отсутствующая, нулевая, чужая или будущая схема отклоняется как unsupported-state-schema до любой мутации. Совместимость держится и строгостью чтения: лишнее или переименованное поле роняет загрузку. Константы ForgeState.Version = 5 и Generation = "v4" существуют только для вывода run status и поля generation в манифесте улик.

Запись идёт только через StateStore.Update: берётся workspace-лок, состояние перечитывается, при наличии ожидаемого снимка сравниваются SHA-256 сериализованных документов (оптимистическая блокировка против гонок между параллельными вызовами CLI), затем документ пишется атомарно — temp + fsync + rename. Опциональный колбэк beforePersist позволяет зажурналировать будущий документ до записи — этим пользуется транзакция Cursor.

Таблица стадий — ядро автомата

DispatchStages.Definitions — единственный источник правды о том, как ведёт себя каждая стадия dispatch:

DispatchStage.Code      → (Reviewer, CodeReview, freshReview: да,  closedByBuilder: нет)
DispatchStage.Build     → (Builder,  Build,      freshReview: нет, closedByBuilder: да)
DispatchStage.FixBuild  → (Builder,  CodeReview, freshReview: нет, closedByBuilder: да)
DispatchStage.FixReview → (Reviewer, CodeReview, freshReview: да,  closedByBuilder: нет)

Из таблицы выводятся: какая роль вправе зарегистрировать сессию, какая фаза требуется для dispatch, нужен ли свежий манифест улик, кто закрывает dispatch (build complete против review verdict) и что считается ревью-стадией (IsReview() = !CompletedByBuilder). Внешние имена стадий и фаз заданы словарём enum → string с обратным индексом, который обслуживает и разбор аргумента, и вывод.

review record-response --stage plan у Cursor не является dispatch-стадией. Команда работает с внешним PendingRun до материализации и хранит plan как тип ответа ревьюера. В DispatchStage такого значения нет.

5. Локи и идентичность репозитория

Каждый прогон привязан к scope id — первым 24 hex-символам SHA-256(gitCommonDir + "\n" + workspaceRoot) (на Windows обе части понижаются в регистре). Scope попадает в state.repositoryScopeId, в имена рефов refs/plan-forge/<scope>/… и в путь внешнего PendingRun. Благодаря этому linked worktrees одного репозитория не путают свои прогоны, а состояние, перенесённое в другой каталог, отклоняется до мутации.

ЛокКлючЧто защищает
RepositoryRunLock<root>/locks/<sha256(gitCommonDir)>.lockобщие для всех worktree'ев ресурсы: refs/plan-forge/*, info/exclude, внешние PendingRun
ForgeStateLock<root>/workspace-locks/<sha256(workspace)>.lock.forge/state.json конкретного рабочего дерева

Корень локов — %LOCALAPPDATA%/plan-forge-flow (или FORGE_LOCK_DATA), то есть вне репозитория: локи не видны в git status и не попадают в улики ревью. Сам лок — это удерживаемый OS-хендл (FileShare.None), а не факт существования файла, поэтому после падения процесса ядро освобождает его само и ручная чистка не нужна. Занятый лок сразу даёт ошибку state без ожидания.

Порядок вложения фиксирован: сначала repository lock, потом workspace lock. Методы, которые могут вызываться и напрямую, и изнутри уже удерживаемого repository lock, принимают флаг repositoryLockHeld.

Выбор моделей (Codex)

Команд выбора моделей в CLI нет: процедура описана в references/model-selection.md и целиком выполняется оркестратором.

  • Роли (ревьюер и билдер) спрашиваются по отдельности свободным текстом.
  • Нормализация: Unicode, регистр, разделители; канонические ID; уникальные алиасы отображаемых имён; русские и английские синонимы эффорта; исправление ровно одной однобуквенной опечатки при уникальном совпадении.
  • Источник истины о доступности — сам multi-agent-рантайм: билдер спавнится в «no-edit hold», чтобы неверная пара выяснилась до материализации.
  • Три попытки на роль, счётчики независимы; после третьей — остановка без дефолта и без материализации.
  • ultra и ультра запрещены всегда.

CLI видит только результат: ModelSelections.Validate проверяет модель по ^[A-Za-z0-9][A-Za-z0-9._\[\]=,-]{0,255}$, эффорт по ^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$, запрещает ultra и приводит эффорт к нижнему регистру. Существование модели в рантайме CLI не проверяет.

Ревью плана (Codex)

Каждый раунд — свежий read-only forge_reviewer; критика и sidecar-решение живут в переписке и в файлах, которые skill просит сохранить, но .forge/ в актах 1–2 ещё не существует, поэтому ни build dispatch, ни review verdict в этих раундах не вызываются. Начальный кап — 5 раундов; счётчики попадают в состояние только через completedReviewRounds и maxRounds в stdin материализации.

7. Хук hook capture-context только Codex

Program.Main перехватывает hook capture-context до общего парсера аргументов и передаёт stdin в HookService.Run. Это единственная команда, работающая по протоколу хуков Codex, а не по конверту CLI, и единственная, которая всегда завершается нулём. hooks/hooks.json вызывает RID-aware launcher с таймаутом 5 секунд.

  1. Вход ограничен 256 КБ, BOM снимается; при любой ошибке — тихо return 0 без вывода.
  2. Из HookInput читаются cwd и transcript_path; без любого из них хук молча выходит. Других полей DTO не содержит.
  3. TranscriptReader.ReadDocument построчно парсит rollout.jsonl (лимит 64 МБ, отказ на симлинках и симлинкнутых родителях, открытие с FileShare.ReadWrite | Delete, чтобы не конфликтовать с пишущим Codex).
  4. TranscriptReader.LatestPlan ищет последнее сообщение ассистента с phase = final_answer, mode = plan и телом <proposed_plan>…</proposed_plan> и снимает теги. Если такого нет — выход без вывода.
  5. PendingPlan.Write сохраняет канонизированный план в <plugin-data>/pending-plans/<sha256(cwd)>.json вместе с schemaVersion, host: codex и путём workspace.
  6. В additionalContext уходит текст: план застейджен, не материализовать его, пока текущий ход в Plan mode; в первом Default-ходе выполнить plan materialize с review-логом, счётчиками раундов и закреплёнными моделями.

TranscriptReader различает виды записей: turn (turn_context с режимом), message (роль, phase, склеенный текст), tool, reasoning, unsupported-activity, other. Режим сообщения берётся из последнего предшествующего turn_context; хук не смотрит на permission_mode, который описывает поведение одобрений, а не режим совместной работы.

8. Workflow Cursor: chat-first и PendingRun v2

У Cursor нет хука, поэтому предодобрение живёт в отдельном версионированном файле вне репозитория: <plugin-data>/cursor-runs/<scopeId>/<sha256(runId)>.json. Корень — $FORGE_PLUGIN_DATA, иначе $CURSOR_HOME/plugin-data/plan-forge-flow, иначе ~/.cursor/plugin-data/plan-forge-flow. До успешной материализации в репозитории не появляется ничего: ни .forge/, ни рефов, ни managed-блока exclude.

Порядок 0.5.1 — chat-first. Ревью идёт по тексту в чате; нативный <name>.plan.md создаётся последним действием Plan-хода, уже после plan finalize. Схема PendingRun — версия 2: у неё есть поле draftText, которое живёт только в фазах reviewing, revision-required и review-approved и обнуляется при finalize и abandon (инвариант проверяется при каждой загрузке).

plan stage --host cursor --run-id <id> + waiver ревьюера stdin: чат-план Cursor

Вход
полный текст плана из чата на stdin. Файл, путь и --source больше не участвуют.

Идемпотентность
повторный вызов с тем же текстом в активной фазе возвращает существующий run; другой текст в активной фазе (кроме revision-required) — ошибка «finalize or abandon the existing run first».
Перестейдж
из revision-required текст заменяется, run возвращается в reviewing, активный dispatch сбрасывается. На капе (по умолчанию 5) нужны --accept-risk и --authorization-note: кап растёт ровно на 1 и попадает в capAudits. Вне капа эти флаги, наоборот, запрещены.

review record-response --host cursor --dispatch-id --stage plan|code|fix-review [--run-id] stdin

Смысл
единственный способ занести вердикт Cursor-ревьюера: полный текст ответа идёт на stdin, CLI сам владеет уликами и решением. Оркестратор не переписывает терминальные строки.
Стадия plan
работает по PendingRun (без .forge/). Без --run-id прогон определяется через ResolvePlanDispatch: должен существовать ровно один run в фазе reviewing, у которого нет активного dispatch либо он совпадает с переданным. Ответ канонизируется, ≤ 256 КБ; требуется ровно одна строка VERDICT: APPROVED|REVISE, и она обязана быть последней непустой; строка COVERAGE: запрещена. Dispatch-id обязан быть свежим для этого run, а reviewRound — меньше капа. Накопленный review-лог проверяется детектором секретов. APPROVED → review-approved, REVISE → revision-required.
Стадии code/fix-review
работают уже по материализованному состоянию: ответ ≤ 512 КБ, ровно одна VERDICT: (терминальная) и ровно одна COVERAGE: FULL|PARTIAL. Прогон резолвится не по --run-id, а из state.sourceRun.source = "cursor:<runId>"; сверяются pending-dispatch, стадия и transactionId, run обязан быть consumed. Затем пишутся .forge/cursor-review-<dispatch-id>.md и sidecar .json — тот же формат решения, что и у Codex.

plan finalize --host cursor --run-id + waiver билдера

Требует
фазу review-approved, waiver роли builder и сохранённый draftText.
Проверяет
CanonicalText.ParseTasks(draft) — ровно одна секция ## Approach с задачами 1..N; обе пары модель/эффорт; отсутствие секретов в черновике и в накопленном review-логе.
Результат
фаза ready, draftText обнуляется, сохраняются оба waiver'а и все ответы ревьюера. Только после успешного ready skill разрешает создать нативный план — и это терминальное действие хода.

plan invalidate --run-id --reason · plan abandon --run-id

invalidate
переводит run в revision-required с причиной ≤ 512 символов и сбрасывает активный dispatch. Недоступен в ready, materializing, consumed, abandoned.
abandon
терминально закрывает run и стирает черновик. Недоступен в materializing и consumed — начатую транзакцию нельзя «отменить», её нужно доиграть.

Контракт нативного плана

Файл создаётся оркестратором после ready и должен содержать ровно один маркер и идущую непосредственно за ним видимую преамбулу:

<!-- plan-forge-flow:run=<run-id>;workspace=<scope-id> -->
> **Plan Forge execution gate (advisory):** Before any repository write, run Plan Forge
> `plan materialize --host cursor --workspace "<workspace>" --run-id "<run-id>"` using the
> installed launcher. Stop if it does not succeed. Cursor can bypass this instruction;
> approval enforcement is advisory.

Текст преамбулы генерируется методом PendingRuns.ExpectedPreamble и сверяется побайтово (это одна строка; выше она разбита только для чтения). Дальше идут заголовок, ## Approach с задачами 1..N, верификация и исключения из скоупа.

DiscoverNativePlan вызывается один раз — в BeginMaterialize:

  • корень поиска — $CURSOR_HOME/plans, по умолчанию ~/.cursor/plans; в Debug-сборке дополнительно сканируется корень workspace;
  • перебираются только файлы *.plan.md верхнего уровня; каталог проверяется на симлинки, файл — на регулярность;
  • отбираются те, что содержат <!-- plan-forge-flow:run=<id>;. Совпадений обязано быть ровно одно: ноль — «no Cursor native plan matches», два и больше — «multiple Cursor native plans match»;
  • файл больше 256 КБ читается префиксом и, если маркер найден, отклоняется как oversized;
  • в канонизированном тексте проверяются: ровно один префикс plan-forge-flow:run=, ровно один полный маркер run=<id>;workspace=<scope>, ровно одна преамбула и ровно одно вхождение пары «маркер + перевод строки + преамбула»;
  • текст прогоняется через детектор секретов и ParseTasks;
  • результат целиком (вместе с frontmatter Cursor) становится transaction.PlanText и после переезда — .forge/PLAN.md.

После открытия транзакции нативный файл больше не нужен: повтор plan materialize играет по снимку, даже если файл отредактировали или удалили. run cleanup его никогда не трогает.

/forge resume

Только восстановление — обычный ход его не использует. По run status находится единственный подходящий run, и дальше по фазе: reviewing — показать черновик и позвать свежего ревьюера; revision-required — обновить, перестейджить, снова ревью; review-approved — waiver билдера, finalize, создать нативный план; ready — если файл уже есть, это успешный no-op, а если создание прервалось и черновик уже стёрт, восстановить его нельзя: run нужно бросить и начать заново; materializing — повторить plan materialize; consumed — уже материализовано; abandoned — нужен новый run.

9. Материализация и подготовка сборки

Codex: прямая запись

plan materialize [--amendment] stdin JSON пишет .forge/ git

Когда
первая команда первого Default-хода; читает pending-план, застейдженный хуком.
Вход
stdin ≤ 2 МБ, DTO MaterializationRequest с ключами reviewLog (одна непустая строка со всеми раундами, не массив и не объект), completedReviewRounds, maxRounds, reviewer, builder (каждая роль — {model, effort}). Лишнее поле или неверный тип дают ошибку usage с описанием ожидаемой формы. Сам план приходит не из stdin, а из pending-артефакта.
Проверки входа
план и review-лог канонизируются и прогоняются через SensitiveInput.IsSensitiveContent; пара модель/эффорт валидируется для обеих ролей; если состояние уже существует, сверяются host и repositoryScopeId.
Свежий прогон
ResetRun: рекурсивно удаляет .forge/, снимает managed-блок из .git/info/exclude, удаляет три scoped-рефа. Затем создаётся пустое состояние в фазе materialized.
Поправка
с --amendment: загружает состояние, требует фазу build или code-review, сверяет, что уже выполненные задачи совпадают по хешу с новым планом, затем сбрасывает dispatch, builderId и review (историю критик сохраняет).
Пишет
.forge/PLAN.md, .forge/PLAN-REVIEW-LOG.md, .forge/state.json с закреплёнными моделями и счётчиками раундов, managed-блок в info/exclude. Затем удаляет pending-план.

Cursor: двухфазная транзакция

plan materialize --host cursor --run-id — это единственный шаг Cursor, который пишет в репозиторий, и он же выполняет за один вызов discovery + materialize + lock + begin. Из-за этого он устроен как восстановимая транзакция.

Общие шаги после материализации

plan lock [--relock --amendment] git

Делает
читает .forge/PLAN.md; CanonicalText.ParseTasks требует ровно одну секцию ## Approach (до следующего заголовка уровня 2) и парсит нумерованный список — номера обязаны идти строго 1..N по порядку; текст каждой задачи хешируется. Фиксирует git-базлайн: rev-parse HEAD и список untracked-файлов с хешами. Фаза → locked.
Relock
с --relock --amendment разрешён из build и code-review; запрещает изменять или удалять завершённые задачи; базлайны не перезаписывает.

build begin [--amendment|--relock] git

Делает
пинит три scoped-рефа: owner и head-base (текущий HEAD) и worktree-base. Если дерево грязное по отслеживаемым файлам, делает git stash create и указывает worktree-баз на этот объект — так правки пользователя отделяются от правок прогона. Фаза → build.
Защита
если все три рефа существуют и это не amendment/relock — отказ: в репозитории следы предыдущего прогона. Для Cursor частично записанные рефы — это признак прерванной транзакции: тогда owner обязан совпадать с baselines.head, иначе отказ.

10. Сборка: dispatch-цикл

build dispatch --stage code|build|fix-build|fix-review [--task-number N] [--retry|--cancel] [--dispatch-id]

Проверки
стадия парсится в DispatchStage; текущая фаза сверяется с definition.ExpectedPhase; нет уже висящего dispatch; для fix-стадий review.fixRound должен быть строго меньше maxFixRounds; для build — существуют оба baseline-рефа этого scope, --task-number равен nextTaskNumber и не выходит за taskCount; если definition.RequiresFreshReview — свежий манифест улик.
Выбор роли и модели
state.Models.For(definition.Role). Модель и эффорт берутся из состояния; если переданы --model/--effort, они обязаны совпасть.
Ветки
--cancel снимает pending; --retry увеличивает счётчик (за капом maxBuildRetries требует --accept-risk и --authorization-note). Обе требуют совпадения --dispatch-id, если он передан. Для Cursor --retry дополнительно генерирует новый dispatch.id и обнуляет зарегистрированную сессию соответствующей роли — потому что повторная попытка обязана достаться свежему агенту.
Результат
dispatch.id = "dispatch-" + nonce[..16], pending = true, стадия, модель и эффорт записаны в состояние.

session builder | session reviewer --id --dispatch-id --model --effort

Смысл
привязать реальную сессию нативного сабагента к выданному dispatch. Без этого ни build complete, ни review verdict не пройдут.
Проверки
dispatch pending и --dispatch-id совпадает; stage.Definition().Role == role; --model/--effort обязательны и должны точно совпадать с закреплёнными в dispatch; reviewer-id нельзя переиспользовать (каждый раунд — свежий агент).
Билдер по хостам
Codex: билдер постоянный, смена уже зарегистрированного id требует --authorization-note. Cursor: id проверяется по накопленному списку agents.builderIds и повтор запрещён вовсе.

build complete --task-number N [--dispatch-id] [--verification-passed false]

Делает
закрывает dispatch стадии build или fix-build. Для build увеличивает nextTaskNumber и, когда задачи кончились, переводит фазу в code-review.
Провал верификации
--verification-passed false требует --accept-risk и --authorization-note, иначе ошибка кода 2.

build resolve --conflict <текст>

Делает
аварийный выход: снимает pending с build-dispatch и записывает произвольную строку в dispatch.conflict.

11. Код-ревью и фиксы

review prepare [--full] [--allow-paths JSON] [--authorization-note] пишет .forge/ git

Когда
в фазе code-review, перед каждым ревью-dispatch (включая fix-review).
Три класса изменений
  • pre-existing: git diff head-base worktree-base — то, что было в дереве до прогона;
  • in-run: git diff worktree-base — то, что сделал билдер;
  • untracked: текущий ls-files --others --exclude-standard против зафиксированного базлайна, сравнение по хешам.
Все списки путей проходят через ReviewEvidence.PathList, который нормализует разделители, отбрасывает дубликаты и валидирует путь (без traversal, без NUL, ≤ 4096).
Решение по файлу
ReviewEvidence.Inspect возвращает (Reason?, Bytes). Причины удержания: pre-existing без авторизации, недоступная untracked-улика, превышение размера (100 КБ на файл, 1 МБ суммарно), бинарник без явного разрешения. Чувствительный путь или содержимое без разрешения — не удержание, а ошибка кода 2.
Покрытие
--full с непустым списком удержанных путей — ошибка кода 2 со списком в details. Иначе coverage = FULL при --full или при пустом наборе изменений, иначе PARTIAL.
Пишет
.forge/pre-existing.patch, in-run.patch, untracked-review.patch (свой tsv-формат: путь, вид, хеш, base64), changed-files.txt и review-manifest.json — манифест version 4 с SHA-256 каждого из четырёх файлов улик и treeFingerprint.
Anti-TOCTOU
treeFingerprint считает HEAD, ls-files --stage, diff --raw --cached и diff --raw против head-base, плюс хеш каждого затронутого пути. Он вычисляется до и после генерации улик и ещё раз внутри транзакции записи состояния; при расхождении — отказ с просьбой повторить. Тот же fingerprint и хеши файлов перепроверяются в RequireFreshReviewManifest при каждом dispatch и вердикте, а сам манифест на диске побайтово сверяется с копией в состоянии.

review authorize-preexisting --authorized-paths '["a","b"]' --authorization-note '…'

Делает
добавляет пути в review.authorizedPaths (не более 256), после чего review prepare перестаёт их удерживать. Требует note с явным согласием пользователя. Массив разбирается общим бандед-парсером ParsedArgs.ParsePathArray: ≤ 256 КБ JSON, только относительные пути ≤ 4096 символов, без .. и NUL.

review verdict --stage code|fix-review --critique-file .forge/<file> [--accept-risk --authorization-note]

Решение
читается из sidecar-файла <critique-file>.json (≤ 16 КБ, внутри .forge, не симлинк): 
{"verdict":"APPROVED","coverage":"FULL"}
{"verdict":"REVISE","coverage":"PARTIAL"}
Для стадии plan поле coverage должно отсутствовать; для code и fix-review — обязательно. Текст критики на вердикт не парсится. В Cursor и критику, и sidecar пишет сам CLI из ответа ревьюера.
Проверки
DispatchStages.RequirePendingReviewVerdict сверяет, что висит ревью-dispatch и запрошенная стадия ему соответствует; нужен зарегистрированный свежий ревьюер именно на этот dispatch; свежий манифест, если стадия его требует; фаза locked для plan и code-review для остальных; критика внутри .forge, ≤ 100 КБ, не симлинк, без чувствительного содержимого; для APPROVED требуется coverage == FULL и manifest.Coverage == FULL.
Капы
REVISE за капом: для plan — нужен --accept-risk с note, для fix-стадий — расширение через run set --key max-fix-rounds.
Пишет
review.verdict/coverage/critiqueFile/verdictFile/verdictHash, запись {path, hash} в историю critiqueFiles (до 256), счётчик раундов; фаза → done при одобрении на code/fix-review. Внутри транзакции хеши критики и sidecar-решения сверяются повторно.

Анатомия fix-раунда

Один fix-раунд — два явных dispatch:

#КомандыСтадияРоль
1build dispatch --stage fix-buildfix-buildbuilder
2session builder → build completefix-buildbuilder
3review prepare → build dispatch --stage fix-reviewfix-reviewreviewer
4session reviewer → review verdict --stage fix-review (Cursor: сначала review record-response)fix-reviewreviewer

Билдер обязан закрыть свой dispatch до того, как ревьюер сможет зарегистрироваться: роль каждой стадии задана таблицей, а build complete принимает только стадии с CompletedByBuilder.

Делает

  • max-rounds / max-fix-rounds — ровно +1, только после того как текущий кап достигнут и последний вердикт был REVISE, с --accept-risk и note.

Делает
под repository- и workspace-локом проверяет, что существующий .forge/ принадлежит этому хосту и scope, затем рекурсивно удаляет его, снимает три scoped-рефа и managed-блок из .git/info/exclude. Инварианты, которые защищает CLI

  1. Автомат: фаза, стадия, роль и «кто закрывает dispatch» выводятся из одной таблицы.
  2. Версия и хост: schemaVersion и host проверяются до десериализации и до любой мутации; чужой хост, чужой scope или иная схема — отказ.
  3. Привязка к репозиторию: scope id входит в состояние, в имена рефов и в путь PendingRun; перенос каталога или чужой worktree отклоняется.
  4. Строгость своих файлов: любое неизвестное поле в Forge-owned JSON роняет чтение; контракт ответа каждой команды задан в коде типом и проверяется компилятором.
  5. Мягкость чужих: новое поле в payload'е Codex не ломает захват плана.
  6. Порядок сборки: --task-number обязан равняться nextTaskNumber; задачи нельзя пропускать и переставлять.
  7. Пиннинг моделей: модель и эффорт берутся из состояния, аргументы только подтверждают; ultra запрещён на всех путях.
  8. Свежесть агентов: reviewer-id нельзя переиспользовать никогда; Cursor-билдер тоже одноразовый, Codex-билдер постоянный и его смена требует note.
  9. Связь dispatch и сессии: закрыть dispatch может только тот, кто зарегистрировал сессию под этот же dispatch-id.
  10. Свежесть улик: treeFingerprint и хеши четырёх файлов проверяются при каждом использовании манифеста; сам манифест сверяется с копией в состоянии побайтово.
  11. Разделение чужих правок: два git-базлайна и stash-объект отделяют pre-existing от in-run.
  12. Одноразовость прогона (Cursor): один активный run на scope, свежий dispatch-id на каждый раунд ревью, ровно один нативный план по маркеру, run doctor отказывается стартовать поверх существующего .forge.
  13. Атомарность снимка (Cursor): текст нативного плана фиксируется в транзакции и перепроверяется по хешу при каждом replay и при финальной верификации.
  14. Утечки: детектор секретов на плане, review-логе, ответах ревьюера, путях и содержимом улик, патчах и файле критики.
  15. Капы: 5 раундов плана, 3 fix-раунда, 3 ретрая билда; расширение только на +1 и только с --accept-risk и непустым --authorization-note (≤ 16 КБ).
  16. Отказ от симлинков: проверки ReparsePoint и LinkTarget на всех путях записи и чтения, включая всех родителей.
  17. Атомарность: temp + fsync + rename, два уровня локов вне репозитория, оптимистическая проверка снимка состояния, журнал ожидаемого следующего состояния для Cursor.

15. Наблюдения и риски

Дефектов, ломающих основной сценарий, при этом проходе не найдено. Ниже — места, где поведение зависит от внешней дисциплины, где остаётся мусор, или где в релизном бинаре живёт тестовая оснастка.
Главное расхождение: у Cursor ревьюится не то, что исполняется. Ревью работает по чат-черновику, сборка — по нативному файлу, а связывает их только маркер прогона. После plan finalize черновик стирается, поэтому даже сопоставить два текста постфактум нечем. Это осознанное решение (оно записано и в skill, и в README), но у него есть цена:
  • PLAN-REVIEW-LOG.md описывает один текст, а PLAN.md и tasks[] получены из другого — журнал ревью перестаёт быть свидетельством о реализуемом плане;
  • «одобрение» проверяет форму (маркер, преамбула, ## Approach), а не содержание, поэтому approvalGuarantee=advisory теперь честен вдвойне;
  • дешёвая середина существует: хранить в PendingRun хеши задач одобренного черновика и при материализации сравнивать с задачами нативного плана — расхождение показывать пользователю (или требовать --accept-risk), не блокируя правки.
  • Discovery по маркеру хрупок. DiscoverNativePlan требует ровно одно совпадение среди *.plan.md верхнего уровня $CURSOR_HOME/plans. Любая копия или бэкап с тем же маркером (plan (1).plan.md, синхронизация папки) превращает материализацию в «multiple Cursor native plans match» без указания путей; вложенные подкаталоги не просматриваются вовсе. Диагностику стоит усилить хотя бы списком найденных файлов в details.
  • plan stage не проверяет ## Approach. Черновик без корректной нумерации проходит все раунды ревью и падает только на plan finalize. Вызов CanonicalText.ParseTasks прямо в Stage — одна строка, которая переносит отказ на несколько минут раньше.
  • Осиротевший staging-каталог Cursor. Материализация собирает .forge/ в .forge.materializing-<tx>/ и переезжает одним Directory.Move. Если процесс умрёт до переезда, каталог останется в корне репозитория: managed-блок info/exclude перечисляет только .forge/, поэтому мусор виден в git status, а run cleanup его не удаляет (DeleteForgeDirectory знает лишь про .forge). Повторная материализация того же run его подберёт и сверит, но после abandon-подобного отказа чистить придётся руками.
  • Точки инъекции сбоев компилируются в релиз. PendingRuns.Fault не обёрнут в #if DEBUG: установка FORGE_FAULT_POINT в одно из 11 известных имён (snapshot-written, cursor-plan-written, locked-successor-journaled, baseline-head-written, …) заставит релизный бинарь падать в выбранной точке. Это только отказ в обслуживании и только для того, кто уже контролирует окружение процесса, но соседние тестовые хуки (FORGE_TEST_HOLD_LOCK, FORGE_TEST_HOLD_AFTER_EXCLUDE, разрешение plan-источника внутри workspace) корректно спрятаны за #if DEBUG — эта нет.
  • Режим работы по-прежнему не проверяется кодом (Codex). Требования «Act 1 только в Plan mode» и «материализовать только в первом Default-ходе» существуют лишь как правила skill. Хук выполняется на каждом промпте и не смотрит на режим хода, а plan materialize не знает, в каком режиме его позвали.
  • Обход преамбулы в Cursor молча перекрашивает изменения. Если агент проигнорирует advisory-гейт и начнёт писать в репозиторий до plan materialize, материализация пройдёт, а build begin запинит базлайны уже поверх этих правок — они станут pre-existing и потребуют отдельной авторизации вместо того, чтобы попасть в in-run-улики. Ошибка обнаружится, но как «неожиданные pre-existing файлы», а не как нарушение гейта.
  • Целостность плана между материализацией и plan lock не подтверждается для Codex: хеша материализованного плана в состоянии нет, поэтому правка .forge/PLAN.md между двумя командами пройдёт незамеченной. У Cursor этот зазор закрыт transaction.PlanHash.
  • --amendment не требует, чтобы план отличался от текущего: повторная материализация того же текста легальна и просто сбрасывает dispatch и review.
  • review prepare не берёт repository lock, хотя читает scoped-рефы и untracked-дерево. Параллельный run cleanup в другом worktree того же репозитория может удалить рефы посреди подготовки улик; итог — ошибка environment, не порча данных, но диагностика будет невнятной.
  • run doctor проверяет dotnet --version, хотя релизный бинарь self-contained; более того, build/package.ps1 требует, чтобы эта проверка прошла, привязывая упаковку к наличию SDK на машине сборки. Для пользователя без .NET doctor сообщит о проблеме, которой нет.
  • README перечисляет четыре переменные окружения и не упоминает FORGE_LOCK_DATA, хотя именно она переносит оба лока.
  • Жёсткая привязка к $CURSOR_HOME/plans. В релизной сборке discovery ищет план только там. Если Cursor изменит расположение планов или начнёт хранить их в рабочем пространстве, Build перестанет запускаться без правки кода.
  • Мёртвые члены. Hashing.Base64UrlEncode/Decode используются только собственным тестом; PendingRuns.ResolveActive не вызывается ниоткуда (его заменил ResolvePlanDispatch); agents.lastReviewerId и dispatch.conflict только записываются; state.modelWaiver валидируется, но не читается, дублирует modelWaiverAudit и не попадает в run status; TranscriptReader.Record.Type хранится, но решения принимаются по Kind; регистрация JsonSuccess<PendingRun?> в контексте не используется.

Б. Решения по существу

  • Привязать одобренный черновик к нативному плану — хотя бы наблюдаемо. Сейчас связь только по маркеру. Достаточно сохранить в PendingRun хеши задач черновика (они и так считаются в ParseTasks) и на материализации сравнить их с задачами нативного файла: совпало — тихо, разошлось — вывести дифф в details. Это не отменяет решения «правки пользователя не требуют повторного ревью», но перестаёт делать вид, что review-лог описывает собираемый план.
  • Заменить bool repositoryLockHeld на тип-токен. Флаг протянут через Materializer.Materialize, BeginBuild, Consume, JournalMaterializationSuccessor, ReconcileMaterializationState, CompleteCursorMaterialization. Передача самого RepositoryRunLock? (или scope-объекта RunScope, владеющего обоими локами) убирает шесть булевых параметров и делает невозможным вызвать вложенный метод без лока вообще.
  • Разделить Materializer.Materialize. Тринадцать параметров, из них шесть опциональных, и три разных режима (Codex fresh, Codex amendment, Cursor transactional), которые внутри метода ветвятся по materializationTransactionId is not null. Выделение общего «записать план+лог+state в каталог X» и трёх тонких вызывающих сторон уберёт большинство взаимоисключающих проверок вроде «transactional materialization is Cursor-only».
  • Убрать журнал successor-состояния, доиграв транзакцию внутри staging. Сейчас после Directory.Move ещё два шага (plan lock, build begin) мутируют state.json на месте, и именно ради них существуют successorStateHash/Phase, JournalMaterializationSuccessor, ReconcileMaterializationState и связанные ветки валидации — суммарно ~70 строк и половина сложности PendingRun. Разбор задач (plan lock) не требует записи в репозиторий и может быть выполнен в staging до переезда; тогда журналировать останется только build begin, который пишет git-рефы, — или можно пинить рефы до Move, и тогда переезд станет единственной точкой невозврата.
  • Разнести Cursor/PendingRun.cs на три файла. 383 строки и три темы в одном типе: схема + ValidateLoaded (~35 строк инвариантов), автомат фаз (stage/record/finalize/invalidate/abandon) и транзакция материализации вместе с discovery нативного плана. Третья тема ещё и пишет в .forge/cursor-review-*.md, то есть класс с именем «pending run» владеет уликами ревью — это ответственность Review/.
  • Свести run status к одной форме. Три возможных shape'а ({exists:false}, StatusPresentData, PendingRun|null) заставляют каждого потребителя угадывать. Конверт вида {state: …|null, pendingRun: …|null} убирает ветвление и из CLI, и из skill — и заодно закрывает вопрос «что показывать в resume, когда есть и то, и другое».
  • Целостность плана для Codex: хранить SHA-256 материализованного плана в состоянии и сверять в plan lock — порядка пяти строк, закрывает класс «файл поменяли между командами» и приводит Codex к тому же уровню, что уже есть у Cursor.
  • Чистить .forge.materializing-* в run cleanup и добавить шаблон в managed-блок exclude — два места, снимает единственный источник мусора в репозитории.
  • Модель доверия к pending-плану, режиму и нативным правкам: сейчас это полностью зона ответственности skill. Стоит зафиксировать решение явно в README или ADR, чтобы будущая ревизия не приняла отсутствие проверок за недосмотр.

В. Оправданная сложность

  • Улики ревью (ReviewEvidence + ForgeReview, ~500 строк): три класса изменений, четыре причины удержания, tsv-формат для untracked, тройная сверка fingerprint. Это ядро ценности акта 4; дальнейшее сжатие требует отказаться либо от untracked-улик, либо от разделения pre-existing / in-run.
  • ValidateLoaded для PendingRun (~35 строк): внешний файл вне репозитория, который решает, можно ли писать в репозиторий, обязан валидироваться целиком, включая пересчёт хешей ответов, привязку draftText к фазе и вывод reviewCap из цепочки аудита. Дублирование инвариантов писателя здесь — фича, а не долг.
  • Два JSON-контекста — именно они дают «свои файлы fail-closed, чужие fail-open», а явная передача JsonTypeInfo переносит проверку контракта в компиляцию.
  • Scope id и два уровня локов — цена поддержки linked worktrees; без них два worktree одного репозитория дрались бы за рефы и info/exclude.
  • Детектор секретов (34 строки) — дёшево и полезно.
  • ProcessExecution (129 строк) — избыточен для двух вызываемых программ, но безвреден; станет ближе к оправданному, если убрать проверку dotnet и оставить только git.
