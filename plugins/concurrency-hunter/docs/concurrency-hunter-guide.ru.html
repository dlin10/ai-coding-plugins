Путеводитель по Concurrency Hunter

Статический анализатор гонок и потерянных обновлений в .NET-коде. Этот документ объясняет, какие ошибки он ищет, как устроен его алгоритм, как он ведёт себя в трудных случаях и где что лежит в коде — для того, кто будет его поддерживать и дописывать.

C# · .NET 8–10 сервер Windows x64 MCP-сервер + skill хоста ~26 тыс. строк движка 1 813 тестов в baseline 244 ожидания demo текущая фаза 5b
Оглавление

  2. Общий алгоритм — процедура, конвейер, стадии
  3. Частные случаи — примеры C# и вердикты
  4. Сопровождение — код, тесты, правила, состояние

Документ идёт от общего к частному. Часть I — какую проблему решает плагин и из чего он состоит. Часть II — общий алгоритм: одна решающая процедура и конвейер, который применяет её, не перебирая все пары. Часть III — частные случаи на коде из demo/: где интуиция подводит и что анализатор отвечает. Часть IV — практическое: карта кода, тесты и гейты, правила, которые нельзя нарушать, и что ещё предстоит сделать.

Предполагается, что вы знаете, что такое гонка данных, lock и async/await, но ничего не знаете об устройстве плагина. Источники истины — PRD, SPEC, CONTEXT.md и ADR; руководство их не заменяет, а связывает с кодом.

Часть I Общая картина

Какую проблему решает плагин

В .NET-бэкенде один и тот же объект в памяти одновременно меняют HTTP-запросы, hosted services, задачи из Task.Run, callbacks таймеров и итерации Parallel.For. Каждый путь по отдельности выглядит правильно. Дефект появляется только при определённом чередовании чтений и записей двух путей, и воспроизвести его руками почти невозможно.

Самый короткий пример — счётчик в singleton-сервисе:

demo: rmw-singleton-counterDCA1002 · High
public sealed class HitStats
{
    public int Hits { get; set; }
}

[ApiController]
[Route("cases/rmw-singleton-counter")]
public sealed class HitsController : ControllerBase
{
    private readonly HitStats _stats;
    public HitsController(HitStats stats) => _stats = stats;

    [HttpPost]
    public void Post() => _stats.Hits++;   // чтение, +1, запись
}

// Program.cs
services.AddSingleton<HitStats>();         // один объект на весь процесс

Code review такие дефекты пропускает по трём причинам, и каждая из них определяет, что должен уметь анализатор.

  1. Какой объект на самом деле общий. Замените в примере выше AddSingleton на AddScoped — и гонки нет: у каждого запроса свой экземпляр (demo di-scoped-per-request). Код в контроллере не изменился, изменилась регистрация в другом файле. Совпадение имени поля или типа ничего не доказывает: нужен настоящий анализ того, куда указывают ссылки.
  2. Какие исполнения на самом деле пересекаются во времени. Два HTTP-запроса — да. Один BackgroundService.ExecuteAsync сам с собой — нет. Задача из Task.Run с родителем — только до await её handle. Периодический таймер — сам с собой тоже да.
  3. Достаточна ли защита. lock на разных объектах не защищает. volatile не делает x++ атомарным. SemaphoreSlim — мьютекс, только если его ёмкость доказанно равна 1. Класс с методами Lock()/Unlock() — не доказательство, пока внутри нет настоящего примитива.

Кроме того, гонка часто пересекает несколько слоёв: запрос приходит в контроллер проекта Web, вызывает сервис из Application, а поле, которое теряет обновление, лежит в Domain (demo rmw-three-layers). Плагин связывает эти слои сам и показывает оба пути от точки старта исполнения до доступа.

Определение, на котором стоит весь плагин

Два доступа образуют гонку, когда они обращаются к одному месту в памяти одного процесса, выполняются в исполнениях, которые могут пересечься во времени, хотя бы один из них пишет, между ними нет доказанного порядка и нет общей достаточной защиты. Все остальные главы объясняют, как проверить каждое из этих условий статически, не запуская приложение.

Что плагин делает и чего не делает

Пользователь вызывает одну команду /concurrency-hunter [target] в Claude Code, Codex или Cursor. Target — .sln, .slnx, .csproj или каталог. Плагин загружает solution через Roslyn и MSBuild, анализирует его статически, ничего не запуская и не меняя, и оставляет report bundle из трёх файлов: report.md, findings.json и run-metadata.json.

Как устроен запуск: skill и server

Плагин состоит из двух частей, которые разговаривают по протоколу MCP. Разделение продиктовано тем, что умеют хосты: у Claude Code, Codex и Cursor команда плагина — это skill (инструкция для агента хоста), а единственный программный интерфейс — stdio MCP-сервер. Сервер не может сам запустить AI или отменить субагента (ADR 0001).

  • Skill (skills/hunt/SKILL.md) — единственный оркестратор. Он запускает анализ, опрашивает сервер, раздаёт субагентам хоста группы находок для текстового объяснения и просит сервер отрендерить отчёт.
  • Server (ConcurrencyHunter.Cli, один процесс на run) — детерминированный анализатор и конечный автомат. Он хранит состояние run и дедлайн, проверяет всё, что приносит AI, и сам пишет отчёт.

Почему отчёт пишет сервер, а не AI

Аудит legacy-кода даёт сотни находок. Если отдавать модели всю цепочку доказательств и просить переписать её в отчёт, токены тратятся на текст, который не требует интеллекта, а дедлайн в 30 минут за это платит. Поэтому сервер детерминированно рендерит skeleton: пути, доказательства, анализ защиты, сценарий чередования, fingerprint. AI добавляет только narrative группы — объяснение словами и варианты исправления с пометкой verify manually. Каждый фрагмент проходит NarrativeValidator: все процитированные evidence id существуют, все упомянутые файлы и символы есть в доказательствах группы. Неверный фрагмент отклоняется с причиной, разрешён один повтор (ADR 0003).

Отменить уже запущенного субагента сервер не может, и это честно записано в спецификации; гарантия в другом — опоздавший ответ никогда не меняет находки.

Минимальный словарь

Словарь плагина живёт в CONTEXT.md, и код, схемы инструментов и отчёт используют эти слова строго в одном смысле. Некоторые обычные слова там намеренно запрещены: не «поток», а execution instance; не «переменная», а resource. Английские термины в тексте ниже оставлены как есть, потому что именно их вы встретите в коде. Полный словарь — в конце документа.

Execution root
Точка, откуда фреймворк или рантайм начинает независимое исполнение: HTTP action, ExecuteAsync hosted service, callback таймера, gRPC-метод.
Spawn site
Вызов в пользовательском коде, который начинает новое исполнение из текущего: Task.Run, Thread.Start, тело Parallel.For, fire-and-forget.
Execution instance
Одно логическое исполнение root-а или spawn-а. Не поток ОС: await внутри его не заканчивает.
Heap region
Идентичность объекта или множества объектов: место аллокации с контекстом, статическое поле, DI-экземпляр, параметр.
Resource
Region плюс access path (поле за полем, с селектором ячейки). Единица, по которой сравниваются доступы.
Ownership
Кто может достать region: Owned, ThreadConfined, Escaped, Shared, Unknown — всегда с цепочкой доказательств.
Access
Одно чтение, запись, RMW, атомарная или составная операция над ресурсом — вместе с исполнением, удерживаемой защитой и guard-ом.
Happens-before
Доказанный порядок двух событий: путь через spawn, join, продолжения и старт хоста. Только удаляет пары, никогда не добавляет.
Protection
Синхронизатор (его region) и режим, который доступ удерживает на всех путях к нему. «Может быть удержан» — не защита.
Candidate → Finding
Пара доступов, прошедшая дешёвые фильтры, — кандидат. Кандидат, переживший уточнение, становится находкой с одним правилом DCA100x.
Occurrence
Один способ достичь пары мест доступа: пара roots с путями вызовов. У находки их может быть много.
Semantic gap
Вызов, который детерминированный анализ не смог разобрать и который трогает общее изменяемое состояние. Честно показывается в отчёте как неопределённость.
Часть II Общий алгоритм

Решающая процедура

Всё, что делает анализатор, сводится к одной процедуре над парой доступов A и B. Четыре правила DCA — это не четыре анализа, а четыре способа назвать её результат (SPEC §7):

Conflict(A, B) =
       SameProcessScope(A, B)                        // один процесс
    && MayResourcesOverlap(A.Resource, B.Resource)   // одно место в памяти
    && MayExecutionOverlap(A.Interval, B.Interval)   // могут идти одновременно
    && OperationsConflict(A.Operation, B.Operation)  // хотя бы одна неатомарная запись
    && !OrderedByHappensBefore(A, B)                 // нет доказанного порядка
    && !ProtectedByCommonSufficientPrimitive(A, B)   // нет общей достаточной защиты
    && PathPairIsNotUnsatisfiable(A.Guard, B.Guard)  // условия путей совместимы

LostUpdate(A, B) =
       Conflict(A, B)
    && (A или B — неатомарный RMW или составная операция)
    && устаревшее чтение может повлиять на последующую запись

Каждая проверка возвращает не просто да/нет, а True, False или Unknown вместе с доказательствами. Отсюда главный принцип плагина:

Неизвестное — не безопасное

Пару удаляет только доказанное False: доказанно разные ресурсы, доказанная изоляция, доказанный порядок, доказанная защита, UNSAT от решателя. Unknown пару оставляет и снижает уверенность. Ошибки несимметричны: лишняя находка стоит читателю минуту, ложное доказательство безопасности молча прячет настоящую гонку. Когда сомневаетесь при доработке — выбирайте сторону, которая оставляет пару.

Классификация правила

Правило выбирается после того, как пара пережила все фильтры, по видам двух операций и результату защиты (ConflictFindings.OperationRule и Classify):

// ConflictFindings.cs
if (!LosesUpdate(a.Op, b.Op) && !LosesUpdate(b.Op, a.Op))
    return CONFLICT_RULE;                                   // DCA1001
return IsIndivisible(a.Op) && IsIndivisible(b.Op)
    ? COMPOUND_RULE                                         // DCA1004
    : LOST_UPDATE_RULE;                                     // DCA1002

// LosesUpdate(stale, other): stale — RMW или Compound, а other меняет ячейку
// IsIndivisible(op):         Compound или любой Atomic*
// Classify: DCA1001 с защитой partial / different-identity / incompatible-mode → DCA1003

Несколько следствий, которые полезно помнить: RMW против простого чтения — DCA1001 (читатель ничего не теряет); RMW против UnknownEffect — DCA1002; составная операция против составной или атомарного RMW — DCA1004. DCA1002 и DCA1004 сохраняют своё правило при любой защите, в DCA1003 переходит только DCA1001.

Конвейер анализа

Процедура выше применяется не к «всем парам всех доступов» — их слишком много. Анализ устроен как конвейер, где дешёвые шаги идут раньше дорогих, а дорогая точность оплачивается только для пар, у которых уже есть общий ресурс, конфликтующие операции и возможное пересечение. Несколько свойств конвейера, о которых стоит знать заранее:

  • Ленивое опускание в IR. ReachableSet строит граф вызовов по иерархии классов и опускает в IR тело метода в момент, когда впервые до него доходит. Тело вне reachable set не анализируется и не считается против coverage. Ошибка опускания одного тела превращается в диагностику lowering: и пустое тело, а не в падение run.
  • Слой Analysis не знает Roslyn. Всё после IR (куча, исполнения, пары, находки, отчёт) живёт в проекте ConcurrencyHunter.Analysis, у которого нет ни одной ссылки на пакеты или проекты. Это проверяют тесты AnalysisBoundaryTests. Roslyn, Z3 и провайдеры — в ConcurrencyHunter.Core.
  • Никакого декартова произведения. Пары перебираются только внутри buckets. На demo это 1 328 сравнений вместо 363 379 возможных пар.
  • Детерминизм. Порядок обхода, нумерация значений, порядок вопросов к решателю — стабильны. Demo-гейт трижды анализирует demo и требует побайтно одинаковый findings.json.

Сквозной пример: одна находка от начала до конца

Прежде чем разбирать стадии по отдельности, проследим один кейс — rmw-three-layers, где гонка живёт на два проекта ниже точки входа.

// Demo.Web
[HttpPost] public void Post(int quantity) => _orders.Place(quantity);          // OrdersController

// Demo.Application
public void Place(int quantity) => _inventory.Reserve(quantity);             // OrderService

// Demo.Domain
public void Reserve(int quantity) => _reserved += quantity;                  // Inventory

// Program.cs
services.AddSingleton<Inventory>().AddSingleton<OrderService>();
  1. Process scope. Demo.Web — исполняемый проект; Demo.Application и Demo.Domain входят в его scope, потому что он на них ссылается.
  2. Roots и DI. AspNetCoreRootProvider находит action OrdersController.Post(int) с политикой Repeated / MayOverlap: запросы могут идти одновременно, в том числе к одному action. DiIndexBuilder видит две singleton-регистрации.
  3. IR. _reserved += quantity опускается в три операции: load-field, compute Add и store-field … rmw=operation:0. Поле ReadModifyWriteOf у записи — это и есть будущий DCA1002.
  4. Куча. Receiver-ы получают регионы di:OrderService@Singleton и di:Inventory@Singleton. Конструктор OrderService сохраняет параметр в _inventory, поэтому поле указывает на регион Inventory. Вызов _inventory.Reserve разрешается в конкретное тело с контекстом «receiver = этот регион».
  5. Исполнения и ownership. Execution instance — сам action. Singleton в контейнере — регион с ownership Shared.
  6. Доступ. ExecutionCollector проходит путь Post → Place → Reserve и выдаёт один доступ: ReadModifyWrite над ресурсом (di:Inventory@Singleton, [_reserved]), замков нет, guard-ов нет, путь вызовов записан.
  7. Пара. В bucket этого ресурса одно место доступа, и оно образует self-pair: root пересекается сам с собой. Порядка нет, регион не изолирован, защита unprotected. Решателю задавать нечего — guard-ов и индексов нет.
  8. Находка. RMW против RMW — LosesUpdate, операции не атомарны: DCA1002. Оценка: 25 (ресурс) + 20 (пересечение) + 20 (операция) + 20 (без защиты) + 5 (решатель не спрашивался) = 90, метка High. Одна occurrence: пара roots Post × Post.

Как опускаются важные для конкурентности конструкции:

  • x++, x += y, ??= над полем или auto-property: load → compute → store с ReadModifyWriteOf. Над volatile-полем операции дополнительно помечаются atomic.
  • Свойства. Автоматическое свойство (невиртуальное, из исходников) читается и пишется как поле-backing field. Остальные — вызовы getter/setter.

  • Примитивы Monitor, Lock, Mutex, SemaphoreSlim, ReaderWriterLockSlim распознаёт класс Synchronization. Любая перегрузка с таймаутом — условный захват: замок держится только на ветке, где флаг успеха истинен. WaitAsync ничего не держит, пока его результат не выжидают.
  • Interlocked и Volatile над полем или элементом становятся обычным load/store плюс пометка atomic.
  • async и итераторы опускаются по исходному CFG, без state machine компилятора: await — операция await, yield return — операция yield.
  • Лямбды и локальные функции — отдельные тела. Захваченные переменные приходят во вложенное тело как входящие SSA-переменные с общим SymbolKey.
  • Вызовы BCL (Task.Run, Thread.Start, Parallel.*, Timer…) получают после call дополнительные операции spawn, join, when-all, timer (AnnotateBclCall). Распознавание — по имени метаданных, поэтому пользовательский тип с именем BCL-типа не распознаётся никогда.
  • Коллекции, таблица библиотек, DI-locator — аннотации на call: Collection, Library, ServiceCall.

Summaries и fixpoint

MethodSummaryBuilder строит для каждого тела summary без контекста: доступы с удерживаемыми замками и guard-ами, записи, возвраты, вызовы, делегаты, spawns и joins, зависимости «эта запись вычислена из этого чтения». SummaryCache строит их лениво. Затем WholeProgram.Solve решает всё вместе — граф вызовов, points-to, разрешение DI, фабрики, type initializers, handles задач и таймеров:

Run():
    Seed()                      // startup-члены + по экземпляру на каждый root; receiver-ы и параметры связаны
    do Propagate() while DefaultEmptyRegistrations()

Propagate():
    loop:
        before = _changes
        for instance in порядок создания:
            Process(instance)   // ячейки, записи, возвраты, делегаты, статики → type init,
                                // Call / Locate / Spawn / TimerCallback / Handoff / WhenAll / Unwrap
            if instance что-то изменил: CountRound(instance)
        ConstructFactory(каждая регистрация)
        if _changes == before: break      // множества только растут → конечность

Две защиты от взрыва. Когда у тела набирается 16 контекстов, все дальнейшие вызовы этого тела связываются с одним экземпляром @merged. Когда экземпляр меняет что-то в 16 проходах подряд, вычисляется его сильно связная компонента в графе экземпляров, и если она циклическая, все её тела сливаются (счётчик scc-budget-exceeded). Слияние консервативно: эффекты объединяются, регион помечается как merged.

Ownership

Ownership вычисляется уже после fixpoint, в ExecutionModel, потому что для него нужно знать исполнения. Первое подходящее правило решает:

  1. регион со слитым контекстом → Unknown;
  2. статик → Shared;
  3. DI-регион всего контейнера (singleton или корневой scope) → Shared;
  4. достижим по полям или захватам из общего корня → Escaped, с цепочкой «X сохранён в F объекта Y в файле:строке»;
  5. к нему обращается исполнение, которое его не создавало → Escaped;
  6. к нему обращаются только создавшие его исполнения → ThreadConfined;
  7. к нему никто не обращается → Owned.

Пара на регионе ThreadConfined отбрасывается фильтром confined. Неизвестный (opaque) вызов ownership не меняет никогда.

Исполнения и happens-before

ExecutionModel.Build превращает roots и spawn sites в execution instances. Вид исполнения (ExecutionKind): Root, Spawn, TimerCallback, LazyConstruction (первый resolve singleton-а), TypeInitializer, Startup, UnknownEnumeration (сбежавший итератор) и UnknownDelegateCall (делегат, отданный неизвестному вызову).

Пересечение решается просто: Overlaps(a, b) = a != b || OverlapsItself(a). Два разных исполнения могут пересекаться всегда; одно исполнение пересекается само с собой, только если его политика Repeated + MayOverlap или неизвестна. Вся тонкость — в том, какая политика у порождённого исполнения и какой порядок доказан.

Кратность spawn-а

Spawn выполняется не более одного раза (AT_MOST_ONCE), только если родитель запускается один раз, место spawn-а не стоит в цикле CFG и до тела ведёт не больше одного пути вызовов (SiteOnce). Parallel.*, нераспознанные формы, рекурсивные spawn-ы и периодические таймеры всегда REPEATED. Хвост async-метода после первого await — отдельное исполнение с политикой родителя.

Поиск пути

HappensBefore строит граф событий (Point, Start, End, Join) и ищет путь в ширину. Ordered(a, b) = Path(a, b) || Path(b, a). Внутри исполнения событие x раньше y, если x недостижим из y по межпроцедурному CFG, поэтому цикл ничего не упорядочивает. Рёбра между исполнениями:

  • spawn → начало задачи (только доверенные, из однократного исполнения);
  • конец задачи → доказанный join. Join доказан, если handle разрешается ровно в один регион одного исполнения того же дерева, этот spawn однократный и ожидание стоит на всех путях. Wait() и Join() могут бросить до завершения, поэтому catch вокруг них ломает join; await бросает только после завершения;
  • конец итераций Parallel.For/ForEach → возврат вызова, даже если итерация бросила;
  • конец antecedent → начало ContinueWith;
  • конец всех аргументов WhenAll → join (если все элементы известны; List<Task> — неизвестны);
  • конец callbacks таймера → доказанное ожидание DisposeAsync или Dispose(WaitHandle);
  • конец startup → начало каждого исполнения вне дерева startup.

Ожидание в вызываемом методе поднимается к месту вызова, если каждый возможный вызываемый ждёт ту же цель на всех путях (AtCallSites): так работает void Run(Task t) => t.Wait();.

Доступы и защита

InterproceduralAccesses.Collect для каждого execution instance запускает ExecutionCollector в четыре шага: Visit → SolveLocks → SolveDependencies → Emit.

  1. Visit — обход в ширину по рёбрам вызовов, конструирования и первого использования типа. Каждый путь от root несёт свои guard-ы. На одно состояние хранится до 16 путей (MAX_ACCESS_PATHS); семнадцатый сливается, и guard-ы выше слияния теряются.
  2. SolveLocks — must-анализ удерживаемых замков: состояние на входе в тело — пересечение состояний всех мест вызова. Лямбда внутри lock начинает с пустым набором: её может вызвать кто угодно.
  3. SolveDependencies — какие чтения питают какую запись, в том числе через возвраты, аргументы, ref-параметры и ячейки захвата. Так SetLevel(GetLevel() + 1) становится RMW в SetLevel, с «прочитано в GetLevel» в доказательствах.
  4. Emit — выдаёт доступы: ресурс, вид операции, root, путь вызовов, удерживаемые замки, условия, spawn sites.

Must-held замки

Состояние анализа (MustHeldLocks) — «ключ замка → глубина, объект, место захвата» плюс три флага: CrossesSuspension (между захватом и освобождением есть await/yield), IsReleasedOnAllPaths, IsPaired. При слиянии ветвей ключи пересекаются, берётся меньшая глубина и более слабый режим. Обработчики catch/finally начинают с минимума по защищённой области. Ключ замка включает вид примитива, поэтому Monitor и Lock на одном объекте независимы. Освобождение замка, который не удерживается, очищает всё состояние — консервативно.

Identity замка — регион объекта. Замок, который не сводится ровно к одному объекту на процесс (lock (new object()), замок на поле per-request объекта), показывается в отчёте с пометкой «not one object per process» и доказать защиту не может.

Вердикт пары (PairProtection.Of) перебирает общие id замков и выбирает самый сильный: одинаковый примитив, исключающие режимы и оба удержания «исключающие» → sufficient; иначе partial; разные механизмы или неисключающие режимы → incompatible-mode. Без общих id: обе стороны что-то держат → different-identity, одна → partial, никто → unprotected. Удержание «исключающее», если для примитива, привязанного к потоку, нет CrossesSuspension, а для SemaphoreSlim — ёмкость 1, освобождение на всех путях и парность permits.

Эффекты вызовов поднимаются к месту вызова

Summary вызываемого несёт его захваты и освобождения (Lifted): что тело оставило открытым на выходе — захват в месте вызова; что тело освобождает на всех путях, не захватив, — освобождение (так Releaser.Dispose отпускает семафор). Это must-эффект: если хоть один возможный вызываемый ничего не несёт, доказательство теряется. Для невыжданного async-вызова поднимается только то, что удержано на каждом await и в конце тела. Итератор отдаёт телу цикла объединение состояний на yield, а коду после цикла — состояние на выходе и на ранних выходах через break.

Buckets и кандидаты

CandidateIndex раскладывает доступы по buckets и перебирает пары только там, где они могут встретиться:

  • внутри bucket-а ресурса — включая пару места доступа с самим собой (self-pair: root пересекается сам с собой);

  • открытый generic-регион (static:Cache<T>) — с закрытыми регионами своей группы по тому же пути.

Затем каждая пара проходит фильтры в порядке таблицы выше: read-read, no-conflicting-operation, no-overlap, ordered, confined, unsatisfiable-path, disjoint-iteration, и после них — вердикт защиты. Тест Demo_findings_are_identical_with_and_without_the_candidate_index сверяет индекс с наивным перебором всех пар.

Селекторы, guard-ы и решатель

ElementSelector — ячейка массива или коллекции: Exact (константа), Range [start, end), Symbol (символическое выражение, в отчёте [?]), Key (ключ словаря с учётом компаратора) или Unknown. Сказать «ячейки разные» могут только доказанные значения; любая другая комбинация — «могут совпасть».

PathPredicate — guard: равенство, неравенство, сравнения, null, проверка типа, с шириной и знаковостью типа. Неподдержанный предикат превращается в запись uncertainty. Дешёвая проверка PathConditions.Contradict ловит очевидные противоречия (null против not-null, разные константы, непересекающиеся диапазоны) — но только для «канонических» значений, которые означают одно и то же в обоих исполнениях.

SolverRefinement задаёт вопросы Z3 для выживших пар в порядке ожидаемой оценки (сначала те, где ответ сильнее всего изменит отчёт):

  • лимит 150 мс на запрос и 10% дедлайна (3 минуты) на весь run, общий для всех scope;
  • пустой запрос (меньше двух поддерживаемых предикатов и нет пары индексов) не задаётся, и path feasibility остаётся «not-analyzed»;
  • неканонические переменные переименовываются с префиксом стороны (first|, second|), чтобы i двух исполнений никогда не считались одной переменной;
  • запрос строится только из битовых векторов ширины типа: суммы переполняются, приведения обрезают или расширяют по знаку операнда, неизвестные значения — свежие переменные;
  • UNSAT снимает пару, SAT сохраняет её с моделью, Unknown сохраняет и снижает уверенность;
  • если нативная libz3 не загрузилась, каждый запрос отвечает Unknown, coverage это показывает, run продолжается (Z3ConstraintSolver.Create).

Находки, occurrences и оценка уверенности

ConflictFindings.Create собирает кандидатов всех scope в находки:

  1. ориентирует стороны A и B детерминированно (по телу, операции, порядку в теле);
  2. группирует кандидатов в находку по identity: правило, ресурс и отсортированная пара мест доступа (тело, операция, путь, span). Roots в identity не входят;
  3. сворачивает occurrences: по одной на пару roots с путями; внутри occurrence побеждает наименее защищённая пара; в отчёте показываются до трёх, считаются все;
  4. классифицирует правило, группирует находки одного правила на одном ресурсе в группу, сортирует группы по оценке и раздаёт run-local id G1…, F1….

Fingerprint — первые 16 hex-символов SHA-256 от строки

ch-fp-1|rule|scope|RegionKey|path|member|bodyA#ordinalA|opA|bodyB#ordinalB|opB|protection

где ordinal — порядковый номер доступа среди доступов того же тела к тому же ресурсу той же операцией, а RegionKey — регион без контекста. Поэтому fingerprint переживает сдвиг строк, переименование локальных и новых вызывающих, но меняется при смене правила, места, ресурса или результата защиты (FindingIdentityTests).

Один объект или два

Первый вопрос к любой паре доступов — указывают ли они на один объект. Анализ отвечает на него через points-to (куда может указывать каждая ссылка), а не по именам и типам.

alias-two-fieldsDCA1001
public sealed class Holder                   // AddSingleton<Holder>()
{
    private readonly Box _primary;
    private readonly Box _mirror;

    public Holder()
    {
        _primary = new Box();
        _mirror = _primary;                      // один объект в двух полях
    }

    public void WritePrimary(string value) => _primary.Value = value;   // worker
    public string? ReadMirror() => _mirror.Value;                       // GET action
}

Синтаксически _primary.Value и _mirror.Value — разные выражения. Points-to видит, что оба поля указывают на один region alloc:Holder..ctor()#Box, поэтому ресурс один: (alloc:…#Box, [Value]). Без points-to эта гонка теряется молча — именно этот пример в ADR 0002 решил, что points-to нужен в первой версии.

escape-into-singletonDCA1001 × 2

{

    _registry.Current = draft;        // объект опубликован в singleton...
    draft.Body = "worker";            // ...и только потом заполнен
    return Task.CompletedTask;

Локальная переменная draft сама по себе ничего не значит: объект, созданный в методе, сбегает (escape), когда его сохраняют туда, откуда его может достать другое исполнение. Ownership региона становится Escaped, и запись draft.Body встречается с чтением в action. Если бы объект не сбегал (demo owned-local-allocation: создать, заполнить, прочитать в одном запросе), region получил бы ownership ThreadConfined, и все его пары отбросил бы фильтр confined.

Отличить объекты, которые только выглядят одинаково

Обратная сторона — не склеивать разные объекты. Этим занимается context sensitivity кучи:

  • distinct-allocation-sites нет находки — один тип и поле, но два разных new, по worker-у на каждый: два региона.
  • receiver-sensitivity нет находки — одно тело метода вызывается на двух разных объектах. Для instance-методов контекст — это абстрактный receiver, поэтому эффекты не смешиваются.
  • factory-distinct-call-sites нет находки — один new в статической фабрике, два места вызова. Для статических методов контекст — место вызова (1-call-site).
  • factory-returns-shared-static DCA1001 — «фабрика» на деле возвращает один статический объект: identity сохраняется, объект общий.

Число контекстов на метод ограничено (сейчас 16). При переполнении контексты сливаются консервативно: эффекты объединяются, ownership становится Unknown, и это видно в uncertainty находки. Слияние никогда не порождает ложной защиты или изоляции.

Два приложения — два процесса

Гонка возможна только внутри одного процесса ОС. Solution часто содержит несколько приложений, которые ссылаются на общую библиотеку. Process scope — это исполняемый проект вместе с проектами, которые он загружает (ADR 0005). Статическое поле общей библиотеки в двух scope — это два разных объекта.

Конструкторы и публикация объекта

Почти любой объект получает поля в конструкторе. Если читать конструктор как обычный код, запись в нём «гоняется» со всеми последующими чтениями, хотя до конца конструирования объект никто не видит. Порядок: spawn, join и happens-before

Два исполнения могут пересекаться, но конкретная пара доступов в них может быть упорядочена. Классика — родитель, который ждёт свою задачу:

task-handle-join-order/before-await DCA1001/after-await нет
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    var task = Task.Run(() =>
    {
        BeforeAwait = "spawned";
        AfterAwait = "spawned";
    });
    BeforeAwait = "parent";     // задача ещё может работать
    await task;                 // join: handle доказанно принадлежит этой задаче
    AfterAwait = "parent";      // задача уже завершилась
}

Правила, которые вытекают из этой картинки (ADR 0008):

  • Join должен выполняться на всех путях, включая исключительные. В join-skipped-on-exception DCA1001 await task стоит в try после вызова, который может бросить; после catch родитель пишет поле, а задача может ещё работать.
  • Handle должен быть доказанно тот же. Задача, сохранённая в поле и awaited в другом методе, — это spawn с join (task-handle-awaited-elsewhere нет находки); задача, чей handle ни на одном пути не доходит до ожидания, — fire-and-forget.
  • WhenAny, ожидание с таймаутом, ManualResetEventSlim.Wait() и Dispose() — не join. event-wait-not-ordering DCA1001 — известное ограничение: event-ожидания порядка не дают.
  • Путь доверяется только внутри одного instance tree. Spawn-ребро верно для всех экземпляров, только если порождающее исполнение запускается один раз (root, который не пересекается сам с собой, например один BackgroundService) и spawn не стоит в цикле. Задача, запущенная из HTTP action, упорядочена со «своим» запросом, но не с соседним запросом — поэтому все spawn-кейсы demo живут внутри одного worker-а.
  • Старт хоста предшествует всем roots. Поэтому запись из Program до запуска хоста (startup-write-before-run) и конструкторы hosted services ни с чем не пересекаются.
  • Happens-before только удаляет пары. Новые пары появляются только из новых исполнений, никогда из графа. Ребро, чья identity handle или сам join не доказаны, не добавляется.

Async-метод без немедленного await

Вызов async-метода, результат которого сразу не ожидают, — тоже spawn, но особый: синхронный префикс до первого await выполняется прямо в вызывающем, а хвост после него — отдельное исполнение (TD-060a).

fire-and-forget-vs-awaited/dropped DCA1001/awaited нет

    Dropped = "parent";       // пересекается с хвостом DropAsync
    Saved = "parent";         // упорядочено после SaveAsync

private async Task DropAsync() { await Task.Yield(); Dropped = "drop"; }

Префиксы StepA и StepB выполняются по очереди в вызывающем, ещё до того, как WhenAll вообще получит задачи, — поэтому Prefix не гонится. Хвосты после await Task.Yield() — два параллельных исполнения, и Suffix гонится.

Замок, привязанный к потоку, и await

Monitor, System.Threading.Lock, Mutex и ReaderWriterLockSlim принадлежат потоку, который их взял, а продолжение после await может выполниться на другом потоке. Область такого примитива с await (или yield return) между захватом и освобождением получает partial, а не sufficient. SemaphoreSlim к потоку не привязан, поэтому await _sem.WaitAsync() … Release() в finally — нормальная защита (semaphore-slim-capacity-one нет).

Самописные замки: обёртка прозрачна

Анализ никогда не распознаёт замок по имени или форме типа. Класс SimpleLock с методами Lock()/Unlock() без настоящей синхронизации внутри — не защита (custom-lock-by-name DCA1001), как и SpinLock, который не входит в моделируемые примитивы (spin-lock-not-protection DCA1001). Но обёртка над настоящим примитивом работает — потому что она прозрачна: summary метода уже несёт его захваты, а Dispose, который освобождает примитив, — это освобождение в точке Dispose (ADR 0009).

{

public sealed class Ledger                   // AddSingleton<Ledger>(); два worker-а
{
    private readonly SemaphoreSlim _semaphore = new(1, 1);
    private readonly AsyncLock _lock;
    private string? _entry;

    public Ledger() => _lock = new AsyncLock(_semaphore);

    public void Append(string entry)

        using (_lock.Enter())                // захват сводится к _semaphore.Wait()

    }
}

Защиту доказывает тот же must-hold анализ, что и для lock, и identity защиты — region семафора, а не обёртки. Поэтому две разные обёртки над одним доказанным семафором защищают друг друга, а обёртки над разными семафорами дают different-identity. Обёртка над семафором с недоказанной ёмкостью не даёт защиты вообще — даже partial.

Коллекции: структура отдельно от ячеек

Для массивов, спанов и коллекций access path заканчивается селектором ячейки: [0], ["a"], [0..8] или [?]. Если бы у коллекции были только ячейки, доказанно разные ключи снимали бы любую пару — а это неверно в опасную сторону. Поэтому у каждой коллекции два вида ресурсов (ADR 0010): структура (количество, слоты, порядок; путь к самой коллекции) и хранилище элементов (путь плюс селектор).

dictionary-disjoint-keys-structuralDCA1001 на структуре
public sealed class Ledger                   // AddSingleton<Ledger>(); два worker-а
{
    public Dictionary<string, int> Entries { get; } = new();
    public void AddFirst()  => Entries.Add("first", 1);
    public void AddSecond() => Entries.Add("second", 2);
}

Какие ресурсы трогает каждый член, записано в таблице членов (ADR 0010 и её поправка 5b). Несколько неочевидных строк: Count и ContainsKey читают только структуру; индексатор-get читает структуру и ячейку; удаление пишет и ячейку, потому что переход «есть → нет» тоже можно потерять; Insert/RemoveAt у List<T> сдвигают соседей и пишут ячейку [?]; перечисление читает структуру и все ячейки. HashSet, Queue, Stack и LinkedList моделируются так же, всегда с ячейкой [?].

У ConcurrentDictionary оба ресурса атомарны: пары двух GetOrAdd нет, и перечисление во время изменения — определённое поведение (concurrent-dictionary-enumerate-while-mutate/concurrent-dictionary нет). Но последовательность атомарных вызовов не атомарна:

concurrent-dictionary-compoundDCA1004 × 2
[HttpPost("flag")]
public void PostFlag()
{
    if (!_registry.Flags.ContainsKey("ready"))   // проверка...
        _registry.Flags["ready"] = 1;            // ...и действие: между ними успевает другой запрос
}

[HttpPost("count")]

Проверка, которая решает, выполнится ли изменение, считается такой же зависимостью, как зависимость по значению. Поэтому check-then-act — это неатомарный RMW над составной операцией, а значит DCA1004. Замена на thread-safe коллекцию тут не помогает: нужна одна критическая секция на проверку и действие либо атомарный член вроде GetOrAdd/AddOrUpdate.

Guard-ы двух исполнений можно связать между собой только если доказано всё сразу: region — ровно один объект на процесс (статик, DI singleton или аллокация, выполняемая не более раза), поле readonly или get-only auto-property, вне конструирования его никто не пишет, и чтение идёт после конструирования. Тогда IsPrimary ∧ ¬IsPrimary — UNSAT. Во всех остальных случаях значение принадлежит одному исполнению и снять пару не может. С неподдержанным предикатом (Name.StartsWith("x")) пара остаётся с пометкой в uncertainty (unsupported-guard-kept DCA1001).

Guard передаётся к доступу по каждому пути от root отдельно (до 16 путей на доступ; дальше условия выше слияния отбрасываются с потерей точности, но не корректности). Условие вызывающего на значение аргумента ограничивает соответствующий параметр — только для параметров по значению и только для входного значения, не после переприсваивания.

Итераторы исполняются там, где их перечисляют

Вызов метода с yield return ничего не выполняет: он строит перечислитель. Тело работает по кусочку в MoveNext — там и тогда, где и когда кто-то перечисляет. Если бы анализ помещал тело в точку вызова, он ошибался бы как раз в защите (ADR 0011).

iterator-created-under-lockDCA1003 · partial
public IEnumerable<int> Walk() { Value = 1; yield return 1; }

// EnumeratingWorker
IEnumerable<int> sequence;
lock (_state.Gate)
    sequence = _state.Walk();      // тело ещё не выполнялось
foreach (var item in sequence) { } // Value = 1 выполняется здесь, без замка

// WritingWorker
lock (_state.Gate) _state.Value = 2;

Зеркальный кейс iterator-enumerated-under-lock нет: итератор создан вне замка, а foreach стоит внутри lock — тело действительно защищено. Итератор, который ушёл туда, где анализ не видит перечисления (сохранён в поле, отдан ToList или неизвестной библиотеке), дополнительно исполняется unknown execution: оно пересекается со всеми исполнениями своего process scope, включая себя, ничем не упорядочено и не держит замков (iterator-escapes-to-field DCA1001).

    Gate.Wait();                 // захват в хвосте, после первого await

От невыжданного async-вызова к вызывающему поднимается только то, что синхронный префикс захватил и тело не отпускает ни в одной точке, где может вернуть управление. Захват хвоста принадлежит хвосту и вызывающего не защищает.

Opaque call: UnknownEffect

Неизвестный вызов не считается «ничего не делающим». Его эффект — одно обращение вида UnknownEffect, которое читает и пишет всё, что достижимо из receiver и аргументов, до глубины summaries и wildcard дальше. В процедуре конфликта он ведёт себя как запись. Но есть важные сужения, каждое из которых снимает огромный шум:

  • Объект одного исполнения (Owned, ThreadConfined) такой вызов только читает: вызов ничей ownership не меняет. Измерение на eShop: обратное правило давало 913 новых находок против 2.
  • readonly-поле тоже только читается (кроме reflection), а то, на что оно указывает, получает эффект целиком.
  • Через receiver виден только тип, объявивший член: библиотечный член, вызванный на объекте из исходников (base-конструктор, унаследованный HttpContext), полей исходников не видит.
  • На структуре thread-safe коллекции эффект атомарен, как её собственные члены.

Вызов — semantic gap вида unknown-library. Он решает одну из проверок находки (здесь — операцию: одна из сторон и есть его UnknownEffect), поэтому этот компонент оценки становится 10 баллов, а итоговый score ограничен 79 — метка не выше Medium. Gap, который лишь стоит на пути вызовов до доступа, находку не меняет.

Делегат, отданный неизвестному вызову, выполняется в unknown execution: когда угодно и сколько угодно раз, ничем не упорядоченно, без замков вызывающего. Одно исключение: делегат отдан в одном месте исполнением, которое запускается один раз и проходит это место один раз (как здесь — worker), — тогда он сам с собой не пересекается. То, что лямбда захватила из объектов «своего» исполнения, остаётся изолированным.

Semantic gap

Opaque call становится gap-ом, только когда его UnknownEffect достаёт до изменяемого региона с ownership Escaped/Shared/Unknown, когда ему передан делегат, или когда его результат записывается в поле общего региона. Вызов только со строками, числами и неизменяемыми типами gap-ом не бывает (reflection-primitive-args-no-gap нет gap). Виды gap: reflection, dynamic, unresolved-dispatch (interface/virtual/delegate-вызов без известного объекта), model-gap (service locator с неконстантным типом) и unknown-library. Gap один на callee в пределах process scope. Их порядок в отчёте — materiality: сначала число roots, потом число регионов, потом число мест вызова, без общего «скора».

Классический пример, где gap честно оставляет неопределённость, — Channel<T> (channel-handoff нет находки): объект, прочитанный consumer-ом, с записанным producer-ом не связан, а запись в канал общего объекта видна как gap в coverage — неопределённость, а не безопасность.

Сейчас gaps только показываются: в отчёте (coverage и uncertainty) и в confidence. AI-разрешение gap-ов — пакеты для субагентов, проверка ответов и повторный fixpoint — запланировано в фазах 5c–5d.

Одна гонка — одна находка

Identity находки — правило, ресурс и неупорядоченная пара мест доступа. Roots, которые до этих мест доходят, — её occurrences, а не отдельные находки (ADR 0007).

group-shared-helper-many-callersDCA1001 · 1 находка, 6 occurrences
public sealed class ActivityLog              // AddSingleton<ActivityLog>()
{

}

[HttpPost("update")] public void Update() => _log.Record("update");

Место записи одно, пара — запись с самой собой. Occurrences — пары roots: 3 самопересечения и 3 пары разных actions, всего 6. Fingerprint находки считается по правилу, содержащим символам обоих мест, форме ресурса, видам операций и результату защиты, но без roots: четвёртый вызывающий не меняет fingerprint, и suppression по нему продолжает работать. Меняется fingerprint только при смене причины.

Глубокие пути и wildcard

Access path ограничен глубиной 8. Более длинный путь сворачивается в wildcard-ресурс ["*"] на регионе, с которого он начинается (deep-access-path-wildcard DCA1001 · Medium). Точное поле не установлено: компонент «ресурс» в оценке падает с 25 до 10, поэтому типичная wildcard-находка получает Medium, а uncertainty называет причину.

Формат expected-findings.json

Ожидания пишутся руками и до реализации и никогда не генерируются из результата анализатора — иначе demo проверял бы сам себя. Запись находки — правило, метка уверенности, ресурс в символьной форме и неупорядоченная пара доступов; roots в identity не входят:

{
  "id": "rmw-singleton-counter",
  "phase": "2",
  "rule": "DCA1002",
  "confidence": "high",
  "resource": {
    "region": "di:Demo.Web.Cases.RmwSingletonCounter.HitStats@Singleton",
    "accessPath": ["Hits"]
  },
  "accesses": [
    { "symbol": "Demo.Web.Cases.RmwSingletonCounter.HitsController.Post()", "operation": "read-modify-write" },
    { "symbol": "Demo.Web.Cases.RmwSingletonCounter.HitsController.Post()", "operation": "read-modify-write" }

}

Две одинаковые стороны — это self-pair action-а. Запись в notDefects без accesses запрещает любую находку на ресурсе, с accesses — только на этой паре. Ячейка коллекции пишется отдельным сегментом пути: ["_cells", "[0]"], ["Items", "[?]"]. Поле phase говорит, с гейта какой фазы запись проверяется; её содержимое — окончательный ответ первой версии и при смене фаз не переписывается.

Правила, которые нельзя нарушать

Эти правила записаны в SPEC и ADR, но в коде их легко нарушить незаметно — одна правка в одном слое без соседнего. Перед каждым изменением движка стоит перечитать список.

  1. Unknown — не safe. Пару удаляет только доказательство. Недоступный решатель, таймаут, слитый контекст, неизвестный вызов, неизвестный компаратор снижают уверенность, но пару оставляют.
  2. Защита — самый опасный вердикт. sufficient только при общем объекте, совместимых режимах и удержании на всех путях. Никакого распознавания по имени или форме пользовательского типа.
  3. Happens-before только удаляет пары. Ребро без доказанной identity handle или без join на всех путях не добавляется.
  4. Неизвестный вызов не меняет ownership. Объект одного исполнения он только читает, общий — читает и пишет.
  5. AI не доказывает безопасность. Принятый AI-факт может добавить ребро, эффект или находку, но не может удалить детерминированный эффект или доказать синхронизацию или порядок.
  6. Одна пара мест доступа — одна находка. Roots — occurrences; fingerprint не зависит от roots.
  7. Никакого декартова перебора. Новые виды ресурсов встраиваются в buckets CandidateIndex.
  8. Analysis не ссылается ни на что. Roslyn-специфичное остаётся во frontend, граница — IR.
  9. Ожидания demo пишутся руками до реализации. Подтверждённый false positive или false negative получает минимальный demo-кейс.
  10. Детерминизм. Все порядки обхода и сортировки ordinal и стабильны: demo-гейт требует одинаковый результат на трёх прогонах.
  11. Документация описывает текущее состояние. История изменений — только в CHANGELOG; в README, SPEC и этом руководстве пишется, как работает сейчас.

Как доработать: частые задачи

Новый demo-кейс

  1. Один файл demo/Demo.Web/Cases/<PascalName>.cs, один namespace Demo.Web.Cases.<PascalName>, регистрация через метод-расширение Add<Case>() или Map<Case>(), вызванный из Program.cs. Общих строк между кейсами нет.
  2. Кейс фазы не содержит конструкций поздних фаз, если они не его предмет: иначе метка уверенности сдвинется в поздней фазе, а запись ожиданий переписывать нельзя.
  3. Если нужна пара, которая не пересекается сама с собой, пишите в двух BackgroundService, а action пусть только читает.
  4. Запись в expected-findings.json (kebab-имя файла как id) и строка в таблице своей фазы в SCENARIOS.md — до изменения движка.

Новый execution root

  1. Один класс IExecutionRootProvider: распознавание по ExactSymbols (символ + диапазон версий), ExecutionRootDescriptor со стабильным id, InstanceBindings и InvocationPolicy.
  2. Регистрация в BuiltInProviders.Create().
  3. Случаи в ProviderFixture с именами Provider_Scenario_ExpectedOutcome и сквозной тест root → находка → отчёт. Шаблон — SyntheticProviderEndToEndTests. Ядро не меняется.

Новый член в таблице библиотек

  1. Одна строка в файле семейства Core/Providers/LibrarySemantics/*Family.cs. Пример из SystemTextJsonFamily.cs:
Known("M:System.Text.Json.JsonSerializer.Serialize``1(``0,System.Text.Json.JsonSerializerOptions)~System.String",
      DeepReadOf("value")),
  1. Обновить эталонный список в LibrarySemanticsTableTests (тест сравнивает таблицу с ним точно). Contract-тесты сами проверят, что id разрешается в реальной сборке, эффект называет существующий параметр, член не принимает делегат и не является setter-ом.
  2. Добавлять только члены, которые реально встретились в demo или корпусах, и никогда — члены, меняющие собственное состояние библиотечного объекта.

Новая конструкция C#

  1. Ветка в LowerValue или LowerTop; новая цель присваивания — LowerStore, адресуемая или RMW-цель — LowerAddress и TryLocation.
  2. Каждое новое определение локальной переменной — в SsaPlan.Scan в том же порядке вычисления, иначе лоуеринг бросит «No SSA definition was planned».
  3. Новый вид операции: запись в IrOperations.cs, ветка в IrPrinter (тест Every_operation_kind_has_a_text_form упадёт без неё), правила в IrValidator, обработка в MethodSummaryBuilder, ReachableSet, HappensBefore и InterproceduralAccesses; подумайте о повышении IrSchema.VERSION.

Новый вид региона

Перечисление в WholeProgram.cs и создание через Region(); затем switch ownership в ExecutionModel, IsContainerWide/SharedRoots, CreationExecutions, AssignRegionExecutions (если регион конструируется), IsInternal, SingleObjects. Проверьте все места, где identity разбирается строкой.

Открытые вопросы

Нумерация — из demo/SCENARIOS.md; каждый решается в плане указанной фазы до написания кейса.

  • 25 (5b) — RMW через одну ссылку в раздельных операторах (ref int r = ref s.Value; var old = r; r = old + 1;) сейчас классифицируется как DCA1001, а не DCA1002.
  • 30 (5b) — куча не хранит элементы List<T> и Dictionary: _state.Items[0].Value = 1 не даёт доступа, а тот же код над массивом даёт.
  • 21 (5c) — снимает ли принятый AI-факт консервативную модель того же opaque-вызова.
  • 20, 29 (5e) — имя региона для keyed-регистраций; эффект returns-arg у LINQ-операторов, сохраняющих элементы.
  • 9, 13 (6) — корень репозитория для suppressions.json; что именно redaction убирает из сниппетов.

Временные границы

Что сейчас намеренно не моделируется и какая фаза это снимет: resolver не вызывается, gaps только видны в отчёте (5d); EF Core — opaque persistence без entity tracking, и общий между исполнениями DbContext не виден (5e); лямбды LINQ-операторов, Polly и MediatR исполняются в unknown execution (5e); [ThreadStatic], ThreadLocal, AsyncLocal, keyed и Type-регистрации не анализируются (5e); suppressions не реализованы (6); только Windows x64 (8).

Похоже на дефекты — стоит проверить тестом

  • Составное присваивание элементу. LowerCompoundAssignment и LowerIncrement обрабатывают поля, auto-properties, ссылки и локальные переменные. Для элемента массива (a[i]++, a[i] += x), обычного индексатора (dict[k] += 1) и свойства с телом (P++) они возвращают Unknown(compound, "unsupported") без операндов: ни чтение, ни запись, ни вызовы внутри индекса не попадают в IR, хотя LowerUnsupported для остальных конструкций детей опускает. Ни в тестах, ни в demo такой формы нет. Если подтвердится, это пропуск DCA1002.
  • Startup и unknown executions. HappensBefore.EndEdges ведёт ребро из конца startup ко всем исполнениям вне дерева startup, включая UnknownDelegateCall и UnknownEnumeration. Комментарий в ExecutionModel и ADR 0011 говорят, что unknown execution не упорядочено «даже startup-ом». Делегат, отданный неизвестному вызову во время старта, может выполниться ещё во время старта.

Словарь

Термины из CONTEXT.md с объяснением по-русски. В скобках — слова, которые словарь запрещает использовать вместо термина.

Run
Один запуск команды от run_start до terminal status. (не scan, session, job)
Skill / Server
Skill — инструкция для агента хоста, единственный оркестратор run. Server — анализатор за MCP: хранит состояние и дедлайн, сам AI не запускает.
Deadline, late response
30 минут от старта run. Ответ AI, пришедший позже, записывается как late и не применяется.
Terminal status
CompleteWithFindings, CompleteClean, Incomplete, Failed; Cancelled появится в фазе 5d.
Execution root
Точка, откуда фреймворк или рантайм начинает независимое исполнение. (не entry point, handler, thread)
Spawn site
Вызов в пользовательском коде, начинающий новое исполнение из текущего. (не fork, background call)
Execution instance
Одно логическое исполнение root-а или spawn-а; не поток ОС. (не thread, request, task)
Fire-and-forget
Вызов, возвращающий задачу, чей handle ни на одном пути не доходит до ожидания.
Unknown execution
Исполнение, о котором известно, что оно запустит код, но неизвестно кто: перечисление сбежавшего итератора или вызов делегата, отданного opaque-вызову. Пересекается со всем в своём scope, включая себя.
Join
Точка, которая выполняется только после завершения другого исполнения, доказанная на всех путях для handle именно этого исполнения. WhenAny, ожидание с таймаутом, event-ожидание и Dispose() — не join.
Happens-before
Доказанный порядок двух событий: путь через spawn, join, продолжения и startup внутри одного instance tree.
Instance tree
Root, который запускается не более раза и не пересекается сам с собой, вместе с порождёнными из него однократными исполнениями. Единственное место, где путь happens-before считается доказательством.
Construction
Работа конструктора или type initializer. Её обращения к собственному объекту не образуют пар, пока объект не опубликован; остальное принадлежит исполнению, которое её запустило.
Reachable set
Тела методов, достижимые из roots и spawn sites. Только они опускаются в IR и считаются в coverage.
Process scope
Исполняемый проект вместе с проектами, которые он загружает. Статик в двух scope — два объекта. (не solution, app)
Heap region
Идентичность объекта или множества объектов: место аллокации с контекстом, статика, DI-экземпляр. (не object, instance)
Access path, selector
Путь поле за полем от региона до места; селектор — последний шаг в массив или коллекцию: константа, символическое выражение, диапазон или неизвестно.
Resource
Регион плюс access path — единица, по которой сравниваются доступы. (не shared state, variable)
Collection structure
Собственная форма коллекции (количество, слоты, порядок) — отдельный ресурс от ячеек.
Ownership
Owned, ThreadConfined, Escaped, Shared или Unknown — с цепочкой доказательств.
Access
Одна операция над ресурсом вместе с исполнением, удерживаемой защитой и guard-ом.
Candidate, bucket
Кандидат — пара, прошедшая дешёвые фильтры. Bucket — ячейка индекса кандидатов: доступы одного scope к одному ресурсу.
Finding, occurrence, fingerprint
Находка — правило, ресурс и пара мест доступа. Occurrence — пара roots, которой она достигается. Fingerprint — стабильное имя находки между прогонами, без roots.
Protection, protection result
Синхронизатор и режим, удерживаемые на всех путях к доступу. Результат пары: sufficient, partial, different-identity, incompatible-mode, unprotected.
Atomic operation
Операция, которую платформа выполняет неделимо над одним местом: Interlocked, Volatile, volatile. Свойство операции, а не защита.
Guard
Условие пути, при котором выполняется доступ. Два доступа с несовместимыми guard-ами не встречаются. (не protection, lock)
Known call, deep read
Вызов без тела, описанный таблицей семантики для точного члена и версии. Deep read — чтение всего, что достижимо из аргумента.
Opaque call, unknown effect
Вызов без тела, который таблица не описывает. Его эффект — «может прочитать и записать всё, до чего достаёт», конфликтует как запись.
Semantic gap, gap packet, materiality
Неразобранный вызов, который трогает общее изменяемое состояние или получает делегат. Packet — ограниченный вопрос к AI о нём (фаза 5c). Materiality — порядок gaps по числу roots, регионов и мест вызова.
Inferred fact
Гипотеза AI, прошедшая проверку сервером и помеченная как AI-derived (фаза 5c).
Confidence label
High (80+), Medium (55–79), Low. Не severity: severity — отдельная оценка последствий.
Skeleton, narrative, report bundle
Skeleton — часть отчёта, которую сервер пишет сам. Narrative — текст AI к группе находок. Bundle — report.md, findings.json, run-metadata.json.
Suppression
Решение пользователя скрыть находку с обязательной причиной; меняет только представление (фаза 6).
