Путеводитель по Concurrency Hunter

Статический анализатор гонок и потерянных обновлений в .NET-коде. Этот документ объясняет, какие ошибки он ищет, как устроен его алгоритм, как он ведёт себя в трудных случаях и где что лежит в коде — для того, кто будет его поддерживать и дописывать.

Документ идёт от общего к частному. Часть I — какую проблему решает плагин и из чего он состоит. Часть II — общий алгоритм: одна решающая процедура и конвейер, который применяет её, не перебирая все пары. Предполагается, что вы знаете, что такое гонка данных, lock и async/await, но ничего не знаете об устройстве плагина. Реализованное поведение здесь описано по исходникам и тестам рабочей копии. PRD объясняет задачи продукта, SPEC — контракты и планируемые возможности, CONTEXT.md — термины, ADR — причины архитектурных решений. Наличие возможности в SPEC само по себе не означает, что она уже подключена к обычному Run.

Для первого знакомства прочитайте общую картину и сквозной пример, затем выполните команды из раздела проверки. Для работы над библиотеками начните с моделей и генератора. Если исправляете пропуск или лишний Finding, используйте маршрут отладки по слоям.

Часть I Общая картина

Какую проблему решает плагин

В .NET-бэкенде один и тот же объект в памяти одновременно меняют HTTP-запросы, hosted services, задачи из Task.Run, callbacks таймеров и итерации Parallel.For. Каждый путь по отдельности выглядит правильно. Дефект появляется только при определённом чередовании чтений и записей двух путей, и воспроизвести его руками почти невозможно.

Самый короткий пример — счётчик в singleton-сервисе:

demo: rmw-singleton-counterDCA1002 · High
public sealed class HitStats
{
    public int Hits { get; set; }
}

[ApiController]
[Route("cases/rmw-singleton-counter")]
public sealed class HitsController : ControllerBase
{
    private readonly HitStats _stats;
    public HitsController(HitStats stats) => _stats = stats;

    [HttpPost]
    public void Post() => _stats.Hits++;   // чтение, +1, запись
}

// Program.cs
services.AddSingleton<HitStats>();         // один объект на весь процесс

Code review такие дефекты пропускает по трём причинам, и каждая из них определяет, что должен уметь анализатор.

  1. Какой объект на самом деле общий. Замените в примере выше AddSingleton на AddScoped — и гонки нет: у каждого запроса свой экземпляр (demo di-scoped-per-request). Код в контроллере не изменился, изменилась регистрация в другом файле. Совпадение имени поля или типа ничего не доказывает: нужен настоящий анализ того, куда указывают ссылки.
  2. Какие Execution Instances на самом деле пересекаются во времени. Два HTTP-запроса — да. Один BackgroundService.ExecuteAsync сам с собой — нет. Задача из Task.Run с родителем — только до await её handle. Периодический таймер — сам с собой тоже да.
  3. Достаточен ли Protection. lock на разных объектах не защищает. volatile не делает x++ атомарным. SemaphoreSlim — мьютекс, только если его ёмкость доказанно равна 1. Класс с методами Lock()/Unlock() — не доказательство, пока внутри нет настоящего примитива.

Кроме того, гонка часто пересекает несколько слоёв: запрос приходит в контроллер проекта Web, вызывает сервис из Application, а поле, которое теряет обновление, лежит в Domain (demo rmw-three-layers). Плагин связывает эти слои сам и показывает оба пути от Execution Root до Access.

Определение, на котором стоит весь плагин

Два Accesses образуют гонку, когда они обращаются к одному месту в памяти одного процесса, выполняются в Execution Instances, которые могут пересечься во времени, хотя бы один из них пишет, между ними нет доказанного порядка и нет общего достаточного Protection. Все остальные главы объясняют, как проверить каждое из этих условий статически, не запуская приложение.

Что плагин делает и чего не делает

Пользователь вызывает Skill concurrency-hunter:hunt с необязательным target; форма команды зависит от хоста (например, /concurrency-hunter:hunt [target]). Target — .sln, .slnx, .csproj или каталог. Плагин загружает проект через Roslyn и MSBuild и статически анализирует C#; само приложение для поиска гонок запускать не нужно. Server оставляет Report Bundle: report.md, findings.json и run-metadata.json. Исходники приложения он не исправляет. При использовании шаблонов Library Models слоя project анализ может обновить .concurrency-hunter/models/models.lock.json; отдельная команда generate пишет JSON в указанный --out.

Как устроен запуск: Skill и Server

Плагин состоит из двух частей, которые разговаривают по протоколу MCP. Разделение продиктовано тем, что умеют хосты: у Claude Code, Codex и Cursor команда плагина — это Skill (инструкция для агента хоста), а единственный программный интерфейс — stdio MCP Server. Server не может сам запустить AI или отменить субагента (ADR 0001).

  • Skill (skills/hunt/SKILL.md) — единственный оркестратор. Он запускает анализ, опрашивает Server, раздаёт субагентам хоста Finding Groups для текстового объяснения и просит Server отрендерить отчёт.
  • Server (ConcurrencyHunter.Cli, один активный Run на Server) — детерминированный анализатор и конечный автомат. Он хранит состояние Run и Deadline, проверяет всё, что приносит AI, и сам пишет отчёт.

Почему отчёт пишет Server, а не AI

Аудит legacy-кода даёт сотни Findings. Если отдавать модели всю цепочку доказательств и просить переписать её в отчёт, токены тратятся на текст, который не требует интеллекта, а Deadline в 30 минут за это платит. Поэтому Server детерминированно рендерит Skeleton: пути, доказательства, анализ Protection, сценарий чередования, Fingerprint. AI добавляет только Narrative группы — объяснение словами и варианты исправления с пометкой verify manually. Каждый фрагмент проходит NarrativeValidator: все процитированные evidence id существуют, все упомянутые файлы и символы есть в доказательствах группы. Неверный фрагмент отклоняется с причиной, разрешён один повтор (ADR 0003).

Чем заканчивается Run

СтатусКогда

CompleteClean означает отсутствие Findings в пределах модели анализа, а не доказанную безопасность приложения. Semantic Gaps и неподдержанные операции нужно читать в Coverage: сами по себе они не переводят Run в Incomplete. Статуса Cancelled в реализации нет.

Deadline принадлежит Server: через 30 минут после run_start он перестаёт выдавать работу, а всё, что пришло позже, записывает как Late Response и не применяет. Отменить уже запущенного субагента Server не может, и это честно записано в спецификации; гарантия в другом — опоздавший ответ никогда не меняет Findings.

Минимальный словарь

Словарь плагина живёт в CONTEXT.md. Термины нужны, чтобы различать близкие вещи: Execution Instance — логический запуск работы, который может продолжиться на другом потоке ОС; Resource — место в памяти, к которому могут вести разные переменные. Английские термины используются во всём руководстве; определения и пояснения даны по-русски. Полный словарь — в конце документа.

Execution Root
Точка, откуда фреймворк или рантайм начинает независимый Execution Instance: HTTP action, ExecuteAsync hosted service, callback таймера, gRPC-метод.
Spawn Site
Вызов в пользовательском коде, который начинает новый Execution Instance из текущего: Task.Run, Thread.Start, тело Parallel.For, Fire-and-forget.
Execution Instance
Один логический запуск работы из Execution Root или Spawn Site. Не поток ОС: await внутри его не заканчивает.
Heap Region
Идентичность объекта или множества объектов: место аллокации с контекстом, статическое поле, DI-экземпляр, параметр.
Resource
Heap Region плюс Access Path (поле за полем, с Selector ячейки). Единица, по которой сравниваются Accesses.
Ownership
Кто может достать Heap Region: Owned, ThreadConfined, Escaped, Shared, Unknown — всегда с цепочкой доказательств.
Access
Чтение, запись, RMW, Atomic Operation или составная операция над Resource — вместе с Execution Instance, удерживаемым Protection и Guard.
Happens-before
Доказанный порядок двух событий: путь через Spawn Site, Join, продолжения и старт хоста. Только удаляет пары, никогда не добавляет.
Protection
Синхронизатор (его Heap Region) и режим, который Access удерживает на всех путях к нему. «Может быть удержан» — не Protection.
Candidate → Finding
Пара Accesses, прошедшая дешёвые фильтры, — Candidate. Candidate, переживший уточнение, становится Finding с одним правилом DCA100x.
Occurrence
Один способ достичь пары мест Accesses: пара Execution Roots с путями вызовов. У Finding их может быть много.
Semantic Gap
Неразобранный вызов, который касается общего изменяемого состояния, получает делегат или передаёт результат в общий объект. Честно показывается в отчёте как неопределённость.
Alias / Points-to
Две ссылки — Aliases, если могут вести к одному объекту. Points-to хранит для значения множество возможных объектов; так анализ связывает синтаксически разные обращения к одной памяти.
Coverage
Что анализ удалось охватить и что осталось неизвестным: проекты, Execution Roots, неподдержанные операции, Semantic Gaps и применённые Library Models. Это не процент покрытия тестами.
Часть II Общий алгоритм

Решающая процедура

Всё, что делает анализатор, сводится к одной процедуре над парой Accesses A и B. Четыре правила DCA — это не четыре анализа, а четыре способа назвать её результат (SPEC §7):

Conflict(A, B) =
       SameProcessScope(A, B)                        // один процесс
    && MayResourcesOverlap(A.Resource, B.Resource)   // одно место в памяти
    && MayExecutionOverlap(A.Interval, B.Interval)   // могут идти одновременно
    && OperationsConflict(A.Operation, B.Operation)  // хотя бы одна неатомарная запись
    && !OrderedByHappensBefore(A, B)                 // нет доказанного порядка
    && !ProtectedByCommonSufficientPrimitive(A, B)   // нет общего достаточного Protection
    && PathPairIsNotUnsatisfiable(A.Guard, B.Guard)  // Guards совместимы

LostUpdate(A, B) =
       Conflict(A, B)
    && (A или B — неатомарный RMW или составная операция)
    && устаревшее чтение может повлиять на последующую запись

Каждая проверка возвращает не просто да/нет, а True, False или Unknown вместе с доказательствами. Отсюда главный принцип плагина:

Неизвестное — не безопасное

Пару удаляет только доказанное False: доказанно разные Resources, доказанная изоляция, доказанный порядок, доказанный Protection, UNSAT от решателя. Unknown пару оставляет и снижает уверенность. Ошибки несимметричны: лишний Finding стоит читателю минуту, ложное доказательство безопасности молча прячет настоящую гонку. Когда сомневаетесь при доработке — выбирайте сторону, которая оставляет пару.

Классификация правила

Правило выбирается после того, как пара пережила все фильтры, по видам двух операций и Protection Result (ConflictFindings.OperationRule и Classify):

// ConflictFindings.cs
if (!LosesUpdate(a.Op, b.Op) && !LosesUpdate(b.Op, a.Op))
    return CONFLICT_RULE;                                   // DCA1001
return IsIndivisible(a.Op) && IsIndivisible(b.Op)
    ? COMPOUND_RULE                                         // DCA1004
    : LOST_UPDATE_RULE;                                     // DCA1002

// LosesUpdate(stale, other): stale — RMW или Compound, а other меняет ячейку
// IsIndivisible(op):         Compound или любой Atomic*
// Classify: DCA1001 с Protection Result partial / different-identity / incompatible-mode → DCA1003

Несколько следствий, которые полезно помнить: RMW против простого чтения — DCA1001 (читатель ничего не теряет); RMW против UnknownEffect — DCA1002; составная операция против составной или атомарного RMW — DCA1004. DCA1002 и DCA1004 сохраняют своё правило при любом Protection, в DCA1003 переходит только DCA1001.

Конвейер анализа

Процедура выше применяется не к «всем парам всех Accesses» — их слишком много. Анализ устроен как конвейер, где дешёвые шаги идут раньше дорогих, а дорогая точность оплачивается только для пар, у которых уже есть общий Resource, конфликтующие операции и возможное пересечение. Общий Run ведёт PhaseOneAnalyzer.AnalyzeAsync, а повторно используемую часть для одного Process Scope выполняет ScopePipeline.Run:

До цикла по Process Scopes PhaseOneAnalyzer читает Library Models слоя project и Model Lock. Для компиляций каждого Process Scope ProjectModelResolver сопоставляет Library Models с точными символами; затем передаёт готовый набор в ScopePipeline. После анализа Process Scopes внешний конвейер сохраняет Model Lock. Сам ScopePipeline файлов Library Models не читает и Model Lock не пишет. Поэтому генератор может использовать тот же движок с другими Execution Roots и Library Models, не запуская полный пользовательский Run.

Несколько свойств конвейера, о которых стоит знать заранее:

  • Ленивое опускание в IR. ReachableSet строит граф вызовов по иерархии классов и опускает в IR тело метода в момент, когда впервые до него доходит. Тело вне Reachable Set не анализируется и не считается против Coverage. Ошибка опускания одного тела превращается в диагностику lowering: и пустое тело, а не в падение Run.
  • Слой Analysis не знает Roslyn. Всё после IR (куча, Execution Instances, пары, Findings, отчёт) живёт в проекте ConcurrencyHunter.Analysis, у которого нет ни одной ссылки на пакеты или проекты. Это проверяют тесты AnalysisBoundaryTests. Roslyn, Z3 и провайдеры — в ConcurrencyHunter.Core.
  • Никакого декартова произведения. Пары перебираются внутри Buckets одного Resource. Разница между числом сравнений и полным перебором видна в metrics: comparisons и cartesianBound.
  • Детерминизм. Порядок обхода, нумерация значений, порядок вопросов к решателю — стабильны. Demo-гейт трижды анализирует demo и требует побайтно одинаковый findings.json.

Сквозной пример: один Finding от начала до конца

Прежде чем разбирать стадии по отдельности, проследим один кейс — rmw-three-layers, где гонка живёт на два проекта ниже точки входа.

// Demo.Web

// Demo.Application
public void Place(int quantity) => _inventory.Reserve(quantity);             // OrderService

// Demo.Domain

Frontend: от Roslyn к IR

Frontend (ConcurrencyHunter.Core/Frontend/IrLowering.cs, самый большой файл проекта) берёт у Roslyn IOperation и control-flow graph каждого метода и строит собственное SSA-подобное промежуточное представление. Зачем своё IR, если есть Roslyn: чтобы всё, что ниже, можно было тестировать и развивать без объектной модели компилятора (TD-010, ADR 0002).

  • IrBody — одно на метод, лямбду или локальную функцию. Id тела: body:{Assembly}:{DocCommentId}, у вложенных — суффиксы #lambda{n} и #local:{Name}.
  • Блоки и области CFG копируются из CFG Roslyn один к одному, включая try/catch/finally. EffectiveFlowGraph добавляет рёбра входа и выхода из finally и исключительные рёбра из каждого блока try в обработчики.
  • Значения пронумерованы в пределах тела: параметры, receiver, локальные, временные, константы. SSA-версии и phi строит SsaPlan. SSA означает, что каждое присваивание получает свой номер значения: x = 1; x = 2; даёт два значения. В месте слияния веток phi перечисляет значения, которые могли прийти из этих веток.
  • Операции перечислены в IrOperations.cs. У каждой есть IrProvenance: файл, строка, колонка, содержащий символ, вид синтаксиса и тег правила опускания (increment, lock-statement, await…).

Как опускаются важные для конкурентности конструкции:

  • x++, x += y, ??= над полем или auto-property: load → compute → store с ReadModifyWriteOf. Над volatile-полем операции дополнительно помечаются atomic.
  • Массивы, индексаторы и свойства с телами. a[i]++ и a[i] += x сохраняют чтение, вычисление и запись ячейки; свойства и индексаторы вызывают getter и setter. Receiver и индексы вычисляются один раз, postfix возвращает прочитанное значение, prefix — записанное. У неподдержанной цели сохраняются вычисления её операндов. Контракт проверяет CompoundAssignmentLoweringTests.
  • Свойства. Автоматическое свойство (невиртуальное, из исходников) читается и пишется как поле-backing field. Остальные — вызовы getter/setter.
  • lock над объектом Roslyn сам переписывает в Monitor.Enter(o, ref taken)/Exit в try/finally — frontend превращает их в acquire/release. lock над System.Threading.Lock компилятор не переписывает и области CFG не даёт, поэтому секцию frontend восстанавливает по span оператора.
  • Примитивы Monitor, Lock, Mutex, SemaphoreSlim, ReaderWriterLockSlim распознаёт класс Synchronization. Любая перегрузка с таймаутом — условный захват: замок держится только на ветке, где флаг успеха истинен. WaitAsync ничего не держит, пока его результат не выжидают.
  • Interlocked и Volatile над полем или элементом становятся обычным load/store плюс пометка atomic.
  • Неявные вызовы C#. Pattern matching, деконструкция и перечисление могут вызывать пользовательские члены, хотя в тексте нет обычного вызова метода. Эти пути проверяют PatternImpliedCallTests, DeconstructionCallTests и ExplicitEnumerationTests. При расширении frontend важно сохранить их эффекты и provenance.
  • async и итераторы опускаются по исходному CFG, без state machine компилятора: await — операция await, yield return — операция yield.
  • Лямбды и локальные функции — отдельные тела. Захваченные переменные приходят во вложенное тело как входящие SSA-переменные с общим SymbolKey.
  • Вызовы BCL (Task.Run, Thread.Start, Parallel.*, Timer…) получают после call дополнительные операции spawn, join, when-all, timer (AnnotateBclCall). Распознавание — по имени метаданных, поэтому пользовательский тип с именем BCL-типа не распознаётся никогда.
  • Коллекции, Library Models, DI-locator — аннотации на call: Collection, Library, ServiceCall.

Execution Roots, DI и Reachable Set

Прежде чем строить кучу, анализ должен знать, откуда начинаются Execution Instances и какие объекты создаёт контейнер.

Провайдеры Execution Roots

DI-индекс

DiIndexBuilder собирает вызовы AddSingleton/AddScoped/AddTransient, TryAdd*, AddHostedService по точным символам и диапазону версий сборки. Разрешение сервиса (DiIndex.Resolve) даёт один из исходов: нет регистраций, неподдержанная форма (keyed, открытые generics, typeof-формы), неоднозначность (разные реализация или lifetime — ничего не связывает, пишет диагностику) или связь с последней регистрацией. Service locator (GetRequiredService, GetService, GetServices, CreateScope) распознаётся во frontend и разрешается в куче по области DI, из которой вызван.

Reachable Set

ReachableSet.Build стартует от Main, методов с регистрациями, конструкторов hosted services и controller-ов, тел Execution Roots и конструкторов DI-сервисов и идёт по графу вызовов на основе иерархии классов (CHA): вызов достигает метода и всех его override и реализаций с телом. Делегаты сопоставляются по форме, работа из Spawn Sites и callbacks таймеров, делегаты фабрик и константные locator-вызовы тоже достижимы. Это грубый надмножественный граф; точный строит куча, а тела, до которых CHA дошёл, а куча — нет, считаются в Coverage как lowered-not-reached.

Куча: Heap Regions, Points-to и Ownership

Куча отвечает на первый вопрос процедуры — один ли это объект. Это field-sensitive Points-to анализ в стиле Андерсена по местам аллокации, с ограниченной чувствительностью к контексту. На практике значение связывается с множеством возможных объектов: x → {A, B}. Field-sensitive означает, что A.Left и A.Right хранят разные множества. Анализ знает не конкретный объект из запущенной программы, а то, какие объекты могли быть созданы в указанном месте кода.

Summaries и fixpoint

Summary — описание поведения одного метода через его входы и выходы: например, «пишет поле Value у первого аргумента». Оно не привязано к конкретному caller. В месте вызова движок подставляет реальные Heap Regions аргументов. Fixpoint — повторение этого распространения, пока новые связи перестают появляться: возврат фабрики может открыть receiver следующего вызова, а тот — новые поля и вызовы.

MethodSummaryBuilder строит для каждого тела summary без контекста: Accesses с удерживаемыми замками и Guards, записи, возвраты, вызовы, делегаты, Spawn Sites и Joins, зависимости «эта запись вычислена из этого чтения». SummaryCache строит их лениво. Затем WholeProgram.Solve решает всё вместе — граф вызовов, Points-to, разрешение DI, фабрики, type initializers, handles задач и таймеров:

Run():
    Seed()                      // startup-члены + по экземпляру на каждый Execution Root; receiver-ы и параметры связаны
    do Propagate() while DefaultEmptyRegistrations()

Propagate():
    loop:
        before = _changes
        for instance in порядок создания:
            Process(instance)   // ячейки, записи, возвраты, модели, делегаты, type init,
                                // Call / Locate / Spawn / TimerCallback / Handoff / WhenAll / Unwrap
            if instance что-то изменил: CountRound(instance)
        EscapeCapturedHolders() // Holder, ушедший в неизвестный код, расширяет набор Execution Instances делегата
        ConstructFactory(каждая регистрация)
        ApplySinks()            // здесь псевдокод: связи со стоками общих объектов
        if _changes == before: break      // множества только растут → конечность

Два ограничения роста анализа. Когда у тела набирается 16 контекстов, все дальнейшие вызовы этого тела связываются с одним экземпляром @merged. Когда экземпляр меняет что-то в 16 проходах подряд, вычисляется его сильно связная компонента в графе экземпляров, и если она циклическая, все её тела сливаются (счётчик scc-budget-exceeded). Слияние консервативно: эффекты объединяются, Heap Region помечается как merged.

Точные типы объектов также помогают отбросить невозможный dispatch: если receiver доказанно List<T>, вызов члена несовместимого типа не исполняется. Это не полное доказательство всех веток программы. При неизвестном receiver анализ сохраняет неопределённость. Примеры — TypeSafetyTests, LateReceiverTests и demo type-test-fast-path.

Ownership

Ownership вычисляется уже после fixpoint, в ExecutionModel, потому что для него нужно знать Execution Instances. Первое подходящее правило решает:

  1. Heap Region со слитым контекстом → Unknown;
  2. статик → Shared;
  3. Heap Region из DI всего контейнера (singleton или корневая область DI) → Shared;
  4. достижим по полям или захватам из общего корня → Escaped, с цепочкой «X сохранён в F объекта Y в файле:строке»;
  5. к нему обращается Execution Instance, который его не создавал → Escaped;
  6. к нему обращаются только создавшие его Execution Instances → ThreadConfined;
  7. к нему никто не обращается → Owned.

Пара на Heap Region ThreadConfined отбрасывается фильтром confined. Opaque Call Ownership не меняет никогда.

Execution Instances и Happens-before

ExecutionModel.Build превращает Execution Roots и Spawn Sites в Execution Instances. Вид Execution Instance (ExecutionKind): Root, Spawn, TimerCallback, LazyConstruction (первый resolve singleton-а), TypeInitializer, Startup, UnknownEnumeration (сбежавший итератор) и UnknownDelegateCall (делегат, отданный Opaque Call).

Пересечение решается просто: Overlaps(a, b) = a != b || OverlapsItself(a). Два разных Execution Instances могут пересекаться всегда; один Execution Instance пересекается сам с собой, только если его политика Repeated + MayOverlap или неизвестна. Вся тонкость — в том, какая политика у порождённого Execution Instance и какой порядок доказан.

Кратность Spawn Site

Spawn Site выполняется не более одного раза (AT_MOST_ONCE), только если родитель запускается один раз, Spawn Site не стоит в цикле CFG и до тела ведёт не больше одного пути вызовов (SiteOnce). Parallel.*, нераспознанные формы, рекурсивные Spawn Sites и периодические таймеры всегда REPEATED. Хвост async-метода после первого await — отдельный Execution Instance с политикой родителя.

Поиск пути

HappensBefore строит граф событий (Point, Start, End, Join) и ищет путь в ширину. Ordered(a, b) = Path(a, b) || Path(b, a). Внутри Execution Instance событие x раньше y, если x недостижим из y по межпроцедурному CFG, поэтому цикл ничего не упорядочивает. Рёбра между Execution Instances:

  • Spawn Site → начало задачи (только доверенные, из однократного Execution Instance);
  • конец задачи → доказанный Join. Join доказан, если handle разрешается ровно в один Heap Region одного Execution Instance того же дерева, этот Spawn Site однократный и ожидание стоит на всех путях. Wait() и Join() могут бросить до завершения, поэтому catch вокруг них ломает Join; await бросает только после завершения;
  • конец итераций Parallel.For/ForEach → возврат вызова, даже если итерация бросила;
  • конец antecedent → начало ContinueWith;
  • конец всех аргументов WhenAll → Join (если все элементы известны; List<Task> — неизвестны);
  • конец callbacks таймера → доказанное ожидание DisposeAsync или Dispose(WaitHandle);
  • конец startup → начало каждого Execution Instance вне дерева startup.

Ожидание в вызываемом методе поднимается к месту вызова, если каждый возможный вызываемый ждёт ту же цель на всех путях (AtCallSites): так работает void Run(Task t) => t.Wait();.

Accesses и Protection

InterproceduralAccesses.Collect для каждого Execution Instance запускает ExecutionCollector в четыре шага: Visit → SolveLocks → SolveDependencies → Emit.

  1. Visit — обход в ширину по рёбрам вызовов, Construction и первого использования типа. Каждый путь от Execution Root несёт свои Guards. На одно состояние хранится до 16 путей (MAX_ACCESS_PATHS); семнадцатый сливается, и Guards выше слияния теряются.
  2. SolveLocks — must-анализ удерживаемых замков: состояние на входе в тело — пересечение состояний всех мест вызова. Лямбда внутри lock начинает с пустым набором: её может вызвать кто угодно.
  3. SolveDependencies — какие чтения питают какую запись, в том числе через возвраты, аргументы, ref-параметры и ячейки захвата. Так SetLevel(GetLevel() + 1) становится RMW в SetLevel, с «прочитано в GetLevel» в доказательствах.
  4. Emit — выдаёт Accesses; каждый содержит Resource, вид операции, Execution Root, путь вызовов, удерживаемые замки, Guards и Spawn Sites.

Must-held замки

Состояние анализа (MustHeldLocks) — «ключ замка → глубина, объект, место захвата» плюс три флага: CrossesSuspension (между захватом и освобождением есть await/yield), IsReleasedOnAllPaths, IsPaired. При слиянии ветвей ключи пересекаются, берётся меньшая глубина и более слабый режим. Обработчики catch/finally начинают с минимума по защищённой области. Ключ замка включает вид примитива, поэтому Monitor и Lock на одном объекте независимы. Освобождение замка, который не удерживается, очищает всё состояние — консервативно.

Identity замка — Heap Region объекта. Замок, который не сводится ровно к одному объекту на процесс (lock (new object()), замок на поле per-request объекта), показывается в отчёте с пометкой «not one object per process» и доказать Protection не может.

Вердикт пары (PairProtection.Of) перебирает общие id замков и выбирает самый сильный: одинаковый примитив, исключающие режимы и оба удержания «исключающие» → sufficient; иначе partial; разные механизмы или неисключающие режимы → incompatible-mode. Без общих id: обе стороны что-то держат → different-identity, одна → partial, никто → unprotected. Удержание «исключающее», если для примитива, привязанного к потоку, нет CrossesSuspension, а для SemaphoreSlim — ёмкость 1, освобождение на всех путях и парность permits.

Эффекты вызовов поднимаются к месту вызова

Summary вызываемого несёт его захваты и освобождения (Lifted): что тело оставило открытым на выходе — захват в месте вызова; что тело освобождает на всех путях, не захватив, — освобождение (так Releaser.Dispose отпускает семафор). Это must-эффект: если хоть один возможный вызываемый ничего не несёт, доказательство теряется. Для невыжданного async-вызова поднимается только то, что удержано на каждом await и в конце тела. Итератор отдаёт телу цикла объединение состояний на yield, а коду после цикла — состояние на выходе и на ранних выходах через break.

Buckets и Candidates

CandidateIndex раскладывает Accesses по Buckets и перебирает пары только там, где они могут встретиться:

  • внутри Bucket Resource — включая пару места Access с самим собой (self-pair: Execution Root пересекается сам с собой);
  • между ячейками одной коллекции — только если Selectors могут совпасть (MayOverlap);
  • Accesses с wildcard Heap Region — между собой и с каждым Bucket того же Heap Region;
  • открытый Heap Region generic-типа (static:Cache<T>) — с закрытыми Heap Regions своей группы по тому же пути.

Затем каждая пара проходит фильтры в порядке таблицы выше: read-read, no-conflicting-operation, no-overlap, ordered, confined, unsatisfiable-path, disjoint-iteration, и после них — Protection Result. Тест Demo_findings_are_identical_with_and_without_the_candidate_index сверяет индекс с наивным перебором всех пар.

Selectors, Guards и решатель

ElementSelector — ячейка массива или коллекции: Exact (константа), Range [start, end), Symbol (символическое выражение, в отчёте [?]), Key (ключ словаря с учётом компаратора) или Unknown. Сказать «ячейки разные» могут только доказанные значения; любая другая комбинация — «могут совпасть».

PathPredicate — Guard: равенство, неравенство, сравнения, null, проверка типа, с шириной и знаковостью типа. Неподдержанный предикат превращается в запись uncertainty. Дешёвая проверка PathConditions.Contradict ловит очевидные противоречия (null против not-null, разные константы, непересекающиеся диапазоны) — но только для «канонических» значений, которые означают одно и то же в обоих Execution Instances.

SolverRefinement задаёт вопросы Z3 для выживших пар в порядке ожидаемой оценки (сначала те, где ответ сильнее всего изменит отчёт):

  • лимит 150 мс на запрос и 10% Deadline (3 минуты) на весь Run, общий для всех Process Scopes;
  • пустой запрос (меньше двух поддерживаемых предикатов и нет пары индексов) не задаётся, и path feasibility остаётся «not-analyzed»;
  • неканонические переменные переименовываются с префиксом стороны (first|, second|), чтобы i двух Execution Instances никогда не считались одной переменной;
  • запрос строится только из битовых векторов ширины типа: суммы переполняются, приведения обрезают или расширяют по знаку операнда, неизвестные значения — свежие переменные;
  • UNSAT снимает пару, SAT сохраняет её с моделью, Unknown сохраняет и снижает уверенность;
  • если нативная libz3 не загрузилась, каждый запрос отвечает Unknown, Coverage это показывает, Run продолжается (Z3ConstraintSolver.Create).

Findings, Occurrences и оценка уверенности

ConflictFindings.Create собирает Candidates всех Process Scopes в Findings:

  1. ориентирует стороны A и B детерминированно (по телу, операции, порядку в теле);
  2. группирует Candidates в Finding по identity: правило, Resource и отсортированная пара мест Accesses (тело, операция, путь, span). Execution Roots в identity не входят;
  3. сворачивает Occurrences: по одному на пару Execution Roots с путями; внутри каждого Occurrence побеждает наименее защищённая пара; в отчёте показываются до трёх, считаются все;
  4. классифицирует правило, группирует Findings одного правила на одном Resource в группу, сортирует группы по оценке и раздаёт run-local id G1…, F1….

Fingerprint — первые 16 hex-символов SHA-256 от строки

ch-fp-1|rule|scope|RegionKey|path|member|bodyA#ordinalA|opA|bodyB#ordinalB|opB|protection

где ordinal — порядковый номер Access среди Accesses того же тела к тому же Resource той же операцией, а RegionKey — Heap Region без контекста. Поэтому Fingerprint переживает сдвиг строк, переименование локальных и новых вызывающих, но меняется при смене правила, места, Resource или Protection Result (FindingIdentityTests).

Отчёт, Narrative и жизненный цикл Run

RunRegistry — конечный автомат Run: Running → AwaitingNarrative (или Failed) → Done. Одновременно активен один Run; Run с истёкшим Deadline новый не блокирует. Один объект или два

Первый вопрос к любой паре Accesses — указывают ли они на один объект. Анализ отвечает на него через Points-to (куда может указывать каждая ссылка), а не по именам и типам.

alias-two-fieldsDCA1001
public sealed class Holder                   // AddSingleton<Holder>()
{
    private readonly Box _primary;
    private readonly Box _mirror;

    public Holder()
    {
        _primary = new Box();
        _mirror = _primary;                      // один объект в двух полях
    }

    public void WritePrimary(string value) => _primary.Value = value;   // worker
    public string? ReadMirror() => _mirror.Value;                       // GET action
}

Синтаксически _primary.Value и _mirror.Value — разные выражения. Points-to видит, что оба поля указывают на один Heap Region alloc:Holder..ctor()#Box, поэтому Resource один: (alloc:…#Box, [Value]). Без Points-to эта гонка теряется молча — именно этот пример в ADR 0002 решил, что Points-to нужен в первой версии.

escape-into-singletonDCA1001 × 2
protected override Task ExecuteAsync(CancellationToken stoppingToken)   // DraftWorker
{
    var draft = new Draft();
    _registry.Current = draft;        // объект опубликован в singleton...
    draft.Body = "worker";            // ...и только потом заполнен
    return Task.CompletedTask;
}

[HttpGet] public string? Get() => _registry.Current!.Body;          // action

Локальная переменная draft сама по себе ничего не значит: объект, созданный в методе, сбегает (escape), когда его сохраняют туда, откуда его может достать другой Execution Instance. Ownership Heap Region становится Escaped, и запись draft.Body встречается с чтением в action. Если бы объект не сбегал (demo owned-local-allocation: создать, заполнить, прочитать в одном запросе), Heap Region получил бы Ownership ThreadConfined, и все его пары отбросил бы фильтр confined.

Отличить объекты, которые только выглядят одинаково

Обратная сторона — не склеивать разные объекты. Этим занимается context sensitivity кучи:

  • distinct-allocation-sites нет Findings — один тип и поле, но два разных new, по worker-у на каждый: два Heap Regions.
  • receiver-sensitivity нет Findings — одно тело метода вызывается на двух разных объектах. Для instance-методов контекст — это абстрактный receiver, поэтому эффекты не смешиваются.
  • factory-distinct-call-sites нет Findings — один new в статической фабрике, два места вызова. Для статических методов контекст — место вызова (1-call-site).
  • factory-returns-shared-static DCA1001 — «фабрика» на деле возвращает один статический объект: identity сохраняется, объект общий.

Число контекстов на метод ограничено (сейчас 16). При переполнении контексты сливаются консервативно: эффекты объединяются, Ownership становится Unknown, и это видно в uncertainty Finding. Слияние никогда не порождает ложного Protection или изоляции.

Два приложения — два процесса

Гонка возможна только внутри одного процесса ОС. Solution часто содержит несколько приложений, которые ссылаются на общую библиотеку. Process Scope — это исполняемый проект вместе с проектами, которые он загружает (ADR 0005). Статическое поле общей библиотеки в двух Process Scopes — это два разных объекта.

Конструкторы и публикация объекта

Почти любой объект получает поля в конструкторе. Если читать конструктор как обычный код, запись в нём «гоняется» со всеми последующими чтениями, хотя до конца Construction объект никто не видит. Порядок: Spawn Site, Join и Happens-before

Два Execution Instances могут пересекаться, но конкретная пара Accesses в них может быть упорядочена. Классика — родитель, который ждёт свою задачу:

task-handle-join-order/before-await DCA1001/after-await нет
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    var task = Task.Run(() =>
    {
        BeforeAwait = "spawned";
        AfterAwait = "spawned";
    });
    BeforeAwait = "parent";     // задача ещё может работать
    await task;                 // join: handle доказанно принадлежит этой задаче
    AfterAwait = "parent";      // задача уже завершилась
}

Правила, которые вытекают из этой картинки (ADR 0008):

  • Join должен выполняться на всех путях, включая исключительные. В join-skipped-on-exception DCA1001 await task стоит в try после вызова, который может бросить; после catch родитель пишет поле, а задача может ещё работать.
  • Handle должен быть доказанно тот же. Задача, сохранённая в поле и awaited в другом методе, — это Spawn Site с Join (task-handle-awaited-elsewhere нет Findings); задача, чей handle ни на одном пути не доходит до ожидания, — Fire-and-forget.
  • WhenAny, ожидание с таймаутом, ManualResetEventSlim.Wait() и Dispose() — не Join. event-wait-not-ordering DCA1001 — известное ограничение: event-ожидания порядка не дают.
  • Путь доверяется только внутри одного Instance Tree. Ребро Spawn Site верно для всех экземпляров, только если порождающий Execution Instance запускается один раз (Execution Root, который не пересекается сам с собой, например один BackgroundService) и Spawn Site не стоит в цикле. Задача, запущенная из HTTP action, упорядочена со «своим» запросом, но не с соседним запросом — поэтому все кейсы Spawn Site demo живут внутри одного worker-а.
  • Старт хоста предшествует всем Execution Roots. Поэтому запись из Program до запуска хоста (startup-write-before-run) и конструкторы hosted services ни с чем не пересекаются.
  • Happens-before только удаляет пары. Новые пары появляются только из новых Execution Instances, никогда из графа. Ребро, чья identity handle или сам Join не доказаны, не добавляется.

Async-метод без немедленного await

Вызов async-метода, результат которого сразу не ожидают, — тоже Spawn Site, но особый: синхронный префикс до первого await выполняется прямо в вызывающем, а хвост после него — отдельный Execution Instance (TD-060a).

fire-and-forget-vs-awaited/dropped DCA1001/awaited нет
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    _ = DropAsync();          // fire-and-forget: join нет нигде
    await SaveAsync();        // выполняется целиком в вызывающем
    Dropped = "parent";       // пересекается с хвостом DropAsync
    Saved = "parent";         // упорядочено после SaveAsync
}

private async Task DropAsync() { await Task.Yield(); Dropped = "drop"; }
private async Task SaveAsync() { await Task.Yield(); Saved = "save"; }
when-all-synchronous-prefix/prefix нет/after-first-await DCA1001
await Task.WhenAll(StepA(), StepB());

private async Task StepA() { Prefix = "a"; await Task.Yield(); Suffix = "a"; }
private async Task StepB() { Prefix = "b"; await Task.Yield(); Suffix = "b"; }

Префиксы StepA и StepB выполняются по очереди в вызывающем, ещё до того, как WhenAll вообще получит задачи, — поэтому Prefix не гонится. Хвосты после await Task.Yield() — два параллельных Execution Instances, и Suffix гонится.

Атомарность — свойство операции, а не Protection

Замок, привязанный к потоку, и await

Monitor, System.Threading.Lock, Mutex и ReaderWriterLockSlim принадлежат потоку, который их взял, а продолжение после await может выполниться на другом потоке. Область такого примитива с await (или yield return) между захватом и освобождением получает partial, а не sufficient. SemaphoreSlim к потоку не привязан, поэтому await _sem.WaitAsync() … Release() в finally — достаточный Protection (semaphore-slim-capacity-one нет).

Самописные замки: обёртка прозрачна

Анализ никогда не распознаёт замок по имени или форме типа. Класс SimpleLock с методами Lock()/Unlock() без настоящей синхронизации внутри — не Protection (custom-lock-by-name DCA1001), как и SpinLock, который не входит в моделируемые примитивы (spin-lock-not-protection DCA1001). Коллекции: Collection Structure отдельно от ячеек

Для массивов, спанов и коллекций Access Path заканчивается Selector ячейки: [0], ["a"], [0..8] или [?]. Если бы у коллекции были только ячейки, доказанно разные ключи снимали бы любую пару — а это неверно в опасную сторону. Поэтому у каждой коллекции два вида Resources (ADR 0010): Collection Structure (количество, слоты, порядок; Access Path к самой коллекции) и Element Storage (Access Path плюс Selector).

dictionary-disjoint-keys-structuralDCA1001 на Collection Structure
public sealed class Ledger                   // AddSingleton<Ledger>(); два worker-а
{
    public Dictionary<string, int> Entries { get; } = new();
    public void AddFirst()  => Entries.Add("first", 1);
    public void AddSecond() => Entries.Add("second", 2);
}

Какие Resources трогает каждый распознанный член коллекции, записано в его модели операций (ADR 0010). Несколько неочевидных строк: Count и ContainsKey читают только Collection Structure; индексатор-get читает Collection Structure и ячейку; удаление пишет и ячейку, потому что переход «есть → нет» тоже можно потерять; Insert/RemoveAt у List<T> сдвигают соседей и пишут ячейку [?]; перечисление читает Collection Structure и все ячейки. HashSet, Queue, Stack и LinkedList моделируются так же, всегда с ячейкой [?].

Кроме Accesses к Collection Structure и ячейкам, куча хранит связи с объектами внутри коллекции. У словаря ключи и значения учитываются отдельно; новый список из существующей последовательности получает новый контейнер, но ссылки на прежние элементы. Вызов через IEnumerable<T> или интерфейс коллекции разрешается по точному типу receiver, если этот тип известен. Это проверяют CollectionElementStorageTests, DictionaryKeyStorageTests, InterfaceCollectionCallTests и ArrayProjectionModelMatrixTests.

У ConcurrentDictionary оба Resources атомарны: пары двух GetOrAdd нет, и перечисление во время изменения — определённое поведение (concurrent-dictionary-enumerate-while-mutate/concurrent-dictionary нет). Но последовательность атомарных вызовов не атомарна:

Guards двух Execution Instances можно связать между собой только если доказано всё сразу: Heap Region — ровно один объект на процесс (статик, DI singleton или аллокация, выполняемая не более раза), поле readonly или get-only auto-property, вне Construction его никто не пишет, и чтение идёт после Construction. Тогда IsPrimary ∧ ¬IsPrimary — UNSAT. Во всех остальных случаях значение принадлежит одному Execution Instance и снять пару не может. С неподдержанным предикатом (Name.StartsWith("x")) пара остаётся с пометкой в uncertainty (unsupported-guard-kept DCA1001).

Guard передаётся к Access по каждому пути от Execution Root отдельно (до 16 путей на Access; дальше Guards выше слияния отбрасываются с потерей точности, но не корректности). Условие вызывающего на значение аргумента ограничивает соответствующий параметр — только для параметров по значению и только для входного значения, не после переприсваивания.

Opaque Call: UnknownEffect

Opaque Call не считается «ничего не делающим». Его эффект — один Access вида UnknownEffect, который читает и пишет всё, что достижимо из receiver и аргументов, до глубины summaries и wildcard дальше. В процедуре конфликта он ведёт себя как запись. Но есть важные сужения, каждое из которых снимает огромный шум:

  • Объект одного Execution Instance (Owned, ThreadConfined) такой вызов только читает: вызов ничей Ownership не меняет. Это явное допущение модели анализа, а не гарантия поведения любой внешней библиотеки.
  • readonly-поле тоже только читается (кроме reflection), а то, на что оно указывает, получает эффект целиком.
  • Через receiver виден только тип, объявивший член: библиотечный член, вызванный на объекте из исходников (base-конструктор, унаследованный HttpContext), полей исходников не видит.
  • На Collection Structure thread-safe коллекции эффект атомарен, как её собственные члены.

Semantic Gap

Opaque Call становится Semantic Gap, только когда его UnknownEffect достаёт до изменяемого Heap Region с Ownership Escaped/Shared/Unknown, когда ему передан делегат, или когда его результат записывается в поле общего Heap Region. Вызов только со строками, числами и неизменяемыми типами Semantic Gap не бывает (reflection-primitive-args-no-gap нет Semantic Gaps). Виды Semantic Gap: reflection, dynamic, unresolved-dispatch (interface/virtual/delegate-вызов без известного объекта), model-gap (service locator с неконстантным типом) и unknown-library. Semantic Gap один на callee в пределах Process Scope. Их порядок в отчёте — Materiality: сначала число Execution Roots, потом число Heap Regions, потом число мест вызова, без общего «скора».

Классический пример, где Semantic Gap честно оставляет неопределённость, — Channel<T> (channel-handoff нет Findings): объект, прочитанный consumer-ом, с записанным producer-ом не связан, а запись в канал общего объекта видна как Semantic Gap в Coverage — неопределённость, а не безопасность.

Semantic Gaps видны в Coverage, uncertainty и confidence; AI-разрешение Semantic Gaps с повторным fixpoint не подключено. Known Call с Delegate Fate unknown-execution — другой случай: Library Model уже дала консервативный ответ о делегате, поэтому сам вызов не становится Semantic Gap.

Library Models: от JSON до эффекта в анализе

Когда код вызывает библиотечный метод, Roslyn знает его сигнатуру, но в загруженном solution обычно нет его тела. Library Model сообщает анализатору то, что нужно для поиска гонок: какие объекты метод читает и меняет, что возвращает и где запускает переданные делегаты. Например, у JsonSerializer.Serialize важно Deep Read аргумента, а у Enumerable.Where — отложенный вызов предиката при перечислении.

Library Model — исполняемые для анализатора данные. IrLowering прикрепляет её к операции call; summaries сохраняют её смысл; WholeProgram строит связи объектов и вызовов; ExecutionModel определяет Execution Instances; InterproceduralAccesses получает Accesses. Поэтому ошибка Library Model может менять Findings, даже если C#-код движка не менялся.

Идентичность — declaration id исходного определения метода, имя и версия сборки. Это позволяет различать перегрузки и generic-методы. Диапазон minimum включителен, maximumExclusive — нет. Library Model похожего метода в другой сборке не подходит. Член с телом в исходниках анализируется по телу; механизмы распознавания Execution Roots, Spawn Sites, синхронизации и коллекций имеют собственную семантику и не должны получать второй конкурирующий способ описания.

Прочитать одну запись целиком

Ниже самостоятельный файл в формате Library Model слоя project. Он описывает ту же перегрузку Where, что и built-in набор; копировать его в проект для обычного LINQ не требуется.

{
  "schemaVersion": 1,
  "assemblies": ["System.Linq"],
  "versions": { "minimum": "8.0.0.0", "maximumExclusive": "11.0.0.0" },
  "models": [
    {
      "member": "M:System.Linq.Enumerable.Where``1(System.Collections.Generic.IEnumerable{``0},System.Func{``0,System.Boolean})~System.Collections.Generic.IEnumerable{``0}",
      "effects": {},
      "result": "sequence(elements(arg:source))",
      "fates": {
        "predicate": {
          "fate": "iterator",
          "inputs": [["elements(arg:source)"]]
        }
      }
    }

}
  1. member выбирает конкретную перегрузку. В обозначении Roslyn двойной backtick указывает generic-параметры метода; это часть идентификатора.
  2. effects: {} не объявляет дополнительных прямых чтений или записей аргументов этой Library Model. Это не означает, что предикат ничего не делает.
  3. sequence(elements(arg:source)) создаёт абстрактную ленивую последовательность, элементы которой — те же объекты, что и у source.
  4. iterator относит Execution Instance predicate к месту перечисления результата.
  5. inputs содержит по одному списку возможных значений на параметр самого делегата. Предикат получает элементы source. Без этого описания анализ не знает, какие объекты пришли в его параметр.

Проектное переопределение и Model Lock

Команда может явно описать член как Opaque Call, например если не доверяет Library Model слоя built-in для своего использования. Настоящий пример находится в demo/.concurrency-hunter/models/demo.json: SerializeToUtf8Bytes объявлен как Opaque Call, а EqualityComparer<T>.Create описан через Holder. Такая запись меняет семантику вызова, а не скрывает его Finding.

Для группы перегрузок проектная запись может использовать шаблон вроде M:System.Text.Json.JsonSerializer.Serialize(*). ModelLock разворачивает его в точные declaration id для встреченной версии сборки и сохраняет в models.lock.json. При следующем анализе этой версии использует закреплённый список; новая версия получает отдельную строку. Удалённые шаблоны убираются из Model Lock, когда файлы Library Models удалось прочитать. Library Models и Model Lock предназначены для ревью и хранения в Git.

Некорректная запись даёт диагностику library-models: и не применяется. Это отличается от валидной записи opaque: true: отклонённая запись не обязательно отменяет Library Model слоя built-in. Для контроля смотрите known-call-built-in, known-call-project, opaque-by-project и диагностику Coverage.

Когда запускается делегат и куда попадают объекты

LINQ: создание запроса и его выполнение

linq-where-runs-on-enumerationDCA1002 · Hits
// Упрощённая форма demo-кейса. Filter зарегистрирован как singleton.
public sealed class Filter
{
    public int Hits;
    public IEnumerable<int> Matching;

    public Filter()
    {
        Matching = new List<int> { 1, 2 }.Where(x => { Hits++; return true; });
    }
}

// Action и worker перечисляют одну сохранённую последовательность:
foreach (var value in _filter.Matching) { }

Конструктор сохраняет последовательность и предикат, но не делает Hits++. Запись выполняется в action и worker при перечислении. Место Access в исходнике остаётся внутри конструктора; Execution Instance определяется перечисляющим. Это тот же принцип, что у пользовательского yield, применённый к библиотечному результату.

Library Models слоя built-in для LINQ описывают Enumerable-операторы с делегатами без comparer. Перегрузки с comparer рассматриваются как Opaque Calls. Where/Select и другие ленивые результаты сохраняют источники; терминальный оператор вроде Any вызывает делегат сейчас. Queryable с expression tree рассматривает выражение как данные, а не как немедленно исполняемый C#-делегат. Это не анализ выполнения запроса в БД.

Как работает команда generate

generate статически исследует один член библиотеки и классифицирует, где могут исполняться переданные ему делегаты. Это детерминированная часть продукта: она не вызывает AI, не скачивает пакеты и не исполняет исследуемую библиотеку. Написанный ею Driver — вход для анализа, а не запускаемый тест.

Точная граница текущей реализации

Команда выдаёт classified с Delegate Fates по параметрам либо reason отказа. Она ещё не создаёт полноценную запись models с effects, inputs, result, outputs и keeps. Hunt и metrics не вызывают генератор автоматически и не подхватывают его выход. Название ModelGenerator описывает компонент архитектуры; фактический выход задают GeneratedAnswer и GeneratedDocument.

Команда и входные данные

Пример запроса к установленному Google.Protobuf 3.21.9. Каталог scratch должен существовать, а пакет — уже находиться в локальном NuGet cache. У --member важны точные backticks и скобки, поэтому в PowerShell используйте одинарные кавычки:

& ./bin/win-x64/concurrency-hunter.exe generate --assembly Google.Protobuf --version 3.21.9 --package Google.Protobuf --framework net8.0 --member 'M:Google.Protobuf.MessageParser`1.#ctor(System.Func{`0})' --out ./scratch/parser-fate.json *> scratch/generate.log
Get-Content scratch/generate.log -Tail 50
Get-Content scratch/parser-fate.json

Без --package --version задаёт major версии framework-сборки; resolver выбирает установленный shared framework Microsoft.NETCore.App этого major. С --package это точная версия NuGet-пакета, а --framework задаёт платформу для выбора совместимого lib/. По умолчанию используется major runtime самого процесса. Resolver читает NUGET_PACKAGES, иначе %USERPROFILE%/.nuget/packages. Reference assembly из ref/ не годится: её сигнатуры есть, а реализации методов нет.

Код завершения 0 означает, что ответ записан; в нём может быть classified: null и причина отказа. Ошибка аргументов не пишет файл, исключение записи или выполнения даёт failure. GenerateCommand записывает только указанный --out и сам не создаёт его родительский каталог.

Путь одного запроса

  1. Найти implementation DLL. ImplementationAssemblies выбирает локальную сборку и зависимости, проверяет, что это не reference assembly, записывает assembly version, file version и MVID. System.Private.CoreLib намеренно отклоняется.
  2. Декомпилировать и получить Roslyn Compilation. LibraryCompilation использует встроенный ICSharpCode.Decompiler и создаёт деревья C# в памяти. Тела с ошибками компиляции превращаются в extern, затем выполняется повторная проверка, максимум три переписывания. Так они становятся обычными Opaque Calls движка. Ошибка декларации или оставшаяся ошибка делает библиотеку непригодной.
  3. Проверить область применения. Найти member по declaration id. EngineClaims отклоняет сборку, если её член уже принадлежит специальному recognizer движка: иначе такой вызов мог бы анализироваться по встроенной семантике вместо исследуемого тела.
  4. Синтезировать Driver. DriverSynthesizer подбирает типы и аргументы, создаёт пробные делегаты и объекты. Каждый Probe делает запись в своё отслеживаемое статическое поле. Driver содержит подготовку, вызов члена и перечисление результата; для потенциального Holder также создаёт вызовы его членов — triggers.
  5. Прогнать общий движок. ScopePipeline.Run получает две компиляции — библиотеку и Driver — и DriverRootProvider. Главный проход использует setup/call/enumeration Execution Roots. Он строит IR, summaries, heap, Execution Instances и Accesses. Pairing, Z3 и пользовательский отчёт генератору не нужны. Library Models слоя built-in для исследуемой сборки исключены, чтобы её extern-тела не получали готовые ответы.
  6. Классифицировать. FateClassifier сопоставляет записи Probes с Execution Instances и проверяет по heap, кто сохраняет делегат. Если получен Holder и существуют triggers, выполняется отдельный подтверждающий проход с ними. Запуск Probe в Task.Run, таймере или Unknown Execution, ошибка либо превышение лимита этого прохода расширяют ответ до unknown.
  7. Записать ответ. GeneratedDocument сериализует schema 1, identity запроса, classification/reason и диагностические сведения. CLI пишет UTF-8 без BOM с завершающим переводом строки.

Driver строится из сигнатуры, поэтому его сложность — отдельная часть продукта: receiver может требовать конструктора или фабрики, generic-параметр — удовлетворения constraints, интерфейс — пробной реализации. TypeShape различает immutable, delegate, коллекции, task и другие формы; ParameterKinds определяет, как переданный аргумент способен нести Probe. Классификация может относиться и к callback, переданному внутри объекта, а не только к параметру типа Func<>.

Почему одного наблюдения недостаточно

Допустим, Driver видит вызов callback() внутри библиотечного метода. Этого мало для invoke-now: библиотека могла ещё сохранить callback в поле и вызвать после завершения метода. И наоборот, отсутствие видимого вызова не означает, что callback никогда не запустится: его может вызвать фреймворк за пределами достижимых Execution Roots. Это Open-world Rule.

Что доказал анализ ProbeОтвет
Запись происходит только в собственном Execution Instance вызова; делегат нигде не сохранён для дальнейшего использования.invoke-now
Через результат доступен сохранённый делегат; соответствующий Probe выполняется при перечислении, в Execution Instance перечисляющего.iterator, если сигнатура допускает такую Delegate Fate.
Достижимость делегата доказана только через один возвращённый объект или receiver; подтверждающий проход не обнаружил другого способа вызова делегата.holder result или holder this
Probe не найден, есть несколько несовместимых способов запуска, callback вызван и сохранён, потерян результат либо нарушены условия точной Delegate Fate.unknown-execution

Набор наблюдавшихся triggers не считается полным списком методов, вызывающих callback. Основание Holder — достижимость делегата только через этот объект. Подтверждающий проход дополнительно проверяет, не отправляет ли доступный trigger callback в отдельный Execution Instance. Ошибка в сторону неизвестности снижает точность; ошибка в сторону более узкой Delegate Fate может скрыть настоящую гонку.

Как читать JSON-ответ

classified — отображение имени параметра в { fate, holder }. holder равен result, this или null. При отказе classified равен null, а reason называет причину. generation сохраняет сведения, нужные для воспроизведения:

  • implementation и framework — какую DLL и платформу действительно использовали.
  • missingDependencies, externBodies — что недоступно или потеряло тело при компиляции.
  • defaultedValues — какие аргументы Driver заполнил значением по умолчанию; setupWidened — где подготовка Probe сама исполнялась или уходила в Opaque Call.
  • refusals — почему для параметра отклонена более точная Delegate Fate; reachedBodies и seconds — размер Reachable Set и время.

Основные причины отказа: corelib, no-implementation, reference-assembly, library-does-not-compile, member-not-found, engine-recognized, driver-not-synthesized, not-a-candidate, body-does-not-compile, closure-bound, analysis-failed. Это ответ о границе анализа, а не доказательство отсутствия эффектов у библиотеки.

Компиляции декомпилированных библиотек повторно используются внутри процесса по пути implementation и набору зависимостей. Это локальная экономия работы генератора; кэша пользовательских Findings между Runs она не создаёт.

[HttpPost("delete")] public void Delete() => _log.Record("delete");

Место записи одно, пара — запись с самой собой. Occurrences — пары Execution Roots: 3 самопересечения и 3 пары разных actions, всего 6. Fingerprint Finding считается по правилу, содержащим символам обоих мест, форме Resource, видам операций и Protection Result, но без Execution Roots: четвёртый вызывающий не меняет Fingerprint, что позволяет использовать его как устойчивый ключ для будущего механизма Suppression. Чтение пользовательских Suppressions пока не реализовано. Меняется Fingerprint только при смене причины.

Глубокие пути и wildcard

Access Path ограничен глубиной 8. Более длинный путь сворачивается в Resource с wildcard ["*"] на Heap Region, с которого он начинается (deep-access-path-wildcard DCA1001 · Medium). Точное поле не установлено: компонент «Resource» в оценке падает с 25 до 10, поэтому типичный Finding с wildcard получает Medium, а uncertainty называет причину.

Правила, которые нельзя нарушать

Эти правила записаны в SPEC и ADR, но в коде их легко нарушить незаметно — одна правка в одном слое без соседнего. Перед каждым изменением движка стоит перечитать список.

  1. Unknown — не safe. Пару удаляет только доказательство. Недоступный решатель, таймаут, слитый контекст, Opaque Call, неизвестный компаратор снижают уверенность, но пару оставляют.
  2. Protection Result — самый опасный вердикт. sufficient только при общем объекте, совместимых режимах и удержании на всех путях. Никакого распознавания по имени или форме пользовательского типа.
  3. Happens-before только удаляет пары. Ребро без доказанной identity handle или без Join на всех путях не добавляется.
  4. Opaque Call не меняет Ownership. Объект одного Execution Instance он только читает, общий — читает и пишет.
  5. Текст AI не меняет анализ. MCP принимает Narrative, проверяет ссылки на evidence и рекомендации. Протокола принятия AI-фактов сейчас нет. Его будущие гарантии нельзя выдавать за поведение работающего кода.
  6. Library Model — часть семантики, а не косметика отчёта. Ошибочное effects: {}, потерянный результат или слишком узкая Delegate Fate способны скрыть гонку. Проверяйте и JSON-контракт, и путь объектов через весь движок.
  7. Open-world Rule. Генератор не вправе считать делегат безопасным только потому, что не нашёл его вызов. Для точной Delegate Fate нужны и место выполнения делегата, и доказательство того, кто сохраняет делегат.
  8. Одна пара мест Accesses — один Finding. Execution Roots — Occurrences; Fingerprint не зависит от Execution Roots.
  9. Никакого декартова перебора. Новые виды Resources встраиваются в Buckets CandidateIndex.
  10. Analysis не ссылается ни на что. Roslyn-специфичное остаётся во frontend, граница — IR.
  11. Ожидания demo пишутся руками до реализации. Подтверждённый false positive или false negative получает минимальный demo-кейс.
  12. Детерминизм. Все порядки обхода и сортировки ordinal и стабильны: demo-гейт требует одинаковый результат на трёх прогонах.
  13. Документация описывает текущее состояние. История изменений — только в CHANGELOG; в README, SPEC и этом руководстве пишется, как работает сейчас.

Как доработать: частые задачи

Новый demo-кейс

  1. Один файл demo/Demo.Web/Cases/<PascalName>.cs, один namespace Demo.Web.Cases.<PascalName>. Если нужны регистрации сервисов или endpoints, добавьте метод Add<Case>() или Map<Case>() и вызовите из Program.cs; controller actions обнаруживаются через MVC. Не связывайте кейсы общими сервисами.
  2. Кейс фазы не содержит конструкций поздних фаз, если они не его предмет: иначе Confidence Label сдвинется в поздней фазе, а запись ожиданий переписывать нельзя.
  3. Если нужна пара, которая не пересекается сама с собой, пишите в двух BackgroundService, а action пусть только читает.
  4. Запись в expected-findings.json (kebab-имя файла как id) и строка в таблице своей фазы в SCENARIOS.md — до изменения движка.

Новый Execution Root

  1. Один класс IExecutionRootProvider: распознавание по ExactSymbols (символ + диапазон версий), ExecutionRootDescriptor со стабильным id, InstanceBindings и InvocationPolicy.
  2. Регистрация в BuiltInProviders.Create().
  3. Случаи в ProviderFixture с именами Provider_Scenario_ExpectedOutcome и сквозной тест Execution Root → Finding → отчёт. Шаблон — SyntheticProviderEndToEndTests. Ядро не меняется.

Добавление Library Model

  1. Зафиксируйте точный член и версию сборки. Разберите поведение библиотеки: аргументы, result, ref/out, сохранённые объекты и каждый delegate-параметр. Если формат не выражает поведение, оставьте вызов как Opaque Call.
  2. Для Library Model из поставки плагина измените соответствующий Core/Providers/LibraryModels/BuiltIn/*.json; для конкретного приложения добавьте JSON в его .concurrency-hunter/models/. Сверьте запись с LibraryVocabulary и примером из demo.
  3. Добавьте contract-тест против реального символа и тест движка: он должен проверить не только исчезновение Semantic Gap, но и сохранение ожидаемого конфликта. Для LINQ особенно важны момент перечисления и Aliases элементов.
  4. Проверьте конфликт с Library Model слоя project, другую перегрузку и версию вне диапазона. Для built-in набора проверьте эталонный список Providers/BuiltInTable.txt через LibrarySemanticsTableTests.

Изменение генератора

  1. Сначала локализуйте стадию: DLL и зависимости → компиляция → Driver → общий pipeline → Delegate Fate. ModelGenerator.Trace предоставляет Driver и результаты проходов тестам; обычный generate выдаёт только JSON-ответ.
  2. Добавьте минимальную библиотеку в тестовой fixture и проверьте опасный вариант: callback вызывается сразу и сохраняется, уходит в Task.Run или достижим в обход Holder.
  3. Запустите тесты соответствующего компонента, FateMatrixTests и проверки Unsafe Narrowing. Затем model evals на установленных пакетах, если правка затрагивает их ответы.
  4. Если причина лежит в IrLowering или WholeProgram, исправление влияет и на пользовательский код. Добавьте тест обычного анализа; не дублируйте логику движка внутри генератора.

Новая конструкция C#

  1. Ветка в LowerValue или LowerTop; новая цель присваивания — LowerStore, адресуемая или RMW-цель — LowerAddress и TryLocation.
  2. Каждое новое определение локальной переменной — в SsaPlan.Scan в том же порядке вычисления, иначе лоуеринг бросит «No SSA definition was planned».
  3. Новый вид операции: запись в IrOperations.cs, ветка в IrPrinter (тест Every_operation_kind_has_a_text_form упадёт без неё), правила в IrValidator, обработка в MethodSummaryBuilder, ReachableSet, HappensBefore и InterproceduralAccesses; подумайте о повышении IrSchema.VERSION.

Перечисление в WholeProgram.cs и создание через Region(); затем switch Ownership в ExecutionModel, IsContainerWide/SharedRoots, CreationExecutions, AssignRegionExecutions (если Heap Region конструируется), IsInternal, SingleObjects. Проверьте все места, где identity разбирается строкой.

Границы, важные для следующего разработчика

  • Связать генератор с Library Model — отдельная задача. Ответ classified содержит место выполнения делегата; полноценной Library Model нужны ещё аргументы делегата, эффекты, result, outputs и keeps. Простого копирования JSON недостаточно.
  • Task-результаты требуют согласования контрактов. Генератор рассматривает ожидаемый T из Task<T>/ValueTask<T>. Проверка Library Models в JSON работает с объявленным return type. Кроме того, передача объектного результата через await имеет ограничения в куче; генератор расширяет такие ответы до unknown, когда не может доказать нужные связи.
  • Точность и скорость связаны. Декомпилированная библиотека может дать большой Reachable Set. Генератор проверяет предел 1500 тел после построения этого множества, до summaries и кучи. Это не таймаут и не ограничение затрат самой декомпиляции или reachability.
  • План и эксперимент не равны реализации. Исследование Library Models и исследование производительности полезны для продолжения работы; поведение продукта подтверждают соответствующие исходники и тесты. Детали открытых вопросов находятся в SCENARIOS.md.

Как найти причину пропущенного или лишнего Finding

Начните с минимального C#-примера и ожидаемого результата, сформулированного независимо от анализатора. Затем ищите первый слой, где исчезает нужный факт или появляется неверное доказательство. Изменять confidence или renderer ради исправления пропуска слишком поздно: они получают уже готовые пары.

ВопросЧто смотретьТипичная причина
Программа попала в анализ?Проекты и diagnostics в Coverage, ProcessScopes, Execution Roots и DI.Проект не загрузился, нет провайдера Execution Roots, регистрация не поддержана.
Нужное тело достижимо?ReachableSet, lowered-not-reached, outside-lowered-set, сообщения lowering:.Пропущен неявный вызов; неверный dispatch; тело не удалось опустить.
Операции сохранились?IrPrinter, load/store/call и provenance.Потеря receiver, индекса или RHS; getter/setter не вызван; ссылка потеряла адрес.

Для лишнего Finding ищите конкретное доказательство, которое должно убрать пару. Для пропуска проверьте наличие каждого Access до pairing. После исправления оставьте минимальный регрессионный тест и demo-кейс, если это подтверждённая ошибка анализа. Снижение числа Findings без объяснения изменения Coverage не является доказательством улучшения.

Словарь

Термины руководства по алфавиту с объяснениями по-русски. Пометки «не …» указывают названия, которые нельзя использовать вместо соответствующего термина.

ТерминЗначение
AccessОдна операция над Resource вместе с Execution Instance, удерживаемым Protection и Guard.
Access PathПуть поле за полем от Heap Region до места в памяти. Последний шаг в массив или коллекцию задаётся через Selector.
Atomic OperationОперация, которую платформа выполняет неделимо над одним местом: Interlocked, Volatile, volatile. Свойство операции, а не Protection.
BucketЯчейка индекса Candidates: Accesses одного Process Scope к одному Resource.
CandidateПара Accesses, прошедшая дешёвые фильтры.
CFG (Control Flow Graph)Граф возможных путей выполнения кода внутри метода. Узлы — блоки последовательных инструкций; рёбра — переходы между ними, в том числе при ветвлении, повторении цикла и исключении. Например, у if (ready) Save(); Log(); есть путь через Save() и путь сразу к Log(). Анализ использует CFG, чтобы проверить, может ли операция повториться и выполняется ли ожидание задачи или удерживается ли замок на всех нужных путях.
Collection StructureСобственная форма коллекции (количество, слоты, порядок) — отдельный Resource от ячеек.
Confidence LabelHigh (80+), Medium (55–79), Low. Не severity: severity — отдельная оценка последствий.
ConstructionРабота конструктора или type initializer. Её обращения к собственному объекту не образуют пар, пока объект не опубликован; остальное принадлежит Execution Instance, который её запустил.
DeadlineПредельный срок Run: 30 минут от его старта.
Deep ReadЧтение всего, что достижимо из аргумента.
Delegate FateГде исполняется переданный делегат: сейчас, при перечислении, через Holder, в startup или в Unknown Execution. Library Model в JSON и выход генератора поддерживают разные подмножества этих вариантов.
DriverСинтезированная программа для статического исследования одного члена. Генератор анализирует её, не исполняя.
Element StorageЯчейки коллекции и ссылки на объекты в них. Для словаря ключи учитываются отдельно от значений.
Execution InstanceОдин логический запуск работы из Execution Root или Spawn Site; не поток ОС. (не thread, request, task)
Execution RootТочка, откуда фреймворк или рантайм начинает независимый Execution Instance. (не entry point, handler, thread)
FindingПравило, Resource и пара мест Accesses.
Finding GroupНабор Findings с одним правилом и одним Resource; к нему AI пишет общий Narrative.
FingerprintСтабильное имя Finding между прогонами, без Execution Roots.
Fire-and-forgetВызов, возвращающий задачу, чей handle ни на одном пути не доходит до ожидания.
Gap PacketТермин SPEC для будущего вопроса к AI о Semantic Gap; текущие MCP-инструменты таких пакетов не выдают.
GuardУсловие пути, при котором выполняется Access. Два Accesses с несовместимыми Guards не встречаются. (не Protection, lock)
Happens-beforeДоказанный порядок двух событий: путь через Spawn Site, Join, продолжения и startup внутри одного Instance Tree.
Heap RegionИдентичность объекта или множества объектов: место аллокации с контекстом, статика, DI-экземпляр. (не object, instance)
HolderОбъект, который хранит делегат. Отличается от Kept Object связями в анализе и правилами вызова делегатов.
Inferred FactТермин SPEC для проверенной гипотезы AI. Приём таких фактов и их применение к анализу пока не реализованы.
Instance TreeExecution Root, который запускается не более раза и не пересекается сам с собой, вместе с порождёнными из него однократными Execution Instances. Единственное место, где путь Happens-before считается доказательством.
JoinТочка, которая выполняется только после завершения другого Execution Instance, доказанная на всех путях для handle именно этого Execution Instance. WhenAny, ожидание с таймаутом, event-ожидание и Dispose() — не Join.
Kept ObjectОбычный объект, который библиотека сохраняет и отдаёт другим вызовам. Передаётся как данные; его нельзя смешивать с Holder, который хранит делегат.
Known CallВызов без тела, описанный Library Model для точного члена и версии.
Late ResponseОтвет AI, пришедший после Deadline. Записывается как late и не применяется.
Library ModelОписание поведения члена библиотеки. Происхождение сохраняется в данных анализа.
Library SequenceЛенивый результат библиотечного вызова. Хранит источники и делегаты, а исполняет их тот, кто перечисляет результат.
MaterialityПорядок Semantic Gaps по числу Execution Roots, Heap Regions и мест вызова.
Model LayerСлой, из которого берётся Library Model. Реализованы built-in и project; project имеет приоритет.
Model Lockmodels.lock.json: фиксирует, в какие точные declaration id развёрнут шаблон перегрузок для данной версии сборки.
NarrativeТекст AI к Finding Group.
OccurrenceПара Execution Roots, которой достигается Finding.
Opaque CallВызов без тела, для которого нет подходящей Library Model или который Library Model слоя project явно оставила как Opaque Call. Получает Unknown Effect.
Open-world RuleОтсутствие наблюдаемого вызова не доказывает, что callback не запустят извне.
OwnershipOwned, ThreadConfined, Escaped, Shared или Unknown — с цепочкой доказательств.
ProbeДелегат или объект с отслеживаемой записью, используемый в Driver.
Process ScopeИсполняемый проект вместе с проектами, которые он загружает. Статик в двух Process Scopes — два объекта. (не solution, app)
ProtectionСинхронизатор и режим, удерживаемые на всех путях к Access.
Protection ResultРезультат проверки синхронизации для пары Accesses: sufficient, partial, different-identity, incompatible-mode, unprotected.
Reachable SetТела методов, достижимые из Execution Roots и Spawn Sites. Только они опускаются в IR и считаются в Coverage.
Report BundleФайлы отчёта: report.md, findings.json, run-metadata.json.
ResourceHeap Region плюс Access Path — единица, по которой сравниваются Accesses. (не shared state, variable)
RunОдин запуск команды от run_start до Terminal Status. (не scan, session, job)
SelectorПоследний шаг Access Path в массив или коллекцию: константа, символическое выражение, диапазон или неизвестно.
Semantic GapНеразобранный вызов, который трогает общее изменяемое состояние или получает делегат.
ServerАнализатор за MCP: хранит состояние Run и Deadline, сам AI не запускает.
SkeletonЧасть отчёта, которую Server пишет сам.
SkillИнструкция для агента хоста, единственный оркестратор Run.
Spawn SiteВызов в пользовательском коде, начинающий новый Execution Instance из текущего. (не fork, background call)
SSA (Static Single Assignment)Форма представления кода, в которой у каждой версии переменной ровно одно место присваивания. Например, x = 1; x = 2; условно превращается в x1 = 1; x2 = 2;. В месте слияния ветвей запись φ (phi) связывает новую версию со значениями из входящих ветвей: используется значение той ветви, по которой пришло управление. Так анализ отслеживает происхождение значений и зависимости между чтениями и записями; это не запрет изменять переменные в исходном C#-коде.
SuppressionПланируемое решение пользователя скрыть Finding с обязательной причиной. Сейчас пользовательские Suppressions не применяются; не путать со счётчиком защищённых пар suppressed.
Terminal StatusCompleteWithFindings, CompleteClean, Incomplete, Failed. Это статусы готового отчёта, а не внутренние состояния RunRegistry.
Unknown EffectЭффект Opaque Call: «может прочитать и записать всё, до чего достаёт». Конфликтует как запись.
Unknown ExecutionExecution Instance для работы, у которой анализ не может установить конкретного инициатора: перечисление сбежавшего итератора или вызов делегата, отданного Opaque Call. Пересекается со всем в своём Process Scope, включая себя.
Unsafe NarrowingОтвет, который допускает меньше эффектов или Execution Instances, чем реальное поведение.
