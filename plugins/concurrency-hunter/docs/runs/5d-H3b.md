# 5d run H3b

## Правило identity handle

R1: когда один регион handle обозначает несколько исполнений одного дерева экземпляров,
handle доказан как исполнение, которое само ожидающее исполнение запустило прямо или,
для задачи async-вызова, через вызванный им пробрасывающий член, только при выполнении
всех условий: каждое значение handle на каждом пути к ожиданию происходит от такого
вызова-запуска в ожидающем теле; ни один обычный или исключительный путь от вызова до
ожидания не проходит через `await`, включая прежнее прохождение самого ожидания;
у ожидающего исполнения ровно одна запись запуска среди исполнений региона в дереве.
Иначе ни одно из исполнений региона не доказано. Для единственного исполнения региона
сохраняется прежний ответ. Определение записано в SPEC TD-067, ссылки — в TD-060 и TD-065.

Выбор сосредоточен в одном доказательстве handle в `HappensBefore`: его ответ получают
потребители join, в том числе выбор исходной задачи async-вызова через `TaskForwarders.Source`.
Прямой async-вызов и вызов пробрасывающего члена подчиняются тем же условиям, что задача,
поток и таймер. Ожидание не читается как ожидание всех исполнений региона; запуск до
приостановки и ожидание после неё в этом случае не доказываются.

Пять фактов `HandleExecutionRuleTests` наблюдают кадры доказательства своего прохода:
собственный запуск в одном участке тела принят; приостановка между запуском и ожиданием,
повторный `await` во внутреннем цикле, повтор после пойманного исключения и чтение handle
из поля отвергнуты с причиной `source`. Исходный положительный факт был красным до
исправления и зелёным после него (`scratch/h3b/rule-red.log`, `rule-green.log`).
Отдельная проверка прямого и проброшенного async-вызова с приостановкой и без неё показала
два ошибочных принятия до исправления общего выбора; после исправления прошли 15 выбранных
тестов (`scratch/h3b/task2-async-red.log`, `task2-async-green.log`).

`HandleExecutionMatrixTests` содержит 66 клеток и три факта: проверку состава, пустого
списка `Wider` и точного ответа каждой клетки. Оси запуска — `Task.Run`, `StartNew`, поток,
таймер, async-вызов и пробрасывающий член; оси пути — один участок тела, промежуточный
`await`, внутренний цикл, пойманное исключение, поле, параметр и возврат другого вызова;
формы ожидания — `await` и блокирующая. Поток проверяется только блокирующим ожиданием,
таймер — только `await DisposeAsync`; возврат другого вызова не добавляет отдельной
клетки async-вызову и пробрасывающему члену. Блокирующий повтор сам приостановки не создаёт.
Каждая клетка наблюдает две работы одного дерева с одним происхождением и разными
родителями и проверяет принятый join либо отказ `source` в кадрах нужного исполнения.
Список `Wider` пуст; итоговый факт всех клеток прошёл (`scratch/h3b/task3-exact.log`).

### Первая попытка записи и повтор

Первая попытка (`scratch/h3b/task4-baseline-record.log`) завершилась с кодом 1:
Core — 17073 Passed, 2 Failed, 40 Skipped; CLI — 173 Passed, 1 Failed, 0 Skipped.
Скрипт отказался записывать красный прогон: `Refusing to record a baseline from a run that
failed: dotnet test exited 1. Fix the run, then record.` Базис тогда остался прежним.

Остановка была вызвана новым отпечатком обычного demo `b685872d760f90d5` и отсутствием
тройки записей (`b7923638effff8ea`, `DCA1002`, High) в admitted. E2E также получил
`generated-in-run 3` вместо 0 и при очистке `Access to the path 'Common.Mcp.dll' is denied.`
Builder остановился, не меняя движок, ожидания, снимки или приёмку.

Причина трёх сбоев — устаревший `bin/win-x64/concurrency-hunter.exe`: он был опубликован
2026-11-12 в 17:13, до изменений движка этого рана. `PublishedExecutableEndToEndTests`
запустил сервер с версией генератора, отличной от версии записанных моделей demo.
Он сгенерировал три члена (`generated-in-run 3`) и 2026-11-13 в 00:03:38, во время набора,
перезаписал `demo/.concurrency-hunter/models/generated/Google.Protobuf/3.30.2/601a02d3-9487-45ce-a28b-99b5cb103efd.json`
со старым `generator` `4f608649052793f8868552bbdbeee6f32b5b5931cd775019621e0869445aa161`.
Последующие прогоны demo читали этот файл как модель другой версии генератора,
то есть без её ответов. Это дало лишний отпечаток обычного demo и потерю тройки admitted,
перечисленные выше.

Перед повторной задачей executable был заново опубликован
(`scratch/h3b/repair-publish.log`), а модели demo записаны и прочитаны повторно
(`scratch/h3b/repair-record-demo-models.log`). Во всех пяти файлах восстановлен
`generator` `237825e2038faad6e461abb329a96888144626af1b399f015fb8a30540d27762`;
ответы сохранились. Так устранены все три сбоя первой попытки.
После этой подготовки отдельные тесты снимков и полный прогон записи базиса прошли;
оба прежде падавших факта Core и E2E стали Passed. Core: Failed 2 → 0, Passed
17073 → 17075; CLI: Failed 1 → 0, Passed 173 → 174. Это изменение исходов тех же
трёх тестов, а не ослабление проверки или удаление случая. В повторной задаче код движка,
находки и ожидания не исправлялись.
Успешная проба demo сохраняет тройки записей и только разрешённые 16 отпечатков остатка.
