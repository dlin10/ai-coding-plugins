# 5g run E-scale — nopCommerce и OrchardCore до terminal status без генерации

## Причина

Замер 5g run E0 ([#430](https://github.com/dlin10/ai-coding-plugins/issues/430),
[`5g-E0-corpora.md`](5g-E0-corpora.md)) не довёл ни nopCommerce, ни OrchardCore до terminal status
с `metrics --generation off`: nopCommerce остановлен по сроку в модели исполнений scope `Nop.Web`
(`AssignRegionExecutions`) после 60–68 минут решения кучи, OrchardCore — сторожем по commit 58,5 ГБ
на сборе доступов. Без terminal status раны E1–E6 не видят на этих корпусах ни находок, ни gaps.
Ран [#441](https://github.com/dlin10/ai-coding-plugins/issues/441) выносит из фазы 7 только то,
без чего ран на них не кончается: модель исполнений `Nop.Web`
([#442](https://github.com/dlin10/ai-coding-plugins/issues/442)), сбор доступов OrchardCore
([#443](https://github.com/dlin10/ai-coding-plugins/issues/443)) и решение кучи `Nop.Web`
([#444](https://github.com/dlin10/ai-coding-plugins/issues/444)). Цели PRD 6.1 по скорости
остаются фазе 7.

Каждая задача — своя сессия и свой рабочий каталог; #442 и #443 шли параллельно, #444 идёт после
#442. Раздел каждой задачи пишет её сессия.

## Как мерили

Как в E0 (раздел «Как мерили» записи E0): Release-сборка `src/ConcurrencyHunter.Cli` из рабочего
каталога задачи, пределы по умолчанию (depth 8, contexts 16, scc 16), корпуса на тех же коммитах.
Корпусный ран на машине один: перед ним сессия атомарно создаёт
`scratch/corpus-run.lock` основного checkout'а (`New-Item -ItemType File`) и удаляет его в конце;

(сумма `TotalProcessorTime` всех процессов за 5 с). Сторож — копия `scratch/e0-corpora/nop/guard.ps1`,
которая к тому же снимает стек (`dotnet-stack report`) каждые 3 минуты: commit больше 58 ГБ или
срок 4 часа от старта — стек и остановка по точному PID.

Гейты каждой задачи: тест, закрепляющий изменённое поведение, `build/check-test-baseline.ps1`
с `CH_ESHOP_ROOT=C:\Dev\eShopOnContainers` (снапшот eShop прогнан, не пропущен) и
`build/record-demo-models.ps1 -Check` с выходом 0.

## #442 — модель исполнений `Nop.Web`

### Изменение

Хвост `ExecutionModel+Builder.AssignRegionExecutions` распространял исполнения по DI-рёбрам
родитель → ребёнок хаотичным fixpoint: каждый круг для каждого ребра копировал всё множество
родителя (`Executions(parent).ToArray()`) в ребёнка, пока что-то менялось. Цена — число кругов,
умноженное на сумму множеств по всем рёбрам, и каждый круг заново хеширует все строки.

Теперь распространяется только прирост: регион, чьё множество выросло, встаёт в очередь с тем, что
он получил, и отдаёт детям только это. Каждое исполнение проходит каждое ребро один раз. Результат —
та же наименьшая неподвижная точка `ребёнок ⊇ родитель` над теми же начальными множествами.
Набор ключей `_regionExecutions` тот же: проход, строящий рёбра, создаёт запись родителя и ребёнка
каждого ребра в том порядке, в каком их создавал первый круг прежнего цикла (все потребители читают
через `GetValueOrDefault(…) ?? []`, так что пустая запись от отсутствующей для них и не отличается).
Порядок вставки внутри множеств меняется; модель от него не зависит (`CanonicalizeWalk`,
`CanonicalOrderTests`).

Тест `OwnershipAndConstructionTests.Transient_resolved_through_a_chain_of_transients_runs_in_every_execution_that_resolves_the_chain`
написан до изменения и прошёл на прежнем коде: transient `Leaf` за цепочкой `Top → Middle → Leaf`
и за `Cache → Middle → Leaf` строится в двух корнях `TopController` и в исполнении конструкции
синглтона `Cache`. Без постановки ребёнка в очередь тест падает (0 корней вместо 2).

темпу около одной секунды CPU в секунду (один рабочий поток).

Сравнение с E0: там модель исполнений за 1 ч 50 мин не кончилась на прежнем fixpoint, здесь за 2 часа
не кончилась на worklist. Время уходит не на повторные круги, а на сами добавления в множества
детей. Из 207 образцов модели исполнений (11:23–12:55, `stack-*.txt` сторожа и `watch/`) самый
внутренний кадр рабочего потока — хеш строки `OrdinalComparer.GetHashCode` в 99,
`HashSet.AddIfNotPresent` в 70, сравнение строк `SpanHelpers.SequenceEqual` в 16, `CheckCancellation`
в 15 и сам `AssignRegionExecutions` в 7. Значит, на `Nop.Web` велико уже само произведение «исполнения × DI-рёбра»
(или сама неподвижная точка), и порядок обхода его не сокращает. Сколько пар регион × исполнение
в итоге, ран не дал: `metrics` их не выводит, а снапшот кучи процесса не снимался. Чтобы модель
исполнений `Nop.Web` кончилась, нужно менять представление (например, общее множество исполнений
на компоненту сильной связности DI-графа или счёт исполнений региона по запросу) — это изменение
модели вне #442, и решение за владельцем.

### Изменение

- `DiIndex.UnresolvedUncertainties`: текст каждой unresolved registration строится один раз на scope;
  его делят `DiIndex.Resolve` и сборщик доступов.
- `ExecutionCollector.BindingEvidenceOf` хранит binding evidence по региону в словаре, общем для
  сборщиков всех исполнений scope; перебор (`BindingEvidenceScan`) идёт один раз на DI-регион.
  Сборщики исполнений идут один за другим (как общий `StringPool`), так что словарь без блокировок.

Тест `AccessExtractionTests.Accesses_to_one_container_object_share_its_binding_evidence_and_uncertainties`
написан до изменения и падал на прежнем коде (`Assert.Same() Failure`): два действия контроллера —
два исполнения; их доступы к одному синглтону делят один и тот же binding evidence и одну и ту же
строку неопределённости от неразрешённой регистрации.

Сознательно не тронуто (на снимке 2 это вторые по величине статьи и вторая горячая точка CPU):
хеширование `ConstructionQuery` в `Localities`, строки `StoragePath.Slot` (603 МБ), словари
`HeldProtections` и code flow на каждый доступ, список неопределённостей на каждый доступ (строки в
нём теперь общие, сам список — нет). Это состояние каждого доступа, а не повторы на scope.

## #453 — исполнения регионов битами

### Изменение

`ExecutionModel+Builder._regionExecutions` хранил для каждого региона `HashSet<string>` id
исполнений, и распространение по DI-рёбрам (#442) хешировало строку на каждое добавление. Теперь
множество региона — биты (`ulong[]`) над той же нумерацией исполнений `ExecutionIds`, что уже
служит обходу (`WalkNode.Executions`). Номера раздаются при первом запросе — теперь уже в
`AssignRegionExecutions`, а не только в `Seed`. Распространение — тот же worklist на приросте, но
прирост и объединение идут словами по 64 исполнения (`Bits.UnionWith` с накоплением добавленного).
Потребители (`Build` → `Entry`, `CanonicalizeWalk`, `StartupTypeInitializers`, `CreationExecutions`,
`OnceInstances`) читают исполнения региона через `RegionExecutions` в порядке номеров; модель от
порядка не зависит (`CanonicalOrderTests`).

Новый счётчик `regionExecutionPairs` (`ExecutionAnalysis.RegionExecutionPairs`, в counters
стадии исполнений и в исключении отмены) — число пар «построенный регион × исполнение, в котором
идёт его конструкция». Тест `EngineCounterTests.Region_execution_pairs_are_counted` сверяет его с
числом различных объектов во входах `Construction` модели и требует, чтобы оно было больше нуля.

## #444 — решение кучи `Nop.Web`

### Диагноз

Разобраны две трассы CPU рана #453 в куче `Nop.Web`: `scratch/e-scale/heap-trace/heap-1-1724.nettrace` и
`heap-2-1759.nettrace` основного checkout, по 5 минут, на 12-й и 47-й минутах кучи, профиль

стеке которого есть `WholeProgram.Solve`. Около 62–64 % этих образцов кончаются в `PollGCWorker`. Это
не работа, а место, где поток стоит, пока среда остановлена: ради GC она стояла 6,8 % и 6,2 % wall,
ради самого сэмплера 17,8 % и 14,0 %. Такие образцы отнесены к кадрам над ними, то есть к месту,
которое аллоцирует или крутит цикл.

Горячий путь: `Propagate` → `ProcessOrSkip` → `Process` → `Call` → `CallTargets` → `Dispatch` →
`DispatchCallees` / `ImplementationsWithoutBody` → `ProgramIndex.Implementation`.

|---|---:|---:|
| Образцов | 136 868 | 96 723 |
| `ProgramIndex.Implementation` | **50,1 %** (через `ImplementationsWithoutBody` 37,5 %, через `Dispatch` 12,5 %) | 24,8 % (17,7 % / 7,0 %) |
| `SubstitutionText` | 7,3 % | **27,1 %** |
| `EligibleReceivers` / `TypeSafety.CannotBe` | 4,2 % / 2,9 % | 15,0 % / 13,2 %, из них собственное время `DefinitionOf` 11,7 % |
| `Bind` | 20,9 % | 10,5 % |
| `Dirty` | 1,2 % | 5,3 % |

Что это за работа:

- `ProgramIndex.Implementation` на каждый вызов заново шёл по цепочке базовых типов runtime-типа. Для
  вызова через интерфейс он на каждом типе цепочки ещё фильтровал interface mappings
  (`Where(...).ToArray()`) и подставлял аргументы. Индекс программы при этом не меняется, а решатель
  на каждом проходе неподвижной точки спрашивает одни и те же тройки (runtime-тип, метод, интерфейс)
  для каждого получателя каждого вызова.
- `SubstitutionText` строил часть ключа экземпляра цепочкой `OrderBy` → `Select` → `string.Join` с
  интерполяцией на каждую привязку. Его зовут `Bind` и `Instance`.
- `CannotBe` на каждого получателя заново разбирал строку declaring type (`DefinitionOf`,
  `NullableValueType`), хотя у вызова она одна.

GC: куча 16,1–17,5 ГБ, из них gen2 12,9–13,5 ГБ. За 5 минут трассы 1 прошло 3544 сборки gen0 и 139
сборок gen1, трассы 2 — 4603 сборки gen0. Паузы GC заняли около 30 с из 300.

### Изменение

- `ProgramIndex.Implementation`: обход (`Dispatched`) делается один раз на тройку (runtime-тип, метод,
  интерфейс), результат лежит в `ConcurrentDictionary` индекса. Допуск `CallSiteAdmission.Admits`
  по-прежнему решается на каждый вызов для найденного метода, потому что зависит от ребра (origin,
  route, call). Прежний код тоже проверял допуск только у итогового метода, и в ветке класса, и после
  перехода по interface mapping, так что ответ для каждого ребра тот же.
- `WholeProgram+Solver.SubstitutionText`: одна сортировка массива привязок и один `StringBuilder`;
  строка получается та же.
- `TypeSafety.CannotBe`: `DefinitionOf` типа и `NullableValueType` declaring type запоминаются в
  словарях экземпляра, как уже `_supertypes`.

Множества points-to, цели вызовов и регионы не меняются: это кеши над неизменными данными и та же
строка ключа.

Тест `ProgramIndexTests.Dispatch_walk_is_shared_while_each_edge_decides_its_admission` использует
иерархию `Derived : Base : I`. Вызовы `Base.M` и `I.M` идут по очереди: из проектного кода (допуск
отказывает, ответ null), из библиотечного (допуск пускает, ответ `Derived.M`), снова из проектного
(null) и без допуска. Кеш, который запомнил бы отказ или допуск вместе с обходом, этот тест не
проходит. На прежнем коде тест проходит: он закрепляет поведение, а не воспроизводит ошибку.

## #455 — дубликаты входов исполнения

### Изменение

`ExecutionModel+Builder.Entry` проверял, есть ли вход в списке исполнения, через
`entries.Contains(entry)` — линейным проходом с `ExecutionEntry.Equals`. Теперь вход сначала
добавляется в множество `_entered` пар «исполнение × вход», и в список он попадает, только если
`Add` вернул true. Порядок списка тот же: вход добавляется в конец при первом появлении, как и

длинным. Изменение хеширует вход один раз на вызов `Entry`, столько же, сколько уже хеширует
`_entryWalks`, и теперь это основная цена `Entry`.

## #457 — вход конструкции один на регион (ADR 0039)

### Изменение

Вход конструкции теперь заводится один раз на пару «экземпляр конструктора × регион», а не на каждое
исполнение региона. `ConstructionEntry` несёт сам вход и биты исполнений региона — тот же массив, что
держит `_regionExecutions`. После `AssignRegionExecutions` в этот массив никто не пишет, поэтому он
общий и не копируется. Остальное:

- Обход в первом круге засевает каждый вход конструкции сразу для всех его исполнений.
- `Constructions` читает взятые входы как множества исполнений. Внешние входы в конструкцию он
  считает один раз на узел: объекты, внутри которых не начинается ни один вход, получают объединение
  всех множеств, а остальные — объединение прочих групп.
- `ExecutionAnalysis.Entries` — представление, а не словарь списков. На каждый запрос оно собирает
  собственные входы исполнения и входы конструкций его регионов в том же каноническом порядке и
  ничего не хранит. В ключах есть и исполнение, у которого только входы конструкций. Читатели
  `Entries` не менялись.
- Контрольная точка `constructions` в конце `Constructions`. Счётчики `entries` показывают новые
  структуры.

Тест `ConstructionEntryListsTests.Construction_entry_is_one_object_every_execution_of_its_region_lists`
зовёт `ExecutionModel.EntryLists` напрямую. Он проверяет:

- вход конструкции — один объект в списках всех исполнений его региона;
- место входа в каноническом порядке;
- ключ для исполнения только с входами конструкций;
- что списки не хранятся.

## #459 — `Ownership` на битах

### Изменение

В ране #457 `Builder.Ownership` шёл больше 35 минут и не кончился. Все образцы попадали в
`Attributed` → `ToDictionary`, в хеш строк. `Ownership` разворачивал биты исполнений регионов в
`HashSet<string>`: по множеству на каждый регион с доступами и ещё по одному на создателей каждого
региона. Каждый id хешировался 3–4 раза (`given`, `visited`, `handedBy`, `attributed`), а потом
`Reached` сравнивал эти множества через `Except`. Теперь всё это идёт на битах:

- кто передал делегат (`handedBy`) — биты по номеру исполнения неизвестного вызова;
- атрибуция через переданные делегаты (`Attributed`) — тот же обход с `visited`, но над словами
  битов;
- исполнения с доступом к региону — объединение битов `CollectedAccess.Executions` и
  `WorkReach`;
- создатели (`CreationExecutions`) и исполнения, что выполняют операцию (`ExecutionsRunning`) —
  биты;
- «остальные» в `Reached` — `Bits.Except`, новый помощник.

`Union` больше не нужен и удалён. Новая контрольная точка `ownership` после `Ownership` пишет
число регионов по видам владения и `evidenceChars` — суммарную длину строк evidence.

После рана `nop-459-1` (ниже) владелец решил форму evidence: список исполнений ограничен
(«Опция 1, N=1»). Там, где evidence перечисляло исполнения — все, к кому обращается регион
`ThreadConfined`, остальные исполнения `TreeConfined` и создатели `Escaped`, — теперь называется
первое исполнение в прежнем порядке (ординальном по id) и число остальных: «… is reached only in
A and 1 other execution.», «… and 5 other executions.». Регион с одним исполнением даёт прежний
текст. Число названных исполнений — константа `NAMED_EXECUTIONS`. `Describe` читает первое
исполнение и число остальных прямо из битов, не строя список имён. Полный набор исполнений остаётся в
модели битами. В fingerprint находок и групп evidence не входит: они строятся из правила, ресурса,
тел, порядковых номеров и операций. Ни SPEC (TD-050 говорит только «с evidence chain»), ни CONTEXT
формат evidence не описывают. Закоммиченные ожидаемые выводы этих строк не содержат, так что
перезаписывать нечего.

Тесты в `CanonicalOrderTests`:

- `Reached_only_in_names_the_first_execution_and_counts_the_rest` — регион `ThreadConfined`, к
  которому обращаются два исполнения: evidence называет ординально первое и «1 other execution»,
  при любом порядке обхода.
- `Reached_only_in_names_a_single_execution_alone` — регион с одним исполнением: evidence называет
  его, без счётчика.

До них ни один тест не закреплял текст evidence владения целиком.

## #462 — `SemanticGaps.Find` по битам

### Диагноз

образца сторожа — в `SemanticGaps.Find` ← `InterproceduralAccesses.Collect`, в первом вызове

Частная память за это время выросла с 59 до 110 ГБ. Построения `Flow` в этом окне нет: графы
`Flow` строятся раньше (14:47–14:50, `Builder.FlowOf` из `FinishSpawnedExecutions`), а рабочий

До сбора `Find` строил словарь `executionRegions`: каждый из 5,35 млн доступов модели исполнений
(`CollectedAccess`, по дампу `nop-459-3`) разворачивал своё множество исполнений в пары строк

неразрешённым вызовам (`UnknownDelegateCallId`).

### Изменение

- `Find` сначала собирает вызовы вместе с их делегатами. Нужные исполнения — неизвестные
  исполнения этих делегатов, и регионы считаются только для них (`ExecutionRegions`).
- До сбора доступов множества исполнений одного анализа нумеруют исполнения одинаково, а равные
  множества — один объект (ADR 0017). Нужные исполнения становятся одной маской битов
  (`ExecutionSet.NumbersOf`), каждое различное множество сверяется с ней один раз
  (`ExecutionSet.Among`), и в строки разворачиваются только совпавшие исполнения.
- После сбора доступ после склейки ADR 0038 несёт свои исполнения (`ExecutionIds`), и каждое
  проверяется на вхождение в нужные — без пар, кортежей и `GroupBy` по всем исполнениям. Цена —
  одна проверка в `HashSet` на пару «склеенный доступ × его исполнение».
- Gaps те же: тот же список, места, экземпляры и число регионов.
- Контрольная точка `gaps:<scope>` после первого `Find` в `InterproceduralAccesses.Collect`: число
  gaps, их регионов и мест вызова и число доступов модели исполнений.

Тест `SemanticGapTests.Handed_delegate_counts_what_its_unknown_execution_touches_before_and_after_collection`:
неразрешённому вызову передан делегат, который пишет свой статик, а воркер сам пишет другой
статик. Gap `CancellationToken.Register(Action)` считает один регион — статик делегата — и до
сбора доступов (`Find(input)`), и после. Без пути через неизвестное исполнение делегата тест падает
в обоих случаях (1 против 0; проверено, затем код возвращён).

получателей и аргументов — со своими `visited` и `reached`, оба `HashSet<string>`, а ключ
получателя, видимого через объявляющий тип, ещё и склеивался строкой. Обход каждого вызова
кончается, но вызовы на одних и тех же получателях и аргументах повторяют одно и то же, а `Find`
зовётся дважды, до сбора доступов и после, и каждый раз с новым `Reach`. Частная память при этом не
росла, рабочий набор упал до 1,2 ГБ: время уходило на хеш строк, а не на память.

#### Изменение

- `Reach` нумерует регионы. Шаг обхода по региону (коллекция, неизменяемый, захваты делегата,
  состояние, слоты по корням с целями) спрашивается у кучи один раз и хранит цели номерами.
- Обход одного старта — региона и, для получателя, типа, через который он виден, — делается один
  раз и хранится битами; одинаковые результаты (старты одной сильно связной части кучи) делят один
  массив. Вызов объединяет биты своих стартов (`Reach.BitsOf`); `Of` отдаёт то же строками.
- Прежний обход шёл по стартам вызова по очереди с общим `visited`. Он даёт то же, что объединение
  отдельных обходов, во всех случаях, кроме одного: обход получателя, видимого через объявляющий
  тип, снова встречает сам получатель. Там обход останавливается, и получатель остаётся невиденным
  целиком и для следующего старта вызова. Такой вызов обходится целиком, по прежнему правилу, на
  номерах (`wholeCallWalks`).
- `SemanticGaps.Find` берёт `BitsOf`, отбирает общие регионы по маске, где каждый регион
  проверяется один раз, и копит регионы gap битами. Gaps те же.
- Строка `gaps-reach:<scope>:before|after` в `checkpoints.log` (без полной сборки): вызовы,
  обходы стартов, обходы вызовов целиком, регионы, посещения, различные результаты.

Тест `UnknownReachTests.Each_start_is_walked_once_and_a_call_reaches_what_one_walk_of_its_starts_in_turn_reaches`
сравнивает `Reach.Of` каждого неразрешённого вызова фикстуры с прежним обходом, переписанным в
тесте как эталон, и проверяет, что общий старт обходится один раз. Тем же эталоном разовой пробой
(не закоммичена) проверены все неразрешённые вызовы demo (Demo.Web — 503 вызова, 44 обхода старта;
Demo.Worker — 5) и eShop (14 скоупов, 2688 вызовов, 453 обхода старта): ни одного расхождения,
обход вызова целиком не понадобился ни разу.

## #460 — время решения кучи

### Диагноз

Грубый профиль `nop-459-1` (61 стек потока решателя, раз в 30 секунд) давал включительно: `Call` →
`CallTargets` 75 %, `Dispatch` 43 %, `Bind` 31 %, `SubstitutionText` 21 %, `Add` 20 %, а лист
`PollGCWorker` — 43 % стеков. По коду: «грязный» экземпляр обрабатывается целиком
(`ProcessOrSkip` → `Process`), и каждый его вызов заново вычисляет получателей, диспетчеризует
каждого и привязывает все аргументы. Обрабатывать только «хвост» получателей и аргументов нельзя:
`Eval` значения с несколькими источниками собирает новое множество, и элемент, который получил
первый источник, встаёт в середину, а не в хвост. Кроме того, работа вызова по старому получателю
зависит не только от него: `Bind` вливает в вызывающего `Returns`, `RefParameters` и `Requests`
вызываемого, типы DI-получателя растут, `_mergedBodies` меняет экземпляр, к которому идёт
привязка. Поэтому изменение сделало worklist на уровень мельче — по вызовам.

### Изменение

- **Счётчики (задача A).** С `CH_DIAG_DIR` точка `heap-end:<scope>` пишет ещё три строки. `solver`:
  проходы, обработки и пропуски экземпляров, обработанные вызовы, вызовы, что добавили факт
  (`changingCalls`, по `_changes` до и после вызова), пропущенные вызовы и время — проверки «грязный
  или нет», `Process`, вызовов, остатка прохода и всего решения (`HeapSolveProfile`). `gc-solve`:
  паузы, сборки по поколениям и выделенные байты самого решения, снятые до принудительных сборок
  точки. `gc-process`: итоги процесса. В счётчики метрик и снапшоты ничего из этого не входит.
- **B1.** `Bind` проверял, что вызов — собственный перенос сводки вызывающего, линейным поиском по
  `Summary.Calls` на каждую привязку. Теперь это множество переносов по ссылке, одно на сводку.
  Подстановка члена для объявляющего типа и аргументов типа и её текст ключа делаются один раз и
  общие для экземпляров.
- **B2.** Каждый вызов экземпляра хранит свою историю: момент начала, прочитанные ключи, вклад в
  перестраиваемые выходы, число `reference-lookups` и снимок индекса достижимости, если он его
  читал. В обработке, которую решил worklist, вызов, ни один ключ которого не записан с начала его
  прошлой обработки, пропускается: его чтения идут в чтения экземпляра, его вклад сливается в
  `_rebuilding` на его месте, его `reference-lookups` прибавляются к счётчику. Чистый вызов ничего
  не пишет, поэтому грязные вызовы пишут в прежнем порядке, а вклад, собранный из кусков по вызовам,
  даёт каждому перестраиваемому выходу тот же порядок первого появления. Проходы, обработки,
  счётчики и все выходы не меняются. В режиме `Audit` пропущенный вызов всё равно прогоняется и
  сверяется (чтения, `_changes`, вклад, `reference-lookups`), аудит экземпляра сверяет собранный
  вклад с полной обработкой, `VerifyConvergence` вызовы не пропускает. `RebuiltState` делает свои
  коллекции при первом обращении: у большинства вызовов вклад пустой. Истории вызовов отпускает
  `Settle`.

Тесты в `WorklistTests`: `Solve_profile_counts_the_skips_and_times_the_passes_apart_from_the_counters`,
`Dirty_instance_skips_its_clean_call_and_processes_the_dirty_one` (с `Audit` и
`VerifyConvergence`). В тесте полей решателя названы новые неотслеживаемые поля.

### Изменение

- **Запросы.** Множества запросов только растут и перечисляются в порядке добавления. `AddRequests`
  (девять мест) помнит для пары множеств по ссылке, сколько первых запросов источника цель уже

- **Рёбра.** `Bind` пропускает ребро, которое привязка уже делала, по самим экземплярам, до

  экземпляра.
- Обе памяти решателя отпускает `Settle`.

## #463 — решённая куча без ключей состояния

### Зачем

ADR 0040 (#461): доступы собирают несколько потоков, и все читают решённую кучу. А чтение кучи
писало: `TrackedMap.Entry` лениво добавлял ключ записи в обычный `Dictionary` (`_keys`) на каждом
`TryGetValue`, `ContainsKey` и индексаторе, проверка членства ставила флаг `_itemsRead`, ключи
пустоты и всего контейнера делались при первом чтении. Два потока на одной карте испортили бы
словарь. Кроме того, по дампу точки `ownership` рана `nop-459-3` только через решатель держатся
1,98 ГБ, из них около 0,95 ГБ — 14,5 млн `StateKey` и их словари.

### Изменение

- **Владелец и реестр.** Контейнер прикрепляется к владельцу (`IStateOwner`) вместо пары
  делегатов чтения и записи; решатель и есть владелец. Ключ контейнер получает только в
  `TrackedContainer.Attach`, и там же владелец слышит о нём: решатель кладёт каждый прикреплённый
  контейнер в список `_attached`. Прикреплённый — значит, в реестре, по построению; рефлексии в
  продукте нет.
- **Заморозка.** Последним шагом `Settle` каждый контейнер реестра отпускает ключ, ключи записей
  карт и ленивые ключи (`TrackedContainer.Freeze`), а реестр отпускается. После этого чтение
  ничего не пишет, с любого потока.
- **Защита от записи осталась.** Изменение замороженного контейнера бросает
  `InvalidOperationException` («…the heap is frozen after its solve»), как прежде бросала запись
  запроса через журнал решателя. Изменение, которое ничего не меняет (добавление уже
  присутствующего), по-прежнему ничего не делает. Контейнеры, созданные запросом, остаются
  изменяемыми.
- `Run` = `Converge` + `Settle`; тесты, которые гоняют шаги решателя после решения, зовут
  `Converge`. `Solving` ставится в `false` до заморозки, чтобы конец `Run` ничего не писал.
- **Безопасными для нескольких потоков** сделаны памяти `TypeSafety` (в том числе отдельного
  экземпляра у `InterproceduralAccesses`, который поделят сборщики #461) и `SummaryCache.Get`:
  `ConcurrentDictionary` и сборка сводки под одной блокировкой с повторной проверкой, одна сводка
  на тело.
- Остальное на путях чтения уже было безопасно: счётчик запросов, `_queryInterned`, `_named`,
  `_anyNamed`, памяти `ProgramIndex`, `_operationsById`; `_reachIndex` строят только шаги решения.

Прикреплено за решение ровно столько, сколько живо на `Settle`: решатель ничего не удаляет из
прикреплённых контейнеров. На demo (`metrics --generation off`, временный счётчик) — 37 117 /
39 896 / 40 419 / 123 прикреплено и столько же заморожено. На eShop (тот же счётчик, под corpus-lock
22.11 в 07:00): 14 решений, в каждом прикреплено столько же, сколько заморожено, всего 39 423, больше
всех `Catalog.API` — 6766. Реестр на `Nop.Web` — по дампу
`nop-459-3` около 3–3,5 млн ссылок, 25–30 МБ, до конца `Settle`.

Тесты в `WorklistTests`:

- `Every_container_with_a_key_is_in_the_solver_registry_and_none_has_one_after_the_solve` —
  независимый обход полей и содержимого (рефлексия только в тесте) находит каждый контейнер с
  ключом в реестре, и их ровно столько же; после `Settle` ни у одного нет ключа.
- `A_solved_heap_lets_go_of_its_state_keys_so_reads_from_several_threads_write_nothing` — чтение
  каждого контейнера и запросы `Resolve` с 8 потоков не меняют ни одного поля и дают то же, что
  один поток.
- `A_change_of_the_solved_heap_throws_and_a_set_made_after_it_does_not`.

## #465, #466 — спаривание

### Шаг 0: замер

Аудит хеширования строк называл стадию спаривания следующей стеной (FN-6…FN-9) по чтению циклов. Большие корпуса до неё

ленивые запросы решённой кучи в доказательствах.

### Контрольные точки

`InterproceduralPairing.Pair` сообщает на входе и выходе. Строка `pairing:<scope>` содержит `accesses`, `candidates` и
`accessExecutions`. Строка `pairing-end:<scope>` содержит:
- `comparisons`, `executionPairs` (пары исполнений, о которых спрошен тайминг), `candidates`, `suppressed`, `buckets`,
  `largestBucket`;
- строку `timing` со счётчиками с момента входа:
  - `orderQueries` — вопросы `OrderedBy`;
  - `pathSearches` и `pathEvents` — поиски путей и события, взятые из очереди;
  - `assumptionQueries` — пары, допущения которых спрошены;
  - `replays` и `replaysTotal` — графы `Withholding`;
  - `flows`, `flowNodes` и `flowsTotal` — построенные графы `Flow` и их узлы;
  - `reachSets` и `reachExecutions` — множества `ExecutionReach` и исполнения в них.

Счётчики (`TimingCounters`) — один набор на граф happens-before и все его replay. Анализ их не читает, в метрики они не
входят. Тест `TimingCountersTests.Graph_and_its_replays_count_the_timing_of_an_ordered_pair` проверяет, что упорядоченная
пара, чьи допущения спрошены, считает поиски, replay и графы `Flow`, а второе спаривание на том же графе не строит ни replay,

## #461 — сбор доступов на нескольких воркерах (ADR 0040)

### Изменение

Сбор доступов шёл по исполнениям одного scope по очереди, в одном потоке. При этом каждый сборщик обходит одно исполнение
от его собственных входов, а решённая куча после #463 заморожена. ADR 0040 (вариант A, решение владельца):

- **Число воркеров.** `InterproceduralInput.Workers`, по умолчанию 1. Ран задаёт его переменной `CH_ACCESS_WORKERS`. При одном
  воркере работает прежний цикл на вызывающем потоке, проверка в проверку.
- **Несколько воркеров.** Каждое исполнение обходит один воркер своим сборщиком. Воркеры берут исполнения по порядку и забегают
  вперёд склейки не больше чем на два исполнения каждый. Склейка (`AccessFolding`) идёт на вызывающем потоке и берёт
  исполнения строго в порядке `ExecutionAnalysis.Executions`. Поэтому каждый доступ сохраняет те же исполнения, позиции и
  варианты, что и при одном воркере.
- **Общее между сборщиками** — кеши чистых функций, теперь потокобезопасные. Каждый вызывающий берёт значение, которое кеш
  хранит:
  - пулы строк, последовательностей и номеров. Код склейки сравнивает code flow по ссылке, поэтому равные code flow должны быть
    одним объектом;
  - `bindingEvidence`;
  - ресурсы, сведения о регионах, места и номера экземпляров;
  - шаги `WalkGraph` по экземпляру;
  - сегменты тела `AsyncSegments`.
- **Запрос конструкции.** Вместо одного замка на все поиски — замок того объекта, который ищут. Метки поиска у каждого потока
  свои.
- **Что не трогали.** `UnknownCalls.Reach` (#462): его обход пишет состояние, но идёт только в `SemanticGaps.Find`, до и после
  обхода исполнений.
- **Ошибка в обходе исполнения** останавливает сбор, когда до этого исполнения доходит склейка. Поэтому сообщается самая ранняя
  ошибка в порядке сбора.
- **Входы исполнения.** Заранее решается только, обходить ли исполнение (`ContainsKey`, без списка). Список входов делает воркер,
  когда берёт исполнение, и он уходит после склейки. Модель строит этот список заново на каждый запрос (ADR 0039), поэтому живых
  списков сразу не больше окна — двух на воркера.
- **Контрольные точки под `CH_DIAG_DIR`.** `execution:<scope>` на каждое обойдённое исполнение: место среди всех исполнений
  (`n=K/N`), id, число доступов, миллисекунды обхода. `accesses-end` пишет число воркеров. `DiagnosticCheckpoint` пишет строку
  под замком.

Тесты:

- `ParallelCollectionTests`: склеенные доступы demo на четырёх воркерах трижды сравниваются с одним воркером — порядок,
  исполнения, позиции, варианты и какой вариант каким объектом. Путь воркеров с одним воркером сравнивается с прежним циклом.
  Отдельный тест проверяет, что на четырёх воркерах одновременно живых списков входов не больше окна.
- Числа `TextNumbers` из восьми потоков.
- Целые строки контрольных точек из восьми потоков.

**Условие теста изменено.** `StageCancellationTests.Cancellation_deep_inside_each_pipeline_step_stops_it` требовал, чтобы после
проверки, на которой сработала отмена, никто больше не проверял. На четырёх воркерах он упал на шаге `Accesses`. Каждый другой
воркер делает ещё одну проверку: на ней он и узнаёт об отмене, как сказано в ADR 0040. Кроме того, воркер, чей обход прервала
отмена, шёл на новый круг и проверял второй раз.

- Код: воркер, чей обход остановила отмена, теперь сразу выходит.
- Тест: считает проверки по потокам. Поток, на котором сработала отмена, больше не проверяет; любой другой проверяет не больше
  одного раза — это проверка, которая его останавливает. При одном потоке условие то же, что прежде.

## #467 — посещение выдаёт доступ только под guards, под которыми исполнение его ещё не выдавало (ADR 0041)

Раны #464 и `nop-461-1` (разделы выше) оставили сбор доступов без конца на обоих корпусах. Повтор в нём двух уровней:
между исполнениями (OrchardCore: 25,3 копии на склеенный доступ) и внутри одного исполнения (`Nop.Web`: семь исполнений
шли больше часа при тех же 0,5–0,6 млн ключей, что у кончившихся за минуты). Владелец выбрал вариант A ADR 0041 вместе
со счётчиками и #470 рядом. Работа — три коммита: счётчики, правило, #470 (раздел ниже).

### Счётчики

Поведение не меняется. Под `CH_DIAG_DIR`:

- **Строка `execution:<scope>`** после `ms=` несёт счётчики сбора этого исполнения:

  | Поле | Что считает |
  |---|---|
  | `entries` | входы исполнения |
  | `visits`, `states` | посещения обхода (путь от входа до состояния) и различные состояния среди них |
  | `rows` | ресурсы, пройденные выдачей: по одному на доступ посещения и его ресурс |
  | `keys` | проверки ключа `EmittedKey`: ресурс на каждую локальность и каждый путь вызова |
  | `hits` | проверки, которые нашли под ключом доступ под guards, входящими в guards посещения; такая проверка ничего не выдаёт |
  | `emitted`, `replaced` | выданные доступы и те из них, которые позже заменил путь под меньшим числом guards |
  | `wouldSkip`, `wouldSkipEmitted` | проверки ключа, которые правило ADR 0041 пропустило бы, и те из них, что всё же выдали доступ |
  | `walkMs`, `locksMs`, `dependenciesMs`, `emitMs` | миллисекунды обхода от входов вместе с хостами, фикспойнта замков, зависимостей записей от чтений и выдачи |

- **Точка `gaps:<scope>`** несёт `executionAccessExecutions` — сумму размеров множеств исполнений по
  `ExecutionAnalysis.Accesses`. Это нижняя оценка `accessExecutions`, известная до начала сбора; неизвестных эффектов в
  ней нет.
- **Цена без `CH_DIAG_DIR`.** Простые счётчики — сложения. Различные состояния и память, по которой считается
  `wouldSkip`, ведутся только в диагностическом ране или когда счётчики читает тест (`InterproceduralInput.Counted`).
- **Правило считается, но не применяется.** Счёт стоит там, где выдача уже знает guards доступа и замки пути, поэтому
  ни один вызов не добавлен и не переставлен.

Тест — `CollectionCountersTests`: поля строки и их порядок; у каждого исполнения `keys = hits + emitted` и
`emitted − replaced` равно числу его доступов; второй путь под большим числом guards даёт попадания, которые правило
пропустило бы, и ни одной выдачи среди них; путь под меньшим числом guards после пути под большим даёт одну замену.
`EngineFixture.Input` отдаёт тесту вход сбора.

### Правило

ADR 0041, вариант A, теперь со статусом Accepted. Находки, порядок доступов, позиции и варианты не меняются: правило
заранее отвечает на проверку, которую `Emit` и так делает последней.

- **Что запоминается.** Сборщик держит для пары «экземпляр и объект доступа» наборы guards, под которыми доступ уже выдан
  в этом исполнении. Новый набор вытесняет из списка те, что его включают, как путь под меньшим числом guards заменяет
  доступ под ключом. Память своя у каждого сборщика и уходит вместе с ним; ADR 0038 и ADR 0040 не затронуты.
- **Какие доступы.** Доступ path-free, если выдача читает путь посещения только ради его guards:
  - это доступ сводки или сохранённого списка unknown effect, то есть один объект на каждом посещении;
  - у него нет selector term;
  - посещение — не хост перечисления и не хост работы без тела;
  - перечисления на пути посещения не добавляют замков.

  Доступ по ссылке, доступ с term, эффекты known call, доступы хоста и доступы посещения с замками перечисления идут как
  раньше.
- **Пропуск.** Если у path-free доступа есть запись и guards посещения включают один из записанных наборов, доступ
  пропускается до чтения его ресурсов. Иначе он проходит прежний код, и его guards записываются.
- **Ничего нового не вызывается.** Правило спрашивается только у доступа с записью. Запись есть, когда хотя бы один ресурс
  доступа дошёл до guards, а это от пути не зависит. Значит, прежний код на этом посещении тоже спросил бы guards доступа и
  замки пути; теперь он спрашивает их раньше, а не чаще. Порядок нумерации guards в сборщике прежний.
- **Форма «до построения списка эффектов»** из ADR не делалась: она берётся, только если счётчики покажут список наверху.
- **Переключатель.** `InterproceduralInput.EmitsUnderRepeatedGuards` (internal) собирает без правила, для теста.
- **Счётчики.** Вместо `wouldSkip` и `wouldSkipEmitted` строка `execution:` несёт `skipped` (пропущенные доступы
  посещений) и `skippedKeys` (проверки ключа, которых они не сделали). `keys + skippedKeys` — проверки до правила.

Тесты — `RepeatedGuardsTests`. Каждый собирает scope без правила и с ним и сравнивает описания: доступы по порядку, каждое
поле, исполнения с позициями и вариантами, и какой общий список каким объектом (code flow, guards, проверки gaps, метки
неопределённости), плюс счётчики покрытия и gaps.

| Случай | Что закрепляет |
|---|---|
| каждый scope demo | описания равны; с правилом пропуски есть, без него их нет |
| путь под большим числом guards после пути под меньшим | один пропуск, один доступ без guards |
| путь под меньшим числом guards после пути под большим | пропуска нет, одна замена |
| два пути под разными guards | пропуска нет, два доступа |
| term, привязанный на двух путях к разным значениям | обе ячейки остаются; чтение поля с массивом (без term) на втором пути пропущено |
| ссылка, разрешённая по двум путям в разные места | оба места остаются |

### Вывод

- **Правило A сняло повтор проверок внутри исполнения.** На OrchardCore 98,2 % проверок ключа были попаданиями, и правило
  убрало 94,8 % из них. Сбор при этом ускорился вдвое, а не в десятки раз: пропущенные проверки были дешёвыми, а цена
  посещения осталась.
- **Что осталось внутри исполнения.** Посещений 11,8 млн на 360 тысяч состояний, и каждое строит список своих эффектов и
  guards пути: по трассе около 38 % потока. Решение правила по одному доступу — это своё время `Emit` и поиск записи, вместе
  до четверти потока. ADR 0041 называет обе следующие формы: решать до построения списка эффектов и решать сразу по группе
  доступов с одним списком своих guards. По ADR первая берётся, когда список оказывается наверху; он наверху.
- **Что осталось между исполнениями.** 785 из 933 крупных исполнений повторяют счётчики другого исполнения. Каждое из них
  заново выдаёт свои копии: 42,4 млн выдач в час, 40,7 % из них потом заменяются.
- **Память.** Проекция — около 136 млн копий на scope, порядка 3,3 ГБ на записи `AccessExecution`. Нижняя оценка из точки
  `gaps:` — 26,4 млн, в пять раз меньше проекции: на OrchardCore доступы дают в основном неизвестные эффекты, которых в
  модели исполнений нет. Для решения о варианте C на `Nop.Web` эта оценка годится как порядок снизу, не как число.
- **Чего этот ран не дал.** `accesses-end` не достигнут, дамп не снимался: число склеенных доступов и доля копий, легших
  в уже склеенные, не измерены. Скорость сравнивается со средней скоростью ночного рана; первого часа отдельно у него нет.

## #470 — первый получатель шага `CodeFlow` один раз на экземпляр

### Изменение

Трассы `nop-462-1` и `nop-461-1` показали `CodeFlow` наверху в первые минуты сбора `Nop.Web`: 61,5 % обхода воркеров, из
них своё время `Enumerable.TryGetFirst` 40,2 % и `Array.Copy` 22,6 %. Шаг «calls … on …» называл получателя выражением
`callee.Receivers.Order(StringComparer.Ordinal).Select(…).FirstOrDefault()`. `Order` перед `FirstOrDefault` не сортирует,
а ищет минимум одним проходом, но проход по всем получателям экземпляра шёл на каждом шаге пути каждого выданного доступа.
Списки шагов и пути при этом росли по одному элементу.

- **Получатель.** Первый получатель экземпляра в ординальном порядке ищется одним проходом и один раз на scope:
  `CollectorShares.FirstReceivers`, по объекту экземпляра. Это кеш чистой функции экземпляра и кучи, и каждый вызывающий
  берёт значение, которое кеш хранит (ADR 0040). Элемент тот же, что давало прежнее выражение.
- **Списки.** Глубина пути считается одним проходом по родителям. Путь — массив этой длины, заполняемый с конца, без
  `Reverse`; список шагов создаётся сразу нужной ёмкости.

Тест — `InterproceduralAccessTests.A_call_step_names_the_first_of_several_receivers_in_ordinal_order`. Метод вызван на трёх
объектах в обратном порядке; при одном контексте на метод это один слитый экземпляр с тремя получателями, и шаг называет
первый из них по ординальному порядку id регионов. С максимумом вместо минимума тест падает.
