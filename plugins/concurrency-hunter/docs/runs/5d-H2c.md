# 5d run H2c — допуск вызова `sequential-awaited` по проходу

База сравнения — `795e71a0` (`HEAD` при записи). Требования рана — строка «5d run H2c» [PLAN](../PLAN.md) и вопрос 210 при допущениях [ADR 0030](../adr/0030-ordering-assumes-the-default-thread-context-unless-visible-code-installs-another.md): вызов `sequential-awaited`, который не проходил отбор только из-за порога однократности по запуску, допускается по проходу сериализованного родителя; одна проверка «задача вызова ожидается сразу» для обоих порогов; join задачи вызова TD-065 остаётся по запуску; `assumed` считает пары, снятые допуском по проходу; demo-кейс `polly-nested-retry`; замер eShop 32 → 2. Нового ADR нет.

## Решения

- D-0001 — Объём — строка H2c и вопрос 210 при допущениях ADR 0030, ничего сверх; всё, что требует другого механизма или ADR, идёт в QUESTIONS; вопрос 210 закрыт.
- D-0002 — Вызов `sequential-awaited`, который не проходил отбор только из-за `SiteOnce`, допускается, если он делается не более одного раза за проход сериализованного родителя, его задача ожидается сразу, а проход завершается до следующего — тем же входом, что у `SequentialRuns`: проход ждёт работу на каждом пути, исключительном тоже, по ADR 0030. Проход — в смысле H2a. Допуск по проходу даёт продолжение перед синхронной частью следующего запуска, непересечение продолжений и завершение запусков прохода к ожиданию задачи вызова.
- D-0003 — Ребро TD-065 (конец запусков → ожидание задачи вызова) сохраняет порог по запуску; `FinishUnknownDelegateCalls` и допуск `sequential` не трогаются (если им нужно то же — строка в QUESTIONS); пары допуска по проходу считаются в `assumed` по ключам ожидания прохода; вопросы 211 и 214 не решаются; нового ADR нет, SPEC, CONTEXT и абзац ADR 0008 правятся.
- D-0004 — Граница правила. Проба со снятой проверкой `SiteOnce` дала 32 → 2, но изменила 21 тест движка — 20 клеток `AwaitedRunsMatrixTests` (`sequential-awaited` × `loop` × `async`) и `AwaitedRunsTests.Wait_of_a_call_task_that_fails_the_gate_stays_an_unproven_join`. Ожидание каждой клетки выводится из правила и записывается с причиной; клетки `wait: none` обязаны сохранить self-pair.
- D-0005 — Матрица порога по проходу: родитель × вызовов за проход × ожидание задачи вызова × завершение прохода × async-входов тела; стороны — продолжение × синхронная часть следующего запуска, продолжение × продолжение, продолжение × код родителя после вызова; ключи `assumed` по клеткам. Образец клетки формы eShop — `Distinct_generic_migrations_keep_distinct_seeders` с ветки `7b36aa6`.
- D-0006 — Demo: кейс `polly-nested-retry` формы eShop в однократном `BackgroundService`, пара снята; контроль — проход не ждёт `SeedAsync()`, пара остаётся; получатели объявлены как `RetryPolicy` и `AsyncRetryPolicy`.
- D-0007 — Приёмка eShop: 32 → 2, обе оставшиеся — `WebhookClient` (7c919c7aedc4b38e, fa3fbc528c46593e); `H2EShopAcceptanceTests` с ветки `7b36aa6` проверяет точных выживших; если правило даёт не 2 — стоп и разбор.
- D-0008 — Задача 1 — тонкий срез. Полный suite и `check-test-baseline.ps1 -Record` — на гейтах и в конце рана; в батче только тесты правила и проверка «падает без правки»; модели demo перезаписываются в каждом батче, меняющем движок; после копии исходника сборка с `--no-incremental`; метка первым аргументом строки теории.
- D-0009 — Фиксы код-ревью проверяются коротко после каждого хода, полностью — в конце рана (`gate=targeted`, `fullGate=final`).
- D-0010 — Допуск по проходу упорядочивает и код родителя после ожидания задачи вызова: пара снимается, как у join своего прохода H2a.
- D-0011 — «Задача вызова ожидается сразу» — `await`, блокирующее ожидание (`Wait()`, `Result`, `GetAwaiter().GetResult()`) сразу после вызова и возврат члена без задачи; одна проверка с одним владельцем для обоих порогов; `Fire/none` в цикле теряет self-pair.
- D-0012 — Вызов в теле с двумя async-входами допускается по проходу: доказательство прохода по каждому входу; `await Helper(); await Helper();` снимает пару, недожданный первый вход — нет.
- D-0013 — Счёт однократности по проходу — тот же, что у `SiteOnce`, но от начала одного прохода до начала следующего: путь обратно к месту, проходящий новое начало прохода, чьё завершение установлено доказательством, не считается вторым вызовом.
- D-0014 — Запуски вызова, допущенного только по проходу, — своя работа прохода, join которой — ожидание сразу; доказательство прохода упорядочивает её перед следующим проходом и перед доступами родителя после ожидания. Ребро TD-065 для такого вызова не ставится: ожидание его задачи остаётся непроверенным join-ом, `unproven-joins` eShop не меняется (47 и 13).
- D-0015 — `assumed`: пара, которую снимает только допуск по проходу, считается под ключами ожидания, на исключительном выходе которого держится завершение прохода (`observers` и `thread-context` вне пула, `observers` и `thread-pool-entry` на пуле); без такого выхода ключей нет. Схема `metrics` — 1.5.
- D-0016 — Продолжения вызова, допущенного только по проходу, не получают политику `SERIALIZED`: их пару с собой решает доказательство прохода, и она снимается как `ordered` (`ExecutionAnalysis.Timing` не меняется, ни одна пара допуска по проходу не снимается как `no-overlap`). «Ожидается сразу» — одна функция, которую читают и `SequentialRuns`, и кадр прохода.
- D-0017 — Условие «запуски разных вызовов упорядочены» в `SequentialRuns` для любого допущенного вызова — доказательство прохода самого вызова; оно заменяет «ровно один async-вход», `inline` и `outer`. Корневое тело, которое не входит ни через один async-вызов, входа не имеет, и пара снимается. `Task.WaitAll` одной задачи — ожидание сразу, `await Task.WhenAll(…)` — нет. Вызов, допущенный только по проходу, входит в `_sequentialRuns` и берёт якорь продолжения.

## Что построено

- Допуск по проходу (R1): `ExecutionModel.AdmittedCalls` отказывает вызову `sequential-awaited` по `RunsOnce` и `OnlyExecution`, а `SiteOnce` теперь выбирает порог — `AdmissionThreshold.PerRun` или `PerPass` в записи `AdmittedCall.Threshold`. Сам `SiteOnce`, `OnePath`, `RunsOnce` и их другие вызывающие не менялись. Политика `SERIALIZED` ставится только продолжениям вызова, допущенного по запуску.
- Ожидание сразу (R2): одна функция, `HappensBefore.Flow.WaitAtOnce`, рядом с `Flow.WaitParts`, который она переиспользует: `WaitParts` принимает и `await` как ожидание своего awaitable, `ConfigureAwait(bool)` — часть ожидания, `ConfigureAwait(ConfigureAwaitOptions)` — нет. Цикл «первый `await` задачи вызова» в `PassCompletionProof.SequentialRuns` убран; функцию читают оба порога.
- Доказательство прохода (R1) — `PassCompletionProof.SequentialRuns`: каждый путь от возврата вызова до него же проходит ожидание (`Flow.BeforeNext` от точки после вызова; поток прохода читает исключительный выход блокирующего ожидания по ADR 0030); родитель проходов не пересекается с собой; входы тела — ноль (корень исполнения, которое выполняется один раз), синхронный или async-вход, проход которого завершается до своего следующего запуска и до запуска другого входа (`CompleteBeforeNext`, `CompleteBefore`); входы собираются только когда ожидание вызова — `await` (приостановка), а блокирующее ожидание сразу и возврат члена без задачи завершают работу до возврата и до приостановки. Одно исполнение продолжения, стоящее за вызовом в нескольких экземплярах тела (`Migrate<A>` дважды), даёт столько допущенных вызовов, сколько якорей, и каждый доказывается сам. Тело, которое приостанавливается на `await`, отдаёт задачу вызывающему, и join, стоящий на таком `await` в префиксе async-тела, не завершает работу для путей вызывающего: кадр прохода заменяет его ожиданиями задачи этого тела, найденными тем же способом выше по async-входам, пока не дойдёт до ожидания, которое останавливает пути (`Climb`); `await` тела, которое входит в исполнение первым, остаётся join-ом; `await` делегата допущенного вызова — тоже для другой работы, потому что его задачу дожидается библиотека (вопрос 217). Для работы допущенного по проходу вызова `await` делегата остаётся join-ом для следующего запуска делегата — библиотека дожидается задачи запуска, — а ожидание задачи самого внешнего вызова читает проход этого вызова (`OuterPass`, `ClimbRuns`, SPEC TD-034a): код после возврата внешнего вызова и его следующий проход упорядочены, только когда эта задача ожидается сразу, и только на исходах ожидания, что следуют за завершением (тем же `ThrowsAfterCompletion`, что читает любое ожидание); ожидание, которое само приостанавливает тело, поднимает подъём выше, `await Task.WhenAll(…)` и ожидание после операции, которая может бросить, ожиданием сразу не считаются. Одно правило читают и допуск вызова, и join своего прохода другой работы: `Task.Run`, которую ждёт `await` async-хелпера, а хелпер никто не ждёт, пару сохраняет.
- Стороны порядка: (а) синхронная часть запуска — делегат и всё, что он вызывает до первого `await`; доступ родителя решают места, до которых он доходит (`OccurrenceOf`): место только в запуске — (а), место только у прохода — доступ родителя, метод, который вызывают и запуск, и проход, — и то и другое, так что его вхождение прохода перед вызовом или после ожидания упорядочено, а пока запуск идёт — нет, а метод, до которого доходит другой обработчик вызова, порядка не получает; (б) продолжения между собой; (в) код родителя после ожидания: в теле, которое делает вызов, и в хвосте этого тела или тела выше по async-входам (`TailFollows`) — когда каждый путь от вызова до каждой приостановки такого тела проходит ожидание (ожидание вызова в теле, которое его делает, join хвоста ниже в теле выше) в любой из форм ожидания сразу, а сам хвост завершается до следующего прохода.
- Join TD-065 (R3): `HappensBefore` строит его только для `_joinedCalls` — вызовов, допущенных по запуску; вызов, допущенный только по проходу, join не получает, ожидание его задачи остаётся непроверенным join-ом, и `unproven-joins` покрытия eShop прежний.
- `assumed` (R4): ключи ставит поток прохода там же, где читает исключительный выход блокирующего ожидания; `ExecutionAnalysis.Timing` и схема `metrics` (1.5) не менялись.
- Комментарии `ExecutionModel.cs`, `PassCompletionProof.cs` и `HappensBefore.cs`, говорившие «один раз за запуск», «ровно один async-вход» и «`await` сразу», поправлены под правило; новые и изменённые XML-комментарии полные.
- Кейс demo `polly-nested-retry` (R5): `demo/Demo.Web/Cases/PollyNestedRetry.cs` и `AddPollyNestedRetry()` в `Program.cs`. `NestedRetryWorker` — `_retry.Execute(() => SeedAsync().Wait())`, где `SeedAsync` делает `await` своего `_seed.ExecuteAsync(async () => { _seeded = 1; await Task.Yield(); _seeded = 2; })`; `UnwaitedNestedRetryWorker` — контроль: делегат внешней политики запускает `SeedAsync()` и не ждёт его, пара `_left` остаётся. Получатели объявлены как `RetryPolicy` и `AsyncRetryPolicy`; кейс не называет пять типов, которые есть и в `Polly`, и в `Polly.Core`. Ожидания записаны в `expected-findings.json` (`notDefects` `polly-nested-retry/waited`, `findings` `polly-nested-retry/unwaited`, DCA1001 `high`, регион `di:…UnwaitedNestedRetryWorker@Singleton`, поле `_left`) и в таблицу 5d `SCENARIOS.md` до кода и до прогона.
- Оставлено: join своего прохода другой работы под делегатом допущенного вызова читает `await` делегата как конец работы и для кода после возврата самого вызова (вопрос 217).

## Документы

- SPEC TD-034a — допуск по запуску и по проходу, «ожидается сразу» вместо «`await` сразу», условие о входах тела вместо «один async-вход», правило для продолжений вызова, допущенного только по проходу (нет `SERIALIZED`, нет `no-overlap`, пара считается в `assumed`), фраза о непроверенном join-е — о вызове, не прошедшем порог по запуску; TD-065 — join задачи вызова строится по порогу по запуску, вызов, допущенный только по проходу, его не получает; TD-060, абзац «Join своего прохода» — запуски такого вызова — работа прохода, join — ожидание сразу, ключи `assumed`.
- CONTEXT — статьи **Site pass** и **Happens-before**: вызов `sequential-awaited`, допущенный по проходу. Абзац поправки ADR 0008 о проходе — тот же вызов; абзац о join задачи вызова по запуску не менялся. Новых ADR нет.
- `AGENTS.md` — замер eShop без восстановленных `project.assets.json` даёт 2 находки, то же число, что верный замер, поэтому файлы проверяются до замера; фраза «ни одна пара eShop не снимается как `ordered`» заменена: снимок считает `ordered` и `assumed` итогами, и каждый сдвиг объясняется до перезаписи.
- QUESTIONS — вопрос 210 закрыт (→ SPEC TD-034a, TD-065, TD-060; ADR 0008; CONTEXT, «Site pass»). Открыты (5g): 215 — место вызова, которое делают два исполнения (повтор после `await` самого тела вызова), и вызов в исполнении, которое не выполняется один раз; 216 — проходы внутри продолжения вызова, допущенного только по проходу (политика продолжения остаётся `MayOverlap`). Причина списков «шире» одна и прежняя — вопрос 214: четыре клетки `PollyRetryAttemptMatrixTests` остались четырьмя; список «шире» `PerPassAdmissionMatrixTests` пуст. 217 — join своего прохода другой работы под делегатом допущенного вызова. Работа допущенного по проходу вызова задачу внешнего допущенного вызова читает (SPEC TD-034a); для другой работы её не читают, и на этом чтении держится утверждённый факт `PollyRetryAttemptMatrixTests` (`await Task.WhenAll(…)` задачи вызова, вопрос 213) — пункт перенесён по стоп-правилу (д) в вопрос 217. Порог `FinishUnknownDelegateCalls` и отбор `sequential` не менялись; потребности в том же правиле ни один замер и ни одна клетка рана не показали, отдельной строки нет.
- PLAN — строка H2c «построено», абзац фазы 5d дополнен состоянием H2c; порядок ранов не менялся.
- Гайд `docs/concurrency-hunter-guide.ru.html`, ответы model evals, `skills/hunt/`, `IrSchema.VERSION`, `PhaseOrder`, `CURRENT_POINT`, `findings.json` и исторические `build/check-phase5d-run*.ps1` ран не трогал; отложенная правка гайда из записи H2b (число встроенных файлов моделей) остаётся отложенной.

## Исправления код-ревью (F-0009 … F-0013)

Корень F-0009 и F-0011 — общий: кадр доказательства прохода (`PassCompletionProof.Frame`) брал любой `await`, который ждёт задачу прохода, за join, в том числе `await` в префиксе async-тела. Префикс покидает тело на первом `await`, поэтому пути вызывающего тела на нём не останавливаются: работа завершена только там, где вызывающий дожидается задачи этого тела, — и так вверх по async-входам. Тот же счёт ошибался и у других работ: `Task.Run`, которую ждёт `await` async-хелпера, а хелпер никто не ждёт, пару с записью родителя и со следующим проходом теряла (одноразовая проба: 0 пар вместо 2).

| Находка | Правило | Где |

| F-0009 | приостановка async-тела завершает работу прохода только после ожидания задачи этого тела вызывающим, на каждом уровне цепочки | `Frame` делится на `Joins` (сырые join-ы, `await` префикса отдельно) и разбор: `Climb` заменяет `await` префикса ожиданиями задачи тела выше (рекурсивно, с условием, что тело выходит из префикса только через него, и с признаком, что исключение тела идёт после работы); `await` тела — входа исполнения остаётся join-ом; `await` делегата допущенного вызова — тоже, но не для работы допущенного по проходу вызова (F-0014). ## Исправления код-ревью, повторно (F-0009, F-0011, F-0015, F-0016)

Корень общий: подъём завершения работы по уровням ожидания читал ожидание каждого уровня по-своему, и каждое чтение ошибалось в своей клетке. Правило одно: работа прохода завершена на ожидании только на тех его исходах, что следуют за завершением, — нормальный всегда, исключительный так, как его читает join (`ThrowsAfterCompletion`: `await` — да; блокирующее ожидание `Task` без таймаута и токена — только по ADR 0030, когда нет достижимого установщика контекста, с ключами в `assumed`; ожидание `ValueTask` и всё остальное — нет), — а для кода, до которого путь доходит через приостановку async-тела, только там, где вызывающий дожидается задачи этого тела, на тех же условиях, уровень за уровнем. Владелец — `Climb` и `ClimbRuns`; `SequentialRuns` (стороны а, б, в), `TailFollows` и кадр прохода читают его одним и тем же `WaitOfCall` и `AwaitedAtOnce`, второго чтения ожидания нигде нет.

| Находка | Правило | Где |
|---|---|---|
| F-0009, F-0011 (вопрос 218) | тело без кода после последнего `await` хвоста не имеет и завершается там, где этот `await` возобновляется; вызывающий, который ждёт его задачу сразу в префиксе, приостанавливается на своём `await`, и подъём идёт от него к его вызывающим, на любую глубину и с хвостом на любом уровне | `Climb` и `TailFollows` идут через вызывающего, который ждёт тело сразу (`AwaitedAtOnce`), как через async-вызов; `SequentialRuns` собирает входы цепочки так же (`EntryPoints`: звонки такого вызывающего — входы, сам такой вызов — нет); вход, который есть вызов допущенной записи, решает проход этого вызова (`RunPassAllows`), а не продолжение его делегата, чей handle без хвоста не доказывается |
