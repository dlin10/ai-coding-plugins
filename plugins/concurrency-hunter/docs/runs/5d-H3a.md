# 5d run H3a

## Задача 1: задача пробрасывающего члена

Правило A (R2): задача, которую возвращает пробрасывающий член, сохраняет происхождение одного
async-вызова, сделанного один раз за запуск члена. `TaskForwarders` проверяет каждый возврат,
единственную цель вызова и однократность цепочки от экземпляра пробрасывающего члена. Ожидание
этой задачи доказывает join исходного вызова; async-вызов остаётся spawn с отдельным исполнением
хвоста и якорем `AsyncReturn`.

Доказательство своего прохода поднимается через пробрасывающие входы к ожиданию вызывающего.
Промежуточные ожидания сохраняют доказательство исключительного выхода, но не становятся
отсечками для вызывающего до его ожидания задачи. Завершение работы перед возобновлением
async-хвоста распространяется на работу, которую запускает этот хвост. Более слабое доказательство
исключительного выхода сохраняется при подъёме: исключение до join дочерней работы не завершает её.
При построении графа пути части `await`, включая `ConfigureAwait(bool)`, учитываются вместе с частями
блокирующих ожиданий; неявное ссылочное преобразование задачи не создаёт исключительный выход.

`TaskForwarderJoinMatrixTests` описывает 639 клеток по форме члена, ожиданию, месту, пути,
родителю, стороне и происхождению. С двумя служебными фактами это 641 тест; список `Wider` содержит
ровно три клетки `Program/TwoTargets/Await/Once/AllPaths|Bypass|ExceptionBeforeWait/Hosted/SameWork`.
Их ожидаемый ответ — пары нет: один запуск вызывает одну из двух целей делегата. Анализ читает
взаимоисключающие цели как два места spawn, которые могут идти оба, и сохраняет самопару `Write`.
Взаимоисключение целей делегата этот ран не строит; правило A этих пар не создаёт. Факт списка
проверяет имена и ожидание «пары нет», а каждая из трёх клеток обязана оставаться шире ожидания.
Клетки проверяют пары и сохранение async-spawn в куче и модели исполнений. Дополнительные
`TaskForwarderTests` проверяют проброс `Task<int>` как `Task` с `ConfigureAwait(false)` и `finally`,
а также явное преобразование, которое может бросить до ожидания.

Отдельная клетка `Chain/Await/Record/AllPaths/Hosted/ParentAfterWait/Program` стала красной
при возвращении фильтра прямого spawn в `Wrapped`. Проверка `ConfigureAwait(false)` и `finally`
стала красной при исключении `await` из сбора частей ожидания. После восстановления исправлений
выбранные клетки и дополнительные факты проходят. Полный класс матрицы и gate задачи запускает сервер.

Общий сборщик частей ожидания различает блокирующее ожидание и `await`: преобразования той же
задачи входят в части обеих форм, но `await` сохраняет прежние исключительные пути производителей
задач и построения группы `Task.WhenAll`. Иначе вызов `Seed`, который блокирующим ожиданием
заканчивает работу записи `sequential-awaited`, теряет зависимость от допущений `observers` и
`thread-context`, а исключение построения группы перестаёт обходить ожидание.
Отдельная проверка воспроизвела все 16 ошибок серверного gate. После исправления прошли 1476
тестов: `PerPassAdmissionMatrixTests`, `BlockingWaitAssumptionMatrixTests`, `TaskForwarderTests`
и выбранные клетки `Chain`, `FaultsBeforeChildJoin` и библиотечного `Expression` матрицы проброса
(`scratch/h3a/exceptional-wait-regressions.log`). Дополнительная теория проверяет сохранение пути
через `catch` при `await Task.WhenAll` над проброшенной задачей, также с `ConfigureAwait(false)`,
и отсутствие пары при прямом ожидании и блокирующем ожидании группы. Без исправления два случая
группового `await` красные; после восстановления все шесть тестов класса проходят
(`scratch/h3a/forwarder-exceptions-red.log`, `scratch/h3a/forwarder-exceptions-green.log`).

## Задача 2: объекты тел библиотеки по месту допуска

Правило B (R3): экземпляр тела библиотеки несёт место допущенного вызова проекта, а вызовы
из этого экземпляра передают его дальше. Единственный владелец места — `WholeProgram.Solver.LibrarySite`:
его читают прямые вызовы, локальные функции, делегаты (включая работу, таймеры и модели),
dispatch, запасные экземпляры без получателя и конструкторы компараторов. Корни, DI и
инициализаторы места не получают. Лимит контекстов и бюджет SCC сливают библиотечные тела
внутри места; открытая подстановка тоже сохраняет место слитого экземпляра.

Место входит в контексты экземпляров и регионов, идентичности и группы открытых регионов.
Создатель региона определяется прежней парой тела и полного контекста. Имена и ключи ресурсов
места не содержат; провайдер созданного библиотекой scope именуется по видимому имени scope,
а не по его контексту. Статика библиотеки остаётся общей для процесса.

`CallSiteContextMatrixTests` содержит 99 клеток, два служебных факта и четыре отдельных факта:
105 тестов. Матрица наблюдает достижимость создающего тела, идентичности и имена всех 19 видов
регионов, три расположения мест, 12 путей и четыре режима слияния. Для объектов, замыканий,
нового результата модели и struct в поле она также наблюдает ресурс, прочитанные в библиотеке
маркеры и пары. Объекты этих клеток публикуются, чтобы проверка пары не завершалась раньше на
владении `ThreadConfined`; объекты двух разных мест при этом всё равно не образуют пару.
Список `Wider` пуст.

Отдельный регрессионный факт проверен без переноса места: два разных места через общую
фабрику библиотеки ошибочно дали пару, тест упал. После восстановления реализации этот факт

### Остановка на gate задачи 2

Серверный gate `context` завершился с кодом 1 на пробе H3: demo с записями — 277 находок,
с допущенными телами — 293, контроль — 281. Добавлены 16 отпечатков, исчезнувших нет.
Матрица задачи 2 и проверки до пробы прошли; полное совпадение находок demo не достигнуто.

Повторная диагностика ограничена двумя исходниками `PollyNestedRetry` и `PollyRetryAttempts`,
скомпилированными как отдельная фикстура с телами Polly 7.2.3. Полная проба повторно не
запускалась. Чужие воркеры в этой фикстуре уже не исполняют делегаты друг друга. Для лишнего
отпечатка `beab0b89c04944ad` (`AsyncRetryWorker._joined`) остаётся иной предел: один прямой
`Task.Run` тела проекта создаёт один несклеенный регион задачи, но два исполнения в одном
дереве — под корнем, где проходит начальная часть async-тела библиотеки, и под продолжением
этого тела, где цикл проходит снова. У этих исполнений разные родители. Доказательство
своего прохода отклоняет прямой `await` этой задачи с причиной `source`: `HandleExecution`
принимает только единственное исполнение региона задачи в дереве ждущего.

Правило A сохраняет нынешнее поведение задачи `Task.Run`, правило B — контексты тел программы.
Разделение двух разных допущенных мест эту неоднозначность внутри одного места не устраняет.
Для удаления этой находки требуется дополнительное доказательство происхождения handle по
текущему исполнению/проходу, когда один регион задачи обозначает несколько исполнений в
одном дереве. Это механизм за пределами A и B; по правилу остановки движок, ожидания и
защищённые файлы не изменены. На этой проверке задача 2 остановлена до решения о границе приёмки.
Диагностический тест прошёл (один факт, без пропусков), отдельная проверка артефакта подтвердила
одного производителя, один регион, два исполнения и отказ `source`
(`scratch/h3a/retry-diagnostic.log`, `scratch/h3a/retry-blocker.log`). Временный тест и его
объёмные дампы удалены; модели demo в этом повторе не перезаписывались, поскольку движок
не менялся.

## Снимок model evals

Снимок `skills/hunt/evals/models/generator-snapshot.json` содержит перезапись оркестратора,
разрешённую D-0022 и D-0023 (R6, R7). До неё G5 перед code review падает только на
