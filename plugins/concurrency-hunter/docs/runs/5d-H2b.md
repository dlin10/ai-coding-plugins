# 5d run H2b — записи ретраев Polly 7 и исключительный конец задачи под `await`

База сравнения — `6e88824` (`HEAD` при записи). Требования рана — строка «5d run H2b» [PLAN](../PLAN.md) и вопрос 204 при допущениях [ADR 0030](../adr/0030-ordering-assumes-the-default-thread-context-unless-visible-code-installs-another.md): две встроенные записи ретраев Polly 7; правило «исключительный конец ожидаемой задачи не несёт завершения дочерней работы, которую задача оставила, выйдя исключением до её join» для `await` в обеих формах вопроса 204; попытки ретрая под записями; demo-кейс `polly-retry-attempts`; замер eShop 36 → 32. Нового ADR нет. Порог однократности допуска `sequential-awaited` по проходу (вопрос 210) — run H2c: в H2b он не построен и не обойдён, 30 находок сидинга eShop, которые он держит, остались.

## Решения

- D-0001 — Фиксы код-ревью проверяются коротко после каждого хода, полностью — в конце рана (`gate=targeted`, `fullGate=final`).
- D-0002 — Объём — строка H2b, вопрос 204 и ADR 0030, ничего сверх. Порог однократности `sequential-awaited` по проходу (вопрос 210, H2c) не строится и не обходится; всё, что требует нового механизма или ADR, идёт в QUESTIONS.
- D-0003 — Ветка `feature/race-hunter-h2-attempt-1` (`7b36aa6`) для H2b не заготовка: с неё перенесена только тестовая фикстура Polly 7.2.3.
- D-0004 — Две записи в формате H1 (`receiver`, `fates.action.runs`), сборка `Polly` от 7.0.0.0 до 8.0.0.0 исключительно, без фильтра исключений, удерживаемых слотов, `onRetry` и привязки по MVID; запись выбирается по статическому типу получателя.
- D-0005 — Вопрос 204 по образцу фикса F-0036 из H2a: обе формы — прямой выход до join и ожидание внутри задачи, пропущенное исключением более раннего ожидания.
- D-0006 — Demo: `Polly` 7.2.3 в `Demo.Web` рядом с `Polly.Core` 8.7.0; два однократных hosted worker-а, без вложения одного ретрая в другой.
- D-0007 — Приёмка eShop — замер опубликованным exe с `--generation off`, 36 → 32; эталон — проба с проектной записью тех же двух членов; другое число встроенной записи — стоп, а не расширение.
- D-0008 — Нового ADR нет; SPEC и CONTEXT правятся в этом ране. Полный suite и `check-test-baseline.ps1 -Record` — на гейтах и в конце рана; в батче — тесты правила и проверка, что новый тест падает без правки; модели demo перезаписываются в каждом батче, меняющем движок.
- D-0009 — Контроль в кейсе demo у каждой записи: в каждом из двух сервисов положительная пара (снята) и контроль (остаётся).
- D-0010 — Исключение более раннего `await`, не пойманное до join, считается выходом исполнения только в запросах с `exceptionalExits: true` (`LeavesWorkRunning` и двойник в `PassCompletionProof`); остальные запросы потока читают `await` как раньше.
- D-0011 — Асинхронный член записан id `M:Polly.AsyncPolicy.ExecuteAsync(System.Func{System.Threading.Tasks.Task})~System.Threading.Tasks.Task`: встроенный слой сравнивает id точной строкой, и каждый не-void id в `BuiltInTable.txt` несёт `~ReturnType`.
- D-0012 — С ветки `7b36aa6` перенесены только `PackageDownload` и копия `Polly.dll` в `ConcurrencyHunter.Core.Tests.csproj` и имя `"Polly"` в `Fixtures/LibraryPackages.cs`. Правки, которых из-за самой записи требуют прежние тесты встроенного слоя, написаны заново. Запись рана H2a не правится.
- D-0013 — Новые истинные находки в прежних кейсах demo допускаются и перечисляются в записи рана.
- D-0014 — Такая находка получает запись `expected-findings.json` с `phase` `"5d"` и строку в записи рана; запись завершённой фазы не правится. Сдвиг, который потребовал бы правки такой записи, и находка, ложная по чтению кода, — стоп.
- D-0016 (заменило D-0015) — В ран входят join-ы-`await` из `Summary.Joins`, в том числе `await` задачи допущенного вызова (`ProveCallTask`), и выход исключения `await` в `Flow` только для запросов `exceptionalExits: true`, только где разрез не держит этот `await`. Кандидаты входа хвоста префиксных `await` остаются как были: их флаг ничто не читает, а исключительный путь первого `await` уже лежит в префиксе. Сторона ожидающего и остальные виды join-ов не входят и записаны вопросами 211 и 212.
- D-0018 — Сборка откатана к задаче 3, работа задач 3–6 сверена с текстом задач. `Task.WhenAll` под `await`: перечисление задач перед `await` читается как обычный вызов, который может бросить (клетки `EarlierWhenAllWithTheChild` ждут пару), а у блокирующего `Task.WaitAll` перечисление — часть ожидания; различие записано вопросом 213.

## Что построено

- Записи ретраев (R1): `Providers/LibraryModels/BuiltIn/polly.json` — сборка `Polly`, версии сборки от 7.0.0.0 включительно до 8.0.0.0 исключительно; `Policy.Execute(Action)` на `T:Polly.Retry.RetryPolicy` — делегат `action`, судьба `invoke-now`, запуски `sequential`; `AsyncPolicy.ExecuteAsync(Func<Task>)` на `T:Polly.Retry.AsyncRetryPolicy` — `invoke-now`, `sequential-awaited`. `LibraryModels.LoadBuiltIn` читает восемь встроенных файлов. Вызов на получателе, объявленном как `Policy`, `AsyncPolicy`, `ISyncPolicy`, `IAsyncPolicy`, на `RetryPolicy<T>`/`AsyncRetryPolicy<T>`, другая перегрузка и сборка вне диапазона записи не берут; сборка вне диапазона сообщается тем же способом, что любая другая, которую называет встроенный набор.
- `await` задачи, оставившей работу (R2): `HappensBefore.EnsureJoins` кладёт в множество блокирующих ожиданий и join-ы-`await` (прежнее исключение `join.Kind != SummaryJoinKind.Await` снято), поэтому `WithoutRunningWork` и `LeavesWorkRunning` решают и для `await`: исключительный выход `await` задачи, которая может выйти исключением, пока работа, которой её join-ы дожидаются на нормальном пути, ещё идёт, перестаёт читаться как завершение этой работы. Нормальный выход `await`, `await` задачи, не оставляющей работы, и ожидающий без обработчика читаются как раньше.
- Join, пропущенный исключением более раннего `await` (R3): `Flow` хранит исключительные шаги `await`, бросающих только после завершения их задач, отдельно от шагов блокирующих ожиданий (`_awaitExits` рядом с `_waitExits`). Их берут только запросы `exceptionalExits: true` — `AlwaysFollows` и `BeforeReturn`, а через них `LeavesWorkRunning` и доказательство прохода `PassCompletionProof` (`BeforeReturn(…, exceptionalExits: true)`) — и только там, где разрез не держит ворота этого `await`. Остальные запросы потока (`Precedes`, `Dominates`, поднятые места вызова) читают `await` как раньше. Исключение `await` группы `Task.WhenAll`, перечисляющей дочернюю задачу, поздний join дочерней задачи из места после вызова `Task.WhenAll` не обходит: ворота выхода те же, что у любого ожидания не более того, чего ждёт группа, и поздний join, ожидание одной дочерней задачи, держит их закрытыми.
- Попытки ретрая под записями (R4): кода нет. `PollyRetryAttemptMatrixTests` — 102 случая — проходит на рабочем дереве и с `HappensBefore.cs` и `PassCompletionProof.cs` из `HEAD` при записи Polly: ни одна клетка не сдвигается от R2–R3. Ключевой получатель виден в паре работы попытки с кодом после вызова (`AfterCall`): попытка, дожидающаяся своей работы на каждом пути, упорядочивает её с кодом после вызова только под записью. Пересечение попыток между собой (`NextAttempt`) от получателя не зависит: делегат непрозрачного вызова, отданный из одного места исполнения, которое идёт один раз и проходит это место один раз, идёт по одному (CONTEXT, **Unknown execution**). Проверка «падает без правки»: с `polly.json`, убранным из списка `LoadBuiltIn`, краснеют 10 из 102 случаев — 6 клеток `Keyed × AfterCall` с `JoinsChild` и `CaughtThenJoin` (`Sync` 2, `Async` 4), 2 клетки списка «шире» `Async/Keyed/EarlierAwaitCaught × NextAttempt` (их пара держится только под записью) и 2 строки `Joins` теории; остальные 92 зелены и без записи — это контроль неизменного поведения (клетки `Base` и `Interface`, клетки `NextAttempt` вне списка «шире», строки `Leaves` теории) и проверки устройства матрицы (`Cells_cover_every_value_of_every_axis`, `Every_wider_cell_names_a_cell_that_expects_no_pair`). Теория `Await_of_the_retry_call_past_the_catch_keeps_the_pair_of_a_child_an_attempt_left` проверяет покрытие обоих маршрутов цели `await` (`HappensBefore.Prove` → `ProveCallTask`): строки `Leaves` держат пару и без записи, и с `HappensBefore.cs` и `PassCompletionProof.cs` из `HEAD`, так что правило «новый тест падает без своей правки» к ним не применяется; строки `Joins` снимает пару запись (с файлами из `HEAD` при записи они тоже без пары, без записи пара держится), а не правки задач 2–3.
- Комментарии `HappensBefore.cs` и `PassCompletionProof.cs`, говорившие, что `await` читается как всегда, поправлены под R2–R3 там, где они ещё говорили это.
- Кейс demo `polly-retry-attempts` (R5): `demo/Demo.Web/Cases/PollyRetryAttempts.cs`, два `BackgroundService` — `SyncRetryWorker` (`RetryPolicy`, `Execute`) и `AsyncRetryWorker` (`AsyncRetryPolicy`, `ExecuteAsync`); в каждом положительная попытка (`Task.Run` пишет `_joined`, попытка его дожидается) и контроль (`Task.Run` пишет `_left`, попытка может бросить до его ожидания). Пять типов, которые есть в `Polly` и в `Polly.Core`, кейс не называет. Ожидания (`findings` — `/sync-left`, `/async-left`; `notDefects` — `/sync-joined`, `/async-joined`) записаны в `expected-findings.json` и в таблицу 5d `SCENARIOS.md` до прогона.

## Документы

- SPEC TD-060 — фраза о том, что завершение задачи не доказывает завершения работы, которую она запустила, распространена на `await` и на join, пропущенный исключением более раннего `await`; фраза о независимости `await` от допущений уточнена: нормальный возврат от допущений не зависит, исключительный выход `await` зависит только через блокирующие ожидания внутри ожидаемой задачи, и такие пары считает `assumed`.
- CONTEXT — статья **Join**: одно уточнение о задаче, которая может выйти, оставив работу, для `await` и блокирующих ожиданий.
- QUESTIONS — вопрос 204 закрыт (→ SPEC TD-060; CONTEXT, «Join»); в строки 207 и 208 добавлено по одной фразе: гранулярность «по исполнению, а не по дочерней работе» и «один флаг на поднятое место вызова» теперь относится и к `await`. Открыты (5g): 211 — сторона ожидающего (`try { await a; await b; } catch (Exception) { } After();` упорядочивает работу `b`, хотя исключение `a` пропускает её join; у блокирующих ожиданий пара остаётся) и выход исключения `await` во всех запросах потока; 212 — тот же пробел у возврата `Parallel.For`/`ForEach`, ожиданий таймера и возврата допущенного вызова `sequential-awaited` без задачи; 213 — `Task.WhenAll` под `await`: перечисление задач перед `await` читается как обычный вызов, который может бросить, а у блокирующего `Task.WaitAll` перечисление — часть ожидания (клетки `EarlierWhenAllWithTheChild` `AwaitLeavingWorkMatrixTests` ждут пару, D-0018); 214 — `await`, который возвращается к попытке и идёт к её join (причина списка «шире» `PollyRetryAttemptMatrixTests`). Список «шире» `AwaitLeavingWorkMatrixTests` (задачи 2 и 3) пуст, у него причин нет.
- PLAN — строка H2b «построено», абзац фазы 5d дополнен состоянием H2b; строка H2c и порядок ранов не менялись.
- SCENARIOS и `expected-findings.json` — кейс `polly-retry-attempts` (записаны до прогона).
- Уточнение к записи рана [H2a](5d-H2a.md): она называет записи Polly, удерживаемые слоты и прочее ядро первой попытки «оставленными для H2b». Бриф H2b (D-0003, D-0012) уточняет: ветка `feature/race-hunter-h2-attempt-1` для H2b не заготовка. `polly.json` ветки с удерживаемыми слотами, `RetainedSlots`, `LibraryVocabulary.Retained`, `ExceptionTransitions`, `Launch/*`, `H2ProbeTests` и черновики ADR 0031–0042 построены на подходе, который ADR 0030 заменил, и относятся к вопросам 195–199 фазы 5g. С ветки перенесена только тестовая фикстура Polly 7.2.3; записи и правила H2b написаны заново. Запись H2a не правилась.
- Отложенная правка гайда: `docs/concurrency-hunter-guide.ru.html` (строка 1894) говорит, что в `Core/Providers/LibraryModels/BuiltIn/` «семь JSON-файлов»; с `polly.json` их восемь. Гайд ран не трогает; правка отложена.
