# PRD Codex Session Pulse P0

Источник: [issue #249](https://github.com/dlin10/ai-coding-plugins/issues/249); рядом лежит [спецификация v1.3](spec.md).

- [Спецификация v1.3 — `plugins/codex-session-pulse/docs/spec.md`](https://github.com/dlin10/ai-coding-plugins/blob/main/plugins/codex-session-pulse/docs/spec.md) — источник истины; до слияния лежит на ветке `claude/great-bohr-s4vriv`.

## Цель

Поставить локальный Codex-плагин для Windows 11 x64, который показывает компактный неактивирующийся WPF-оверлей над Codex Desktop. В оверлее видны последние наблюдаемые cache read и input, оценка TTL и статус источника. Метрики относятся к одному автоматически выбранному потоку. Продукт читает локальные rollouts и работает без сетевых запросов.

## Ключевые решения

- Плагин называется `codex-session-pulse` (имя `session-pulse` занято Claude-модом), живёт в `plugins/codex-session-pulse/`, регистрируется только в `.agents/plugins/marketplace.json`; структура, workflows и документация — по конвенциям соседних .NET-плагинов (спека §4.2).
- Поставка framework-dependent: один `win-x64` WinExe, требует .NET 10 Desktop Runtime; EXE — GitHub Release asset, который cmd-launcher из `bin/` скачивает при первом запуске; в git бинаря нет (§10).
- Один EXE остаётся: путь `--hook` не загружает WPF и укладывается в тёплый старт ≤150 мс; отдельный hook-бинарь — записанный запасной вариант, если порог не достигается (§4.4 п. 1).
- Hooks — усилитель, не фундамент: после каждого релиза плагина они требуют повторного Review hooks, поэтому overlay работает по JSONL в `Auto · inferred` и запускается вручную (§4.4 п. 7). `hooks.json`: `commandWindows`, `async` для `SessionStart`/`UserPromptSubmit`, `timeout: 3` для `SessionEnd`, без matcher.
- TTL — настраиваемые 30 минут как гипотеза, обучение в P1; скорость в P0 показывается как «—», rate limits не показываются (§6.2, §6.4).
- Named Pipe и удаление состояния по `SessionEnd` с tombstones остаются как в спеке; pipe получает `CurrentUserOnly`, SID и версию в имени (§4.4 п. 2).
- Правило «что считается окном Codex» — настраиваемый список имён процессов и фильтр заголовка, уточняется измерением в #250 (§3.3).
- Контракт снимка для UI зафиксирован в §4.3, поэтому #251 начинается параллельно с #250 на синтетических фикстурах, а #253 — параллельно с #252 на стаб-снимке.

## Критерии приёмки

- [ ] На Windows Desktop оверлей не перехватывает фокус, следует за окном Codex по правилу §3.3 и завершает работу после закрытия последнего такого окна.
- [ ] Main и fork отслеживаются отдельно, выбор потока автоматический, неопределённость отображается явно; при двух и более окнах Codex — не выше `inferred`.
- [ ] Последний наблюдаемый cache hit отделён от оценки TTL. Скорость в P0 отображается как «—».
- [ ] Один WinExe обслуживает короткоживущие hooks и долгоживущий overlay; тёплый старт `--hook` ≤150 мс измерен. Неоднозначный `SessionEnd` не очищает состояние активного потока.
- [ ] Без hooks (не доверены после обновления или отключены) overlay работает по JSONL в `Auto · inferred`, диагностика это показывает, ручной запуск `--overlay` документирован.
- [ ] Пройдены сборка, тесты, `npm run validate:plugins`, проверка установки из каталога с Review hooks и smoke framework-dependent пакета в чистой Windows Sandbox с .NET 10 Desktop Runtime и без SDK.

P0 не включает UI Automation для выбора вкладки, эксперимент Auto Warm, расчёт скорости и показ rate limits. Источник требований — спецификация v1.3; критерии #250–#254 выведены из неё, не только из этого PRD.
