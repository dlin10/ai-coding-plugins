Inside the plugin · a beginner’s guide

Cache Detective
from idea to implementation

The plugin reads C# code and maps the relationships between caches and data to find places where the data may change while a stored copy stays the same.

We will first explain the overall algorithm using a product example. Then we will trace how Roslyn, the graph, rules, and MCP tools implement it. You only need to know what a method, a variable, and a function call are; other concepts are introduced along the way.

01 / the big picture

What problem does it solve?

Cache Detective looks for structural risks of stale and inconsistent cached data. The problem is not limited to one cache entry and the database: a single change can affect a product card, a catalogue list, a composite response, and data in another project. Correctly deleting one copy does not mean that the others will be refreshed.

There are two common ways to limit staleness: delete the relevant entry after its source changes, or give it an expiration period—TTL, time to live. Deleting an entry so that the next request fetches the data again is called invalidation. This may happen in the same method, through a helper call, or after a message is delivered.

Cache consistency and cache coherence

To understand the plugin’s capabilities, it helps to distinguish two questions. Cache consistency: does the stored copy reflect the current source data? Cache coherence: do related cached copies and representations agree with one another after a change? We are discussing application data here; these questions overlap, and these terms are not separate plugin rules.

For example, a product’s price changes from 100 to 120. The application deletes product:42, and the next request refills the product card with a price of 120. But nobody deletes catalog:list, which is also built from product data. The user sees different prices for the same product on two screens.

If both fill paths are recognized, the plugin links both keys to the same table and can report the missing list invalidation through UNGUARDED_WRITE. If one stored result is built from another cache, STALE_PARENT_KEY also applies. Coherence is therefore checked through dependencies and invalidation coverage, rather than a universal comparison of all caches with one another.

The plugin helps answer four questions:

  • Which stored results could this change make stale?
  • Does suitable invalidation reach every known dependent copy?
  • Does the command delete an existing key in the correct store?
  • If there is no invalidation, is the recognized TTL within the allowed staleness period?

Which problematic scenarios does it detect?

These are practical situations, not a list of new rules. Several situations may trigger the same rule, and one mistake may produce several findings (Finding). Detection depends on recognized paths, workspace completeness, and TTL conditions; the exact conditions are given in the rules section.

What else can it help establish?

Whether the risk is visible right now. Optional runtime verification compares accessible cache fields with permitted database rows. A field difference or evidence of a later write may produce an observation of possible. This supplements a static finding; it is not a new rule or a guaranteed check of any computed value. See the live-data section.

Where unknowns obstruct the investigation. The plugin exposes unresolved analysis (Unresolved): for example, a key it cannot determine, SQL it cannot parse, or a missing interface implementation. This distinguishes “no problems found in the known paths” from “the necessary path could not be investigated.” These entries do not by themselves prove a cache defect.

What does “detect” mean here?

The main analysis is static: the plugin examines code without running the indexed application. It produces a finding with a rule, confidence, and an evidence chain (Chain). The likely level means an inference; unknown means substantial incompleteness. The tables and examples in this section describe risks that can be established within this model.

A complete guarantee of cache coherence requires more. The plugin does not model every cache-fill race, event delivery order, replication between physical cache nodes, or per-request value flow. For example, the race “read the old price → another request changes the database and invalidates the cache → the first request writes the old price back” may go unnoticed even when an invalidation is found. Mass simultaneous refilling after a miss (cache stampede), caching efficiency, and memory usage are also outside these rules. Other boundaries are described separately.

Sources: README.md, CONTEXT.md, UnguardedWriteRule.cs, StaleParentKeyRule.cs, OrphanInvalidationRule.cs, ExternalNoTtlRule.cs. Key-coverage subtleties are covered in section 07 and section 08.

02 / the complete algorithm

Collect facts first, then ask questions

The unit of analysis is a workspace: a set of solutions or projects, API recognition settings, mappings between projects, and, when needed, one database. All information is combined into a shared graph.

  1. Load the code. MSBuild helps Roslyn understand projects, references, and types.
  2. Find the application’s entry points. Follow calls from HTTP methods, message consumers, and background tasks.
  3. Record operations. Who reads a table, who changes it, who reads or fills the cache, and who deletes an entry.
  4. Normalize names. For example, turn $"product:{id}" into the template product:{id}, and reduce different data-access approaches to dbo.Products.
  5. Compute dependencies (depends_on). From each key being filled, trace what its filling methods and their callees read.
  6. Check the rules. Compare source changes with reachable invalidations and the allowed staleness period.
  7. Keep the explanation and the gaps. Every relationship has provenance; a construct that cannot be analyzed becomes a separate unresolved entry (Unresolved).

The key simplification: cache contents are opaque

The static analysis does not try to prove which fields make up the object passed to Set. It considers reads in the filling method and methods reachable from it. The same model therefore works for an EF object, a SQL result, a DTO, or a calculated price.

The cost of this simplification: dependencies are determined at the method and table level, rather than by tracing each field precisely into each cache write. A read that does not affect a particular stored object can also enter the model. This is a useful risk map, but not proof that all operations execute within one real request.

03 / a worked example

From two methods to one warning

Below are teaching examples of controller methods. Assume that db.Products maps to the table dbo.Products, and cache has type IMemoryCache.

public Product Get(int id)
{
    var product = db.Products.Find(id);
    cache.Set($"product:{id}", product, TimeSpan.FromMinutes(10));
    return product;
}

public void Rename(int id, string name)
{
    var product = db.Products.Find(id);
    product.Name = name;
    db.SaveChanges();
    // No invalidation of the corresponding cache entry here.
}

For clarity, reading an existing cache entry is omitted: a real application usually calls TryGetValue before querying the database. Dependency analysis primarily needs the fill path.

  1. Get produces the edge Reads → dbo.Products and the edge Caches → product:{id}.
  2. The key receives the role cache: its stored result depends on data that was read.
  3. Rename produces the edge Writes → dbo.Products: the entity change is accompanied by SaveChanges.
  4. The rule finds a match between the dependency source and the data being changed. No suitable invalidation is found from Rename.
  5. The TTL is 600 seconds. With the default staleness budget (Budget) of 60 seconds, the finding remains visible: UNGUARDED_WRITE.

How changing the code changes the result

Change to the teaching exampleWhat the rule does
In Rename, add cache.Remove($"product:{id}")Finds a matching invalidation in the same store; does not create this finding.
Set the TTL to 30 secondsKeeps the finding with the property suppressed: true: the lifetime is within 60 seconds. Normal output hides these entries but counts them.
Delete products:{id}The forms differ. There may be an unguarded-write warning as well as findings about an orphan invalidation and a close pattern mismatch.
Delete the same textual key in RedisThe invalidation does not cover memory: identity includes the store.

04 / the model’s language

What is in the graph?

A graph is a set of objects, called vertices, and relationships between them, called edges. A vertex answers “what is it?”, and an edge answers “how is it related to another object?” For example, a method and a table are vertices; a read from the method to the table is an edge.

VertexWhat it representsImportant detail
Cache key CacheKeyTemplate, store, TTL, tags, and role.One vertex per (Template, Store) pair, not for each actual value of id.
HandlerA method reached from an entry point; this may also be a helper method.Identity: solution + method symbol. The project is stored separately.
TableA common source for EF, SQL, and database objects.The name schema.name; the database name is an attribute, not part of the identity.
EventA message contract between a publisher and a consumer.Identity is the fully qualified type name, including its namespace.
External source (ExternalSource)An HTTP or gRPC read.May become a link to code in another project or remain a terminal source.
Stored procedure, trigger, viewNamed SQL Server objects.Extend read and write paths beyond C#.

In the code, the type hierarchy restricts valid relationships: ReadSource can read; WriteSource can also modify data. A view inherits from the former; writes through it are not described by this model.

EdgeDirection and meaning
Reads / readsFrom a reader to a table, key, view, or external source.
Writes / writesFrom a writer to a table, with the operation kind: INSERT, UPDATE, DELETE, or TRUNCATE.
Caches / cachesA handler fills a key.
Invalidates / invalidatesA handler deletes an entry by key, tag, or prefix.
Calls / callsA call to another method or stored procedure.
Publishes / publishesA handler publishes an event.
Consumes / consumesAn event reaches a handler.
Serves / servesAn external source (ExternalSource) is mapped to a serving method.
Fires / firesA table change can activate a trigger.

A dependency (depends_on) is computed on demand over these edges. It is not stored as another independent truth. The computed result is kept in memory for reuse and invalidated when the graph changes.

Types: GraphModel.cs. Data ownership and indexes: CacheGraph.cs.

05 / architecture

Three parts with different responsibilities

01 · C#

Core: CacheDetective.Core

Accepts a Roslyn Solution object, extracts relationships, stores the graph, and runs rules. The catalogue component accepts an already-open database connection. Loading files by path is not the core’s responsibility.

02 · C#

Shell: CacheDetective.Cli

Reads settings, loads projects through MSBuild, opens connections, serves MCP, and assembles compact responses. Live-data verification also lives here.

The third part is the agent workflow: skills/scan/SKILL.md defines the order of tool calls and report preparation. The agent explains findings and may propose annotations (Annotation); ordinary C# code constructs the underlying static facts.

MCP, Model Context Protocol, is the communication contract between the agent and the server. A tool call is a structured request such as “show issues” or “explain this key.” Running cachedet mcp starts a server that communicates through the process’s standard input and output. Logs go to standard error so they do not interfere with the protocol.

Program.RunMcpAsync registers WorkspaceSession as a singleton: one instance lives for the server’s lifetime. The session owns the graph, configuration, latest indexing results, and annotations (Annotation). SemaphoreSlim(1, 1) protects sequential access: two requests must not modify shared state simultaneously.

During reindexing, ReplaceSolution replaces the contribution from a particular solution. Other solutions and the catalogue remain in the shared graph. Record provenance makes it possible to remove old information and then rebuild shared vertices. ReplaceDatabase performs the equivalent replacement for the catalogue.

Why the core does not load .sln files itself

A test can create source code directly in memory, obtain a Solution, and verify analysis without disk access or MSBuild. Slow, environment-dependent loading is tested separately. This is a simple boundary: “understand code that is already loaded” is separated from “prepare code to be understood.”

How the executable is packaged

The current distribution targets Windows x64 and the .NET 10 SDK. The CLI is published as a single cachedet.exe that depends on an installed .NET runtime. IncludeAllContentForSelfExtract includes resources that are extracted at startup, including BuildHost, which MSBuildWorkspace launches as a separate process. So “one file in the distribution” does not mean “no other files or processes internally.”

Program.cs, WorkspaceSession.cs, ADR 0002, ADR 0001.

06 / the code indexer

How Roslyn turns C# into relationships

The code indexer uses Roslyn, the C# compiler infrastructure. The syntax tree shows how an expression is written; the semantic model tells us which type and method it refers to. This matters: two methods named Get may belong to completely different libraries.

Loading already affects result quality

MsBuildSolutionLoader.LoadAsync opens .sln, .slnx or .csproj. It collects diagnostics and loading-coverage information. Loading errors do not become “no problems found.”

  • Loading settings disable treating warnings as errors. This does not edit project files.
  • Analyzer references missing from disk are removed with a diagnostic; source generators are not globally disabled.
  • For a multi-targeted project, the first loaded variant for its file path is retained: not all target frameworks are analyzed at once.
  • The loading report counts C# and VB projects, but CallGraphIndexer itself selects C# projects. Successfully loading VB does not mean its code is fully analyzed.

Where traversal starts

FindEntryPointsAsync looks for public controller actions, Minimal API registrations, gRPC methods, MediatR request handlers, consumers of recognized messages, BackgroundService.ExecuteAsync, IHostedService.StartAsync and IJob.Execute. Specific type, interface, and name checks apply; a method does not become an entry point merely because it is public.

Breadth-first traversal, not an arbitrary file-reading order

CallGraphIndexer.IndexAsync first queues all entry points. It then processes their direct calls, followed by the next level. This is breadth-first search, or BFS. Each method symbol is expanded once, at its minimum distance from any entry point. The depth limit is 12 call hops.

For an interface call, Roslyn searches for implementations in the loaded solution. One available implementation produces an edge with confidence confirmed; several produce likely edges, because the actual runtime choice is unknown. A missing implementation is recorded as unresolved analysis (Unresolved) of kind call.

When expanding a method, EF and SQL facts are collected first; calls are then checked by the cache, event, and external-request analyzers. Ordinary calls become Calls. After traversal, deferred message publications are resolved, EF mutations are linked to saves, and roles (Role) are computed.

CallGraphIndexer.cs, MsBuildSolutionLoader.cs, ADR 0014.

07 / keys and operations

How to recognize a cache call and recover its key

A recognizer describes a library

A cache call site (Sink) is a specific call to Get, Set or Remove. To understand it, CacheCallAnalyzer uses a declarative description: the API type’s full name, a store label, method names, and argument positions for the key, TTL, and tags.

An operation’s semantics (Semantic) answers “what does this call do to the entry?”: get, set, remove, remove_by_tag, remove_by_prefix, increment, expire or lock. It does not describe the meaning of the stored object.

// A shortened example of a built-in description’s structure.
new CacheRecognizer(
    "Microsoft.Extensions.Caching.Memory.IMemoryCache",
    "memory",
    [new("Set", CacheSemantic.Set, 0, 2),
     new("Remove", CacheSemantic.Remove, 0)]);
// Zero-based positions: argument 0 is the key; argument 2 is the TTL/options.

Built-in descriptions cover IMemoryCache, IDistributedCache, HybridCache and StackExchange.Redis.IDatabase. Argument offsets are accounted for with extension methods. A name pattern such as StringGet* covers the corresponding method variants.

A custom library is declared in the caches section. A configuration description has confidence confirmed as an explicit project assertion about its own API; a description supplied through an annotation has confidence likely. A user-provided type description replaces the built-in description for the same type. For GetOrCreate, the semantics (Semantic) are set: the call can fill the cache.

Expression folding: compute what is known, name what is unknown

StringConstantFolder reads literals, constants, available field initializers, interpolation, string concatenation, Format, Concat, Join, and helper-method source code. Up to five hops through such methods are allowed. The application is not executed.

ExpressionRepresentation in the analysis
"product:42"Fully known text product:42.
$"product:{id}"Template product:{id}. The parameter’s name is known; its actual value is not.
"product:" + opaque()If the call cannot be analyzed: product:{?}, with a reason for incompleteness.
opaque()If there is no known literal segment, no nameable key is created; the operation is kept pending resolution.

Branching produces a set, not the first assignment

var key = compact ? $"product:{id}" : $"product:full:{id}";
cache.Remove(key);

Folding produces a template set. Here, two elements are possible. For a write, each nameable element becomes a graph key. For an invalidation, each is only a possibility: one will be selected at runtime.

The set is limited to eight distinct results. The bound is checked after combinations: three alternatives on the left and three on the right can produce nine strings. Overflow, an unnameable part, or self-appending through += leaves a Collapsed flag. It propagates into a composite expression even when only one element remains visible after folding.

One visible string does not guarantee an unambiguous result. An invalidation receives InvalidationModality.Must only when there is one element and no Collapsed. Otherwise it receives May: it remains in the evidence but does not clear an unguarded-write warning.

Here, Must describes whether the recovered key is unambiguous. It is not proof that a condition, exception, or concurrent request can never prevent the invalidation from executing.

A key can be an object (Key object)

Some libraries pass a key object, rather than a string, to the API. For example, new CacheKey("Nop.category.all.{0}-{1}-{2}"), with a factory substituting the arguments storeId, roleIds, showHidden. Describing the type, constructor argument, and factory makes it possible to obtain Nop.category.all.{storeId}-{roleIds}-{showHidden}.

The analysis recovers argument names, but does not compute a hash of an identifier list or other internal library transformations. The Orchard CacheContext form, where identity is assembled through a chain of contexts, is not supported by this mechanism.

CacheRecognizer.cs, CacheCallAnalyzer.cs, StringConstantFolder.cs, KeyTemplateFolder.cs; ADR 0015, ADR 0016.

08 / merging and classification

When are two writes treated as one key?

The same template under the same store label is merged into one vertex. For example, (product:{id}, memory) and (product:{id}, redis) are different vertices. Names such as memory, distributed, hybrid, redis come from API descriptions; the static analysis does not reconstruct connections or DI instances themselves.

TTLs are merged using the longest lifetime

If one site writes for 30 seconds and another for 600, the merged lifetime is 600. If at least one site has no recognized TTL, the merged lifetime is unknown: for staleness protection, it is treated as unbounded. A short-lived write must not hide the risk from a long-lived one.

There are separate accumulators for writes and other observations: if actual Caches operations exist, the key’s properties come from them. Therefore, a Get call without a TTL does not erase the lifetime recognized on Set. TtlAgreed preserves whether all write lifetimes agreed.

Tags need to be merged in two ways

Suppose one site writes a key with the tag catalog, while another writes it without that tag. For tag invalidation to count as complete protection, the tag must be present on all writes: use the intersection TagsAll. To determine whether a command deletes anything at all, a tag on even one write is enough: use the union TagsAny.

Why a Redis session is not automatically a cache

The role cache means a copy of other data. The role store means the entry is itself a store: a session, lock, counter, or token. The second category has no source against which it can become stale.

  1. Store indicators come first. Prefixes session:, lock:, idempotency:, ratelimit:, token:, increment/expire/lock operations, and conditional writes such as When.NotExists produce store.
  2. Then look for a path to data. If the filling method reaches a source read, the result is cache.
  3. No reads and no blocking gaps. The result is store; a pure computation without an external source is classified this way too.
  4. No established read, but the analysis is incomplete. The result is unknown and an unresolved entry (Unresolved) of kind role, with links to the blocking gaps.

Order matters: an explicit store indicator is checked first. Classification is recomputed after a gap is resolved. For performance, CacheRoleIndex reuses data-reachability and blocker information instead of traversing the whole graph again for every key.

CacheGraph.cs: KeyAccumulator and KeyFacts, CacheRoleClassifier.cs.

09 / data sources

How EF, SQL, and the database meet in one vertex

EF Core: from an entity to a table name

EfReadAnalyzer extracts mappings from DbSet<T>, ToTable and [Table]. The current implementation first collects conventions based on DbSet property names, then applies fluent settings, and then attributes. This is the analyzer’s specific ordering; it does not fully reproduce EF Core’s runtime model-building process.

Entity reads are reduced to tables (Table). The default schema is dbo. This lets db.Products and the SQL expression SELECT ... FROM dbo.Products meet in the same vertex, even though they look completely different in C#.

Changing an object in memory is not yet a database write

EfWriteAnalyzer first collects facts about possible mutations and SaveChanges. For tracked mutations, a write appears when a save exists in the accumulated facts. For ExecuteUpdate and ExecuteDelete, no save is required: these APIs perform changes directly.

Code patternHow it is handled
Add / Update / Remove and Range variantsAn explicit mutation that requires SaveChanges.
Assigning a property after reading an entityA mutation of a recognized entity type; also requires a save.
Entry(...).State = ..., Attach followed by a mutation, adding to a navigation collectionSupported through specific syntax and type checks.
Calling a method on an entity, or passing the entity to a method, between reading and savingA heuristic for possible mutation: confidence likely, if no more explicit mutation has been established.
ExecuteUpdate / ExecuteDelete, including Async variantsA direct write without requiring SaveChanges.

Callee facts propagate to callers until no new information appears. This loop is called a fixed-point computation. It is needed, for example, when one method mutates an entity, another saves, and a third calls both.

This is a bounded analysis of code patterns. It does not reconstruct every DbContext instance, transaction, or condition governing whether a save is reached. The word confirmed refers to recognized relationships in the model, not a guarantee of a successful transaction in a running application.

SQL: the position of the unknown fragment matters

SqlAnalyzer recognizes Dapper, ADO.NET, and EF raw SQL. SqlTextFolder recovers the available text, and the ScriptDom T-SQL parser analyzes its structure. A simple regular expression that “finds the word after FROM” is not enough for subqueries, aliases, and other constructs.

// The object name is known. An unknown value does not prevent finding the read.
"SELECT * FROM dbo.Products WHERE Id = " + id

// The object name is unknown. The table cannot honestly be named.
$"SELECT * FROM {table}"

// Several possible price values do not erase the known UPDATE.
$"UPDATE dbo.Products SET Price = {branchyPrice}"

For SQL, folding is limited to one value. A branching fragment is replaced by a neutral parameter in its original position, preserving the known surrounding structure. Alternative shapes of an entire query are not enumerated. The parser may accept the text syntactically, but that does not make an unknown object name known: for example, accessing a table variable is valid T-SQL.

Dynamic SQL through EXEC(@sql) or sp_executesql is neither executed nor guessed: it produces unresolved analysis (Unresolved) with a reason.

The SQL Server catalogue exposes hidden writes (Hidden write)

The database indexer (DB indexer) reads sys.*: procedure definitions, object dependencies, views, and trigger bindings. It neither runs user procedures nor reads rows from user tables. Catalogue-read permissions are checked separately; insufficient access is recorded as a gap.

The operation kind matters: a DELETE trigger is not reached through an INSERT; TRUNCATE does not activate DML triggers in this model. A write with an unknown event set is conservatively matched against all relevant triggers.

A stored procedure that is never called from indexed code does not produce an unguarded-write warning by itself: the finding needs a handler from which the write is reachable. A procedure known to the code when no database has been indexed is one kind of gap; a procedure absent from an indexed catalogue is another.

Only one database is allowed per workspace. The reason is identity: dbo.Products from EF, where the database name is unknown, must meet dbo.Products from the catalogue. Connecting two independent databases would incorrectly merge objects with identical names.

EfReadAnalyzer.cs, EfWriteAnalyzer.cs, SqlAnalyzer.cs, DatabaseIndexer.cs; ADR 0006, ADR 0007.

10 / project boundaries

How a relationship continues into another service

A service here corresponds to a project—that is, an assembly—not a solution. A single .sln may contain Catalog, Pricing, and Notifications. The shared graph links their information while retaining project names in the report.

HTTP and gRPC: who answers this call?

An HTTP read initially becomes an external source (ExternalSource). Then ServiceJoins tries to add a serving relationship (serves) to a method inside the workspace.

  1. Explicit mapping in services. The client name points to a project or solution. A matching endpoint is confirmed.
  2. The client name resembles the project name. After name normalization, the search is restricted to that project; confidence is likely.
  3. A route matches across the whole workspace. A unique candidate produces likely. Several candidates produce an unresolved entry (Unresolved) listing the alternatives.

In the first two cases, the project is already selected, so paths are compared using their known suffixes. The client address and an unknown gateway prefix can be discarded; comparison proceeds from the end using the shorter suffix. At the third tier, the complete route must match. The plugin does not read API gateway configurations.

For gRPC, it uses the service and method names, together with an override in a class with a recognized generated base. A deterministic join has confidence confirmed. If an external read is never joined to code, it remains a terminal dependency.

Events: who publishes and who consumes?

An event recognizer describes the publishing API, how the message type is obtained, and the consumer interface. MediatR, MassTransit, Rebus, and NServiceBus are built in; a custom bus can be described in events. Implementing the consumer interface is considered sufficient static evidence; the analysis does not check bus registration.

If the fully qualified contract names match, the hop is confirmed. If the full names differ but the short names match and the two sides are in different projects, an inferred likely hop is created with the reason “duplicated contract.” Two different types sharing a short name within one project are not joined this way. The original Consumes edge is not rewritten.

Why publication is attributed to the caller

Send(new ProductChanged(id));
Send(new PriceChanged(id));

void Send(BaseEvent message) => bus.Publish(message);

If both types were attributed to the shared Send, every caller would inherit publications belonging to other callers. EventCallAnalyzer recovers the type of expressions, branches, and assignments, and traces parameters back to callers for up to five hops. The publication is attributed to the handler that named the concrete type. The helper itself remains connected by Calls.

Resolution is deferred until code traversal finishes: otherwise, a caller not yet visited would incorrectly appear absent. An indeterminate type, an unavailable caller, or a missing consumer produces an unresolved entry (Unresolved) of kind event.

ServiceJoins.cs, EventCallAnalyzer.cs; ADR 0009, ADR 0010, ADR 0017.

11 / the dependency algorithm

Find the best path without enumerating every path

CacheGraphDependencies.Build starts at a key and finds all methods that fill it. It then follows reads and calls: through views (View), stored procedures (Stored procedure), inner keys, and joined external sources (ExternalSource).

If another key is read, the dependency on that key is retained and traversal continues through the methods that fill it. Depth resets to zero when entering those methods: the limit bounds the call chain, not the number of nested keys. A key is not declared dependent on itself.

Why not simply enumerate every chain?

Imagine that each method makes five calls. At depth 12, this can produce 5¹² = 244 140 625 paths. Many end at the same table. The report does not need hundreds of millions of rows: one good evidence chain (Chain) per source is enough.

The dependency (depends_on) contract: one result per target object, with the strongest reachable confidence, and, among paths at that confidence, the fewest edges.

What the search actually stores

A WalkState is a triple (Source, Confidence, Depth): the current object, the quality of the incoming path, and the depth consumed. Only the shortest arrival is kept for a given triple. PriorityQueue returns states by path length; a separate best dictionary selects the best result for each target object.

All three coordinates are necessary. An arrival with confirmed at depth 10 is better for the current result, but an arrival with likely at depth 2 leaves more room for further exploration. Replacing one alternative with the other could lose a reachable dependency.

  1. Relax records a shorter arrival at a state and enqueues it.
  2. Settle reads an object’s outgoing relationships.
  3. Descend checks the depth limit and proposes a hop.
  4. Offer compares a candidate with the best result for the source.
  5. BuildPath reconstructs the selected chain from predecessor links.

The entire path is not copied at every step: the previous state and transition edges are recorded. Each object has at most three confidence levels and thirteen depth values, rather than an arbitrary number of path histories. An adjacency index provides outgoing relationships without scanning the entire edge list at every step.

A cycle must not masquerade as missing code

The cycle A → B → A can use up the entire depth allowance, but this does not necessarily mean that a source remains unexplored. Rejected descents at the boundary are therefore recorded first and checked after the search: if the object has already been reached with equal or greater confidence, the rejection is not treated as incompleteness. A genuinely long path to an object not yet visited sets DepthLimitReached.

WalkDependencies returns both dependencies and gaps from every visited branch, including those that yielded no source at all. Live-data verification needs this: an empty answer from an unknown helper does not prove that no hidden dependency exists.

Why this algorithm was introduced: the project’s recorded experience

ADR 0018 describes the former path enumeration on the DataService solution: 5,405 vertices and 24,687 edges; the process was stopped after 46 minutes. After the change, indexing returned in 152 seconds in the same documented experiment. This is a historical measurement from the repository, not a test run for this guide or a speed promise for every project. Timing the metrics command alone did not reveal the problem: it does not run rules or compute the dependency closure.

CacheGraphDependencies.cs, CacheGraphAdjacency.cs, ADR 0018.

12 / rules

Which situations does the plugin detect?

FindingCatalog.GetAll invokes the rules and assembles a single list. The current code has six public rule names. It helps to read them as specific questions asked of the graph.

UNGUARDED_WRITE
A write with no invalidation found

The rule takes a table write, finds the responsible handler, and then keys with the role cache that depend on that table. From the responsible method, reachable invalidations are searched through Calls and message hops.

An invalidation covers a key if the store and a supported matching form agree and its modality is Must. For a hidden write, the search is attached to the C# method that reached the procedure or activated the trigger, so invalidation in that method itself is considered.

// Teaching pseudocode, not the implementation text.
for each table write:
    for each associated responsible method:
        find reachable invalidations
        for each dependent cache key:
            if no matching Must invalidation exists:
                create a Finding
                if known TTL <= Budget:
                    mark as suppressed

The staleness budget (Budget) is selected by exact name, then by a schema pattern dbo.*, and otherwise defaults to 60 seconds. This is not a general-purpose glob system. TTL suppression retains the finding in the data; a covering invalidation prevents its creation altogether.

CROSS_SERVICE_GAP
Publication exists, but a covering invalidation does not

A cross-service gap is a variant of the preceding rule. If the search from the original method finds a publication with consumers but still no suitable invalidation, this name is used. A second UNGUARDED_WRITE is not added for the same occurrence. The explanation retains message hops and the projects searched for protection.

The name must be read within the model: it does not prove a broker failure or a lost message. The check looks for reachable invalidation among known consumers. A complete absence of consumers is recorded as unresolved analysis (Unresolved), not an invented delivery path.

ORPHAN_INVALIDATION
Invalidating a key that nobody fills

For each invalidation, the rule looks for at least one matching Caches operation. If none exists, the invalidation is “orphaned.” The comparison is against cache writes, not database writes: Remove("old:product:42") may remain after the key naming scheme changes.

For tag invalidation, TagsAny is used: at least one write carrying the tag is enough. A possible May invalidation is also relevant here. Unlike the staleness rules, this code does not filter writes by role == "cache": it checks whether an invalidation target exists.

PATTERN_MISMATCH
An invalidation almost matches an existing key

For an orphan invalidation, a string skeleton is built by replacing the contents of braces with {}. For example, product:{id} and product:{productId} produce the same skeleton. Among written keys in the same store, the rule then finds the nearest skeleton with a Levenshtein distance of 1 or 2—the number of character insertions, deletions, and substitutions.

products:{} differs from product:{} by one character. This is a useful hint when checking for a typo, but it does not prove that the author intended the suggested key. Ties are resolved deterministically by text. The current catalogue retains both findings: ORPHAN_INVALIDATION and the more specific PATTERN_MISMATCH.

STALE_PARENT_KEY
The inner cache was invalidated, but the composite cache remains

Suppose dashboard:{id} is built by reading product:{id}. The first key is the parent; the second is its dependency. When the second is deleted, the stored dashboard can stay unchanged. The rule looks for invalidation of a dependency from which no unambiguous parent invalidation is reachable.

There is a TTL condition: if the parent has a known lifetime no greater than the dependency’s lifetime, the pair is skipped; a missing dependency lifetime is compared as infinity. A parent without a TTL does not pass this cutoff, including when both lifetimes are absent. This is a practical rule heuristic, not a claim that every other cascading-cache arrangement is safe.

A possible May invalidation of the dependency can initiate a finding, but a May invalidation of the parent does not clear it. Both facts matter: the dependency may disappear, while invalidation of the parent has not been unambiguously established.

EXTERNAL_NO_TTL
An unbounded or overly long-lived external read

If a dependency ends at an external source (ExternalSource) with no serving join (serves), the local graph does not know its changes. The rule creates a finding and suppresses it only if a known TTL is no greater than 60 seconds.

The name EXTERNAL_NO_TTL is shorter than the actual condition: a finding with a TTL greater than 60 seconds also remains visible, not only one without a TTL. This uses the default budget, not settings for a particular table.

How invalidations are matched

CacheKeyCovering first requires the same store label. For tags, it checks membership in the appropriate set; for ordinary strings, it compares skeletons or a known prefix with a trailing *. Placeholder names therefore do not have to match.

An implication when reading the report: product:{id} and product:{otherId} can match in the model even when their parameter values differ in a particular request. Shape matching does not replace value-equality analysis. An API’s string prefix must be represented in a supported form; the analyzer does not execute the library’s deletion algorithm.

FindingCatalog; UnguardedWriteRule, OrphanInvalidationRule and PatternMismatchRule, StaleParentKeyRule, ExternalNoTtlRule, StalenessBudget.

13 / an honest analyzer response

“Found,” “inferred,” and “could not analyze”

Confidence describes the quality of a path in the model. It is neither problem severity nor a percentage probability.

ValueHow to read itExample
confirmedThe current analyzer has established the relationships statically.A directly recognized table read and cache write.
likelyThe path contains an inference from an indirect indicator or an annotation.Several interface implementations; matching short contract names; an inferred EF mutation.
unknownA substantial unresolved entry (Unresolved) prevents a reliable conclusion about the path or coverage.SQL whose structure could not be recovered is reachable from the method.

Along a sequence of relationships, the weakest confidence applies. Among multiple paths to one source, the strongest is selected, then the shortest among equally strong paths. Rules also check gaps on data paths and within the invalidation search scope. A well-understood write therefore does not necessarily yield a fully confirmed finding.

Unresolved analysis (Unresolved) is separate data

An entry contains an identifier, kind, source snippet, location, and reason. Kinds include key, sql, call, cache_api, event, event_api, role. Some gaps are recorded during indexing; others are derived from the current graph, such as an unknown procedure or an ambiguous HTTP destination.

A warning does not necessarily accompany a gap: an unknown key without a literal segment may never produce a vertex usable by a rule. Reading only find_issues without get_unresolved therefore misses an important part of the result.

An annotation adds an explicitly stated assumption

Through annotate, the agent resolves a specific u:... entry: it supplies a key, SQL facts, a call target, an event type, a role, or an API description. The change is applied to the in-memory graph and retains the original snippet, solution, and explanation. New edges have confidence likely.

For cache_api and event_api, a library description is registered and the affected solution is reindexed through the normal path. Related roles (Role) and findings are then recomputed. An annotation can reveal a previously invisible problem or change an earlier conclusion; its provenance remains in the explanation.

An empty warning list must be read alongside loading coverage and gaps. It only means that no rules fired in the constructed model. A region the analyzer could not see does not become verified as a result.

ConfidenceGaps.cs, WorkspaceSession.AnnotateAsync, CONTEXT.md.

14 / live data

Can we check whether the cache is stale now?

Runtime verification is a separate, optional step. Static analysis looks for risk in the program’s structure; this step reads the current state of Redis and SQL Server. The tool still does not run the application, and it does not write to the cache or database.

How entries are selected for comparison

  1. The verify settings define available connections, stores, and mappings from keys to rows. Verification is requested through --verify or permitted with auto: true for the scan workflow.
  2. A bounded verification sample is found using the known template suffix: no more than 20 keys.
  3. Redis traversal uses SCAN, with at most 50 iterations or 5 seconds. An incomplete traversal is explicitly marked.
  4. TYPE determines a supported reading method: strings through GET, supported hash representations through HGET. TTL and idle-time information are also read.
  5. The verify.tables setting maps a placeholder to an identifier column so a parameterized SQL query can read a specific row.
  6. The server compares accessible structured fields and returns only a safe description of the observation.
// A configuration fragment, not a connection command.
"tables": {
  "dbo.Products": { "key": "Id", "from": "id" }
}
// product:{id} → extract id → WHERE [Id] = parameter.

Both parts of the mapping are required: the column name key and the placeholder name from. Without them, there is nothing to compare with a specific stored object, so current staleness cannot be refuted. Rows are read only from tables listed in verify.tables. For other dependencies, only a last-write (Last write) signal from server statistics is available.

Three possible observations (Observation)

ValueBasisWhat it does not mean
possibleComparable fields differ, or there is evidence of a write to a table associated with the finding after the cache entry was created. basis: field_difference, age or both.This does not necessarily prove an error in a particular field: the age signal applies to the entire table.
refutedComparable fields in the corresponding row match, verification is applicable, the sample is not truncated, traversal is complete, and no later-write signal blocks the conclusion.This does not prove correct invalidation on future requests or equality of every possible computed value.
not_verifiableThere is no sufficient comparison method, no keys, insufficient access, or insufficient completeness; a reason is included.This does not mean “the data is fresh,” and it is not necessarily a technical failure.

Across the whole finding, one possible in the sample is enough for that observation. For refuted, the requirements are the opposite: every read entry must support refutation, and incompleteness must not leave a portion unchecked. If a later read fails, an already-observed difference is retained and the result is marked partial.

Why age alone cannot refute staleness

The TTL may have been extended after the entry was created. Or code may have read an old row, waited through someone else’s update, and only then stored the old data in the cache. A young entry therefore does not prove fresh contents.

Last-write time (Last write) applies to an entire table, not a single row, and is evaluated using the server’s clock. A restart or index rebuild can reset the statistics. Unknown age or reset statistics are not interpreted as “there were no writes.” Age can produce possible or prevent refutation, but cannot justify refuted without field comparison.

Why all comparison stays inside the server

Real keys and values must not enter the agent’s context before sensitive data is removed. The server therefore reads, compares, and redacts its response itself. The agent sees a template, a short key hash, field names, and the fact that they differ. A sensitive field is identified by patterns such as email, phone, *password*, *token*, *secret*; extra patterns extend the built-in set.

Verification does not support in-process IMemoryCache, Redis Cluster, multiple Redis endpoints in one connection, or arbitrary value types. A connection with the INFO command disabled is rejected: according to the implementation and ADR, the Redis client could issue a probe write while establishing such a connection. Reaching the SCAN budget stops waiting, but does not cancel a client command already sent.

FindingVerifier.cs, RedisReader.cs, VerificationReader.cs, README: runtime verification, ADR 0011, ADR 0012.

15 / usage

What happens after the scan command?

The user invokes /cache-detective:scan. This is an agent workflow, not a standalone CLI command called cachedet scan: the executable’s main commands are mcp and metrics. The workflow supports --solution <name>, --budget <n> and --verify.

--budget in this workflow sets the unresolved-analysis (Unresolved) review allowance, which defaults to 50. It should not be confused with the staleness budget (Budget) in seconds stored in the configuration.

{
  "version": 1,
  "solutions": ["src/Shop.slnx"],
  "budgets": {
    "dbo.Products": 60,
    "dbo.*": 120
  },
  "services": {
    "CatalogClient": "Catalog"
  }
}

This is a minimal teaching example of .cache-detective/workspace.json. The databases, caches, events, verify and sensitive sections are added as needed. Database and Redis connections are specified as env:VARIABLE_NAME references, rather than actual connection strings. Unknown fields in supported configuration schemas are rejected so a misspelled setting does not appear to work.

MCP toolWhy it is called

workspace_statusCheck status, indexing times, counts, and verification settings.
index_solutionLoad a solution or project and replace its contribution to the shared graph.

The workflow’s sequence

  1. Open the workspace. On the first run, the workflow shows discovered solutions and asks for confirmation of the selection before creating settings; later runs use the saved settings.
  2. Index the selected solutions, then the database catalogue. Failure in one solution must not erase information about the others; loading coverage and diagnostics are retained.
  3. Retrieve findings and unresolved analysis (Unresolved). The workflow assigns bounded review of the latter to the static-analyst agent, then requests findings again after annotations (Annotation).
  4. Retrieve evidence for every finding, reading all pages.
  5. If verification is configured and requested, assign verification calls to runtime-verifier. Keep observations (Observation) as a separate part of the report.
  6. Write the Markdown report .cache-detective/report-<timestamp>.md: groups by confidence, evidence, suppressed findings, loading problems, and remaining gaps.

The workflow’s normal report uses a linear evidence chain (Chain), from top to bottom, with file:line or a database object name. The SVGs in this teaching document explain the algorithm’s structure; they do not change the standard report format.

Why responses are small

MCP responses are limited to about 8 KB and paginated. The full graph lives on the server, while the agent asks narrow questions. Large diagnostics can be split into fragments with a shared identifier and part/parts numbers. These must be reassembled before quoting a message.

Identifiers such as f:1 and u:7 belong to the session. FindingCatalog reuses an identifier based on the finding’s composite identity while the session exists. Annotations (Annotation) are not permanent application edits and do not persist between runs.

16 / model boundaries

What to remember when reading findings

The analysis is useful to the extent that its model matches the application. The current code’s limitations below help you choose the next investigation step.

BoundaryPractical implication
Dependencies at the method and table levelExact columns, rows, and the flow of a particular value into a particular Set are not modeled. An unrelated read can broaden a dependency.
Invalidation is matched by key shapeIdentical skeletons do not prove that id and otherId are equal at runtime.
The store is defined by a recognizerThe plugin distinguishes named categories but does not automatically infer every physical connection, prefix, or isolated in-memory instance.
Reachability is not complete execution analysisOperation order, branch conditions, errors, races, and event delivery are not fully proven. “A path was found” does not mean “that path definitely executed.”
A finite set of APIs and syntax patternsOutput/response caching, unknown libraries, dynamic SQL, and unsupported object-key forms need separate attention. Not every unrecognized external call is guaranteed to produce its own gap.
Bounded depthOrdinary calls are limited to 12 hops; key-building helpers and publication-type tracing to 5. Work hidden beyond the limit may remain unknown.
A TTL may be unrecognizednull in the model does not always mean an intentionally infinite lifetime in the application: the configuration source may have been unavailable to analysis. Such an entry does not receive short-TTL protection.
TTL is a simplified numeric propertyThe code can extract sliding expiration among other values. Its renewal on access and cache-fill races are not modeled; suppression based on a number of seconds should be read as a rule decision, not a universal guarantee of a maximum staleness period.
One database only, and limited loading coverageTwo independent tables sharing a name cannot be reliably separated in one workspace. Missing projects and a different target framework can hide operations.
Live-data comparison is limitedAggregates, arbitrary transformations, dependencies on another cache, or missing row mappings may prevent refutation. An observation applies to the data accessible now.

The access boundary is also specific. The code component reads source and build metadata; the catalogue component reads SQL Server metadata; live verification reads permitted rows and cache entries. The server modifies its managed configuration file, the workflow writes a report, and MSBuild may create ordinary build artifacts. The analyzer itself neither fixes the application nor executes its business operations.

Additional live-data access limitations

The README separately notes that an integration test verifies the catalogue user’s minimum permissions, while no equivalent test verifies the listed minimum permissions for the separate row-verification user. SQL command parameters may also be visible to SqlClient diagnostic subscribers in the same process; hiding values in the MCP response does not close that in-process channel.

18 / self-check

Can you predict the analyzer’s answer?

Try answering before opening the explanations.

1. Get uses product:{id}, while Remove uses product:{productId}. Is this necessarily PATTERN_MISMATCH?

No. When checking coverage, placeholder names are replaced by {}, so the skeletons match. The vertices may still have different textual templates (Template). This comparison does not prove equality of actual parameter values.

2. The TTL is 30 seconds in one Set and absent in another. Will a 60-second budget suppress the warning?

No. The merged TTL is not considered bounded if at least one write has no known lifetime. The staleness budget (Budget) must not hide the risk from the second site.

3. Remove chooses between two keys, and one is the right key. Has protection been found?

No unambiguous protection has been found. Each alternative has modality May. The invalidation is visible in the graph and explanation, but does not suppress an unguarded-write finding.

4. Invalidating the catalog tag affects one of two write sites. Is the invalidation orphaned?

No: TagsAny shows at least one target. But it does not fully protect the key if the second site writes without the tag: TagsAll does not contain that tag.

5. All fields in the available sample match, but Redis traversal is incomplete. Can the result be refuted?

No. The unchecked portion might differ. In the absence of a positive risk signal, the result will be not_verifiable with incompleteness given as the reason.

6. One path to a table is confirmed; another is likely. Should the shorter one always be selected?

No. A dependency (depends_on) result first selects the strongest confidence, and only then the shortest of those paths. During the search, a weaker arrival with more depth remaining may still be needed for other targets.

7. find_issues returns an empty list. What should you inspect next?

Loading coverage, missing projects, and get_unresolved. An unknown data-access implementation may have prevented the construction of writes needed for rules to fire.

8. Verification returned refuted. Can the missing-invalidation warning be deleted?

No. The observation describes matching accessible data at the current moment. The finding describes the code’s structure; the next write could still expose the risk.
